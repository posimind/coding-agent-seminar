# Part 1. 코딩 에이전트 도구 ② 선택과 비용 (3~4장)

## 3장. 도구 선택: 무엇을 기준으로 고르는가

- **핵심 질문**: 필요해지면 언제든 다른 도구로 옮길 수 있으려면 무엇을 알고, 무엇을 갖춰 둬야 하나요
- **도달 목표**: 네 가지 축으로 지금 조건에 맞는 도구를 고르고, 조건이 바뀌면 다시 판단해 옮길 수 있습니다

2장은 "그렇다면 어떤 하네스(도구)를 골라야 하는가"로 끝났습니다. 이 장은 도구 이름으로 답하지 않습니다. 이름으로 답하면 그 답은 몇 달 뒤에 낡습니다. 대신 판단하는 축을 줍니다.

이 장의 메시지는 "도구가 자주 바뀐다"가 아닙니다. **특정 도구에 묶이지 않고, 필요에 따라 언제든 갈아탈 수 있어야 한다**는 것입니다. 그러려면 두 가지가 필요합니다. 지금 조건에 어떤 도구가 맞는지 스스로 판단하는 축(3.1~3.3절), 그리고 도구를 옮겨도 따라오는 형태로 내 자산을 두는 방법(3.4절)입니다. 마지막 절에서는 각자의 조건을 표로 적어 봅니다(3.5절).

### 3.1 사례: 우리 환경의 변천

우리 팀은 주력 도구를 두 번 바꿨습니다. GitHub Copilot에서 opencode + omo로, 다시 Claude Code와 Codex CLI로 옮겼습니다. 이 절은 연혁을 외우게 하려는 것이 아닙니다. **옮길 때마다 어떤 조건이 바뀌었는가**를 보려는 것입니다.

| 시점 | 선택 | 그때 그 선택이 옳았던 조건 | 그 뒤에 바뀐 조건 |
| --- | --- | --- | --- |
| 처음 | GitHub Copilot (Business) | 폐쇄망에서 승인된 유일한 경로였습니다. 자동완성과 채팅에는 충분했습니다 | 여러 단계를 맡기는 에이전트 작업이 늘었습니다 |
| 2026년 1월 | opencode V1 + oh-my-opencode(omo) 플러그인. 백엔드는 같은 Copilot | 요청 수 과금이라 요청 하나에 토큰을 많이 써도 비용이 같았습니다. 하네스를 열어 보고 고칠 수 있었습니다 | 2026년 6월의 토큰 과금 전환, 7월의 Claude 5 세대 모델 |
| 지금 | Claude Code, Codex CLI | 토큰 과금에서는 얇은 하네스가 유리합니다. 최신 모델은 얇은 하네스를 전제로 만들어졌습니다 | (다음 변화) |

#### 첫 번째 이동: 같은 백엔드, 다른 하네스

2026년 1월에 팀이 opencode를 검토할 때 VS Code의 Copilot에는 이미 agent mode가 있었습니다. 에이전트 기능이 없어서 옮긴 것이 아닙니다. 있었는데도 아쉬웠습니다. 2026년 1월 기준으로 팀이 아쉬워한 점은 네 가지입니다.

| 아쉬웠던 점 (2026년 1월 기준) | 1~2장의 용어로 |
| --- | --- |
| 탐색을 일찍 멈춥니다. 조금만 큰 작업이면 관련 파일을 다 보지 않고 결론을 냅니다 | 수집 컨텍스트가 얕습니다 |
| 작업 중간에 끊깁니다. "계속할까요"에 사람이 답해야 이어집니다 | 루프가 과제가 끝나서가 아니라 요청 수 상한에 닿아서 멈춥니다 |
| 팀 규약이 지켜지도록 강제할 방법이 없습니다 | 사용자 하네스에 센서를 넣을 자리가 없습니다 |
| 왜 그렇게 동작했는지 들여다보고 고칠 수 없습니다 | 빌더 하네스를 읽고 고쳐 쓸 수 없습니다 |

opencode는 팀이 이미 가진 Copilot 자격증명을 그대로 백엔드로 붙였습니다. 모델도 같고 과금되는 계정도 같았습니다. 그런데 결과가 달랐습니다. **모델이 같은데 결과가 다르다면 원인은 하네스입니다.** 2.1절의 `Agent = Model + Harness`를 사내에서 직접 확인한 사례입니다. GitHub도 2026년 1월 16일에 Copilot 구독으로 opencode를 쓰는 것을 공식 지원한다고 발표했습니다(출처: [GitHub Changelog, GitHub Copilot now supports OpenCode](https://github.blog/changelog/2026-01-16-github-copilot-now-supports-opencode/), 2026-01-16).

여기에 과금 구조가 겹쳤습니다. 당시 Copilot은 요청 수로 과금했고, 에이전트 기능에서는 사용자가 보낸 프롬프트만 세었습니다.

> "For agentic features, only the prompts you send count as premium requests; actions Copilot takes autonomously to complete your task, such as tool calls, do not."
> (에이전트 기능에서는 사용자가 보낸 프롬프트만 프리미엄 요청으로 센다. 과제를 끝내려고 Copilot이 스스로 하는 동작, 예를 들어 도구 호출은 세지 않는다.)
> 출처: [GitHub Docs, Requests in GitHub Copilot (legacy)](https://docs.github.com/en/copilot/reference/copilot-billing/request-based-billing-legacy/copilot-requests), 2026-10 확인. 지금은 옛 과금 방식에 남은 일부 개인 구독자에게만 적용되는 문서입니다.

요청 하나의 값이 고정이면, 그 요청 안에서 도구를 많이 부르고 컨텍스트를 넓게 모으는 하네스가 사용자에게 이득입니다. omo는 무거운 시스템 프롬프트, 병렬 서브에이전트, 적극적인 컨텍스트 수집으로 이 구조를 끝까지 썼습니다. 토큰은 많이 썼지만 결과가 더 좋았고 비용은 같았습니다. 당시 조건에서는 합리적인 선택이었습니다.

"과금 구조가 하네스의 두께를 정한다"는 설명은 **가설**입니다. 사용자는 프롬프트 단위로 내고 제작사는 모델 제공자에게 토큰 단위로 낸다면, 제작사로서는 루프를 짧게 유지할 이유가 있다는 추론입니다. GitHub이 그런 의도를 밝힌 적은 없습니다. 문서로 확인되는 것은 과금 단위와 요청 수 상한의 기본값뿐입니다.

> **발표자 노트**: 예상 질문은 "`chat.agent.maxRequests`를 올리면 되지 않았는가"입니다. 이 설정은 VS Code Copilot agent mode에서 사용자 프롬프트 한 턴 안에 에이전트가 모델에 보낼 수 있는 요청 수의 상한이고, 상한에 닿으면 계속할지 묻는 확인이 뜹니다. 2026년 1월 당시(VS Code 1.108~1.109) 기본값은 25였고, 1.110(2026-03)부터 소스의 기본값은 50입니다. 공식 설정 문서의 표는 아직 25로 적혀 있습니다(출처: [VS Code 문서, AI settings reference](https://code.visualstudio.com/docs/agents/reference/ai-settings)와 `microsoft/vscode` 저장소 소스, 2026-10 확인). 값을 올리면 위 표의 첫째와 둘째(일찍 멈춘다, 중간에 끊긴다)는 완화됩니다. 셋째와 넷째(강제할 장치가 없다, 하네스를 고쳐 쓸 수 없다)는 이 설정으로 해결되지 않습니다.

> **발표 전 확인**: 위 표의 셋째와 넷째 항목은 2026년 1월 당시의 Copilot에 대한 서술입니다. 이번 조사에서는 현재 상태만 확인했습니다. 당시 팀 기록과 대조합니다.

#### 두 번째 이동: 전제 두 개가 무너졌다

opencode + omo 도입은 두 전제 위에 서 있었습니다. 하네스를 두껍게 돌려도 추가 비용이 없다는 것, 그리고 모델에게 촘촘한 지시가 필요하다는 것입니다. 2026년 여름에 둘 다 바뀌었습니다.

- **과금 구조.** 2026년 6월 1일 Copilot이 요청 수 과금에서 토큰 과금으로 바뀌었습니다(4.1절). 요청 하나에 토큰을 많이 쓸수록 이득이던 구조가 정반대가 됐습니다. 무거운 시스템 프롬프트와 넓은 컨텍스트 수집이 그대로 청구서에 찍힙니다.
- **모델 세대.** 2026년 7월 Anthropic은 Claude 5 세대 모델에 맞춰 Claude Code 시스템 프롬프트의 80% 이상을 지웠습니다(2.5절). 규칙을 촘촘히 나열하고, 예시를 많이 주고, 전부 앞에 싣고, 반복해 강조하는 설계는 구세대 모델에서는 맞았습니다. 최신 모델에서는 같은 설계가 토큰과 사고 시간을 더 쓰게 만듭니다.

그래서 지금은 제작사가 최신 모델에 맞춰 얇게 다듬은 하네스인 Claude Code와 Codex CLI를 씁니다. 백엔드는 여전히 승인된 Copilot입니다(연결 절차는 부록 A).

#### 지금의 선택도 잠정이다

세 번 모두 당시 조건에서는 옳은 선택이었습니다. 틀린 선택을 바로잡은 것이 아니라, 조건이 바뀌어서 옮긴 것입니다. 같은 이유로 지금의 선택도 잠정입니다. 조건은 지금도 움직입니다.

- **지금의 Copilot은 2026년 1월의 Copilot이 아닙니다.** Copilot CLI는 훅을 정식으로 지원하고 `AGENTS.md`와 `CLAUDE.md`를 읽습니다. 앞의 가설이 맞다면, 토큰 과금으로 바뀐 지금은 제작사가 루프를 짧게 유지할 이유도 약해졌습니다. Copilot으로 돌아가는 것이 옳은 선택이 될 수 있습니다.
- **"opencode + omo"도 그때의 그것이 아닙니다.** omo는 저장소 이름이 바뀌었고 v5.0.0(2026-09-26)부터 opencode 플러그인이 아니라 독립 실행형 도구입니다. opencode도 V2(2026-09-11)가 나오면서 플러그인 방식이 달라졌습니다. 지금 같은 이름으로 설치하면 다른 물건이 깔립니다.
- **조건은 또 바뀝니다.** 과금이 다시 바뀌거나, 폐쇄망 제약 때문에 열어 볼 수 있는 하네스가 필요해지면 판단은 달라집니다.

(출처: [GitHub Docs, Hooks](https://docs.github.com/en/copilot/concepts/agents/hooks), [oh-my-openagent 저장소](https://github.com/code-yeongyu/oh-my-openagent), [opencode 문서](https://opencode.ai/docs/), 모두 2026-10 확인)

이 사례에서 가져갈 것은 도구 이름이 아닙니다. 왜 그 도구가 그때 유리했는지를 설명하는 축입니다.

### 3.2 선택의 네 축

3.1절의 두 번의 이동을 설명한 말은 네 가지였습니다. 과금 구조, 모델 세대, 하네스의 두께, 손댈 수 있는 표면의 넓이입니다. **이 네 축을 쥐고 있으면 새 도구가 나와도 스스로 판단합니다.** 축이 없으면 매번 남의 결론을 빌려 와야 합니다.

| 축 | 무엇을 보는가 | 3.1절에서 어떻게 움직였나 |
| --- | --- | --- |
| **과금 구조** | 무엇에 돈이 나가나요? 요청 수인가 토큰인가요? 누구의 계약으로 어느 백엔드에 붙나요 | 요청 수 과금일 때는 두꺼운 하네스가 공짜였습니다. 토큰 과금으로 바뀌자 같은 하네스가 비용이 됐습니다 |
| **모델 세대** | 쓸 수 있는 모델이 무엇이고, 그 하네스가 어느 세대 모델에 맞춰 만들어졌나요 | 구세대 모델에는 촘촘한 규칙이 필요했습니다. Claude 5 세대에서는 같은 규칙이 과잉 제약이 됐습니다(2.5절) |
| **하네스의 두께** | 빌더 하네스가 기본으로 싣는 것이 얼마나 많은가요(시스템 프롬프트, 도구 정의, 오케스트레이션). 얼마나 깊이 탐색하고 어디서 멈추나요 | 일찍 멈추는 하네스가 아쉬워 두꺼운 하네스로 갔고, 두께가 비용이 되자 얇은 하네스로 왔습니다 |
| **손댈 수 있는 표면의 넓이** | 사용자 하네스를 덧댈 자리가 얼마나 있나요(지침, Skill, Hook, MCP, Subagent). 빌더 하네스를 읽고 고칠 수 있나요 | 규약을 강제할 장치와 열어 볼 수 있는 하네스가 필요해 opencode로 갔습니다. 지금은 주요 도구 대부분이 이 표면을 제공합니다 |

네 축은 서로 묶여 있습니다. 과금 구조가 하네스의 적정 두께를 정하고, 모델 세대가 그 두께가 얼마나 필요한지를 정합니다. 그래서 한 축만 보고 고르면 틀립니다. 가장 좋은 모델을 쓸 수 있는 도구가 토큰 과금에서는 가장 비싼 선택일 수 있습니다. 가장 싼 도구가 규약을 강제할 수단이 없어 우리 팀에는 쓸 수 없는 도구일 수 있습니다.

축마다 직접 확인하는 방법이 있습니다.

- **과금 구조**: 요금 문서에서 과금 단위를 읽습니다. 같은 작업을 한 번 시켜 보고 사용량 화면에서 실제 차감을 봅니다(4.11절).
- **모델 세대**: 고를 수 있는 모델 목록과, 조직 관리자가 허용한 모델을 확인합니다.
- **하네스의 두께**: 새 세션에서 아무 요청도 하지 않고 컨텍스트 사용량을 봅니다(1.5절의 `/context`). 이 숫자가 내 환경에서 그 도구의 기본 두께입니다.
- **손댈 수 있는 표면**: 내가 쓰려는 부품(5~6장)을 그 도구가 받는지, 강제 장치인 훅이 있는지 문서로 확인합니다.

#### 두께 축은 읽는 방향이 뒤집혔다

네 축 가운데 **하네스의 두께**는 뜻이 한 번 뒤집혔습니다. 예전에는 빌더 하네스가 촘촘한 시스템 프롬프트로 모델을 얼마나 잘 끌고 가는지가 도구의 장점이었습니다. 요청 수 과금에서는 그 두께가 사용자에게 공짜이기도 했습니다(3.1절). 지금은 제작사들이 스스로 그 지시를 덜어 내고 모델의 판단에 맡깁니다. Anthropic은 Claude Code 시스템 프롬프트의 80% 이상을 지웠고, OpenAI도 얇은 프롬프트에서 평가 점수가 오르고 토큰이 줄었다고 적습니다(2.5절).

그래서 두께는 **장점이 아니라 비용 항목**으로 읽습니다. 축이 없어지지는 않습니다. 두께가 0이 될 수는 없으므로, "얼마나 촘촘하게 통제하는가"를 묻는 대신 **"얼마나 얇은가, 그리고 내가 그것을 잴 수 있는가"** 를 묻습니다.

#### 그러면 무엇으로 고르는가

제작사들의 시스템 프롬프트가 함께 얇아지면 그 문구의 차이로 도구를 가르기 어려워집니다. 남는 차이는 글이 아니라 **기계 장치**입니다. 네 가지를 봅니다.

| 평가 항목 | 왜 이것이 남는가 | 확인 방법 |
| --- | --- | --- |
| 컨텍스트 관리 기능 | 지시를 덜어 낸 자리를 "필요할 때만 싣기"가 메웁니다. 2.5절 여섯 전환의 셋째가 이것입니다 | tool search의 유무와 기본값(4.8절), 압축 뒤에 무엇이 살아남는가(1.3절), 경로 조건부 지침(5.3절), 서브에이전트 격리(6.3절) |
| 도구와 인터페이스의 설계 | 사용법이 시스템 프롬프트에서 **도구 설명**으로 옮겨 갔습니다(여섯 전환의 둘째·넷째). 이제 도구 정의의 표현력이 결과를 가릅니다 | 내장 도구의 종류, 코드 탐색의 정확도, 편집이 실패했을 때 어떤 메시지를 돌려주나요 |

| 측정과 감사 수단 | 지침 문구로 조율할 수 없으면 재서 조율합니다 | `/context`, `/usage`의 캐시 통계(4.11절), 지침 감사 명령(5.2절) |

이 넷은 새 축이 아닙니다. 3.3절 비교표의 "하네스의 두께"와 "손댈 수 있는 표면" 두 행이 실제로 재고 있는 것입니다. 축 이름은 그대로 두고 그 안에서 보는 항목이 바뀌었습니다. 폐쇄망에서는 과금과 승인된 백엔드가 여전히 먼저 거른다는 점도 바뀌지 않았습니다(3.5절).

### 3.3 주요 도구 비교

네 축으로 주요 도구 넷을 놓아 봅니다. 아래 표는 결론이 아니라 **2026년 10월 시점의 스냅숏**입니다. 3.1절에서 봤듯이 칸의 내용은 몇 달 사이에 바뀝니다. 표를 외우지 말고 표를 채우는 방법을 가져갑니다.

기준 버전은 VS Code 1.141, GitHub Copilot CLI v1.0.95, Claude Code v2.1.296, Codex CLI rust-v0.162.1, opencode v1.19.0입니다(모두 2026-10-12 확인). opencode는 V1(1.x)과 V2(2.x)가 함께 배포되고 있고 동작이 다릅니다. 아래 표는 V1 기준이고 V2가 다른 곳은 따로 적었습니다.

표를 읽기 전에 알아 둘 변화가 있습니다. **VS Code는 이제 여러 하네스를 고르는 호스트입니다.** 세션을 시작할 때 Copilot, Claude, Codex, Local, Cloud 가운데 하나를 고릅니다. Copilot 하네스는 Copilot SDK 기반이어서 Copilot CLI와 같은 계열이고, 예전부터 있던 VS Code agent mode는 Local 하네스로 남아 있습니다. Claude 하네스는 Anthropic의 Claude Agent SDK로 돌고, 사용량을 Copilot 구독으로 과금할 수 있습니다. 문서는 모델을 고르는 것과 하네스를 고르는 것이 별개라고 적습니다(출처: [VS Code 문서, Understand agent harnesses](https://code.visualstudio.com/docs/agents/concepts/agent-harnesses), 2026-10 확인). 그래서 "VS Code의 Copilot"이라고만 말하면 어느 하네스인지 정해지지 않습니다.

두 표에서 읽을 것은 세 가지입니다.

- **부품의 종류는 수렴했습니다.** 지침, Skill, MCP, Hook, Subagent가 네 도구 모두에 있습니다. 3.1절의 "강제할 장치가 없다"는 이제 도구를 가르는 기준이 아닙니다.
- **형식은 아직 다릅니다.** 지침과 Skill과 MCP는 같은 파일을 여러 도구가 읽습니다. Hook과 Subagent는 도구마다 설정 형식이 다르고, Plugin은 도구마다 뜻부터 다릅니다. 이 차이가 3.4절의 주제입니다.
- **지금 도구를 가르는 것은 과금과 백엔드입니다.** 폐쇄망에서는 승인된 백엔드에 붙일 수 있는가가 먼저 걸러 냅니다. 그다음이 기본 컨텍스트를 줄이는 수단이 내 환경에서 실제로 동작하는가입니다(4장).

> **발표 전 확인**: 두 가지는 문서에서 확인하지 못했으므로 발표에서 단정하지 않습니다. VS Code의 Copilot 하네스에 Copilot CLI의 tool search가 같은 방식으로 적용되는지, Codex CLI를 커스텀 프로바이더에 붙였을 때도 도구 정의가 미뤄 실리는지입니다.

### 3.4 갈아탈 수 있게 해 두기

도구를 옮길 때 비용이 드는 것은 설치가 아닙니다. 그동안 쌓은 사용자 하네스를 다시 만드는 일입니다. 그래서 갈아탈 수 있으려면 **무엇이 그대로 옮겨지고 무엇을 다시 만들어야 하는지**를 미리 알고, 다시 만들어야 하는 쪽을 얇게 유지해야 합니다.

| 자산 | 옮기기 | 근거 | 주의 |
| --- | --- | --- | --- |
| MCP 서버 | 쉽습니다 | 공개 규격입니다. 서버는 그대로 두고 연결 설정만 다시 적습니다 | 설정 파일의 위치와 형식은 도구마다 다릅니다(3.3절) |
| Skill | 대체로 쉽습니다 | Agent Skills 공개 규격입니다. 네 도구가 모두 `SKILL.md`를 읽습니다 | 표준 필드와 일반 마크다운 본문만 쓴 스킬이 그대로 옮겨집니다. 디렉터리 위치가 도구마다 다릅니다 |
| 지침 파일 | 쉽습니다 | `AGENTS.md`를 네 도구가 모두 읽습니다 | Claude Code에는 조건이 있습니다(아래) |
| Hook | 다시 만듭니다 | 도구별 설정 형식입니다 | 훅이 부르는 검사 스크립트는 그대로 쓸 수 있습니다 |
| Subagent | 다시 만듭니다 | 도구별 정의 형식입니다(Markdown, TOML) | 프롬프트 본문은 옮길 수 있습니다 |
| Plugin | 일부만 옮겨집니다 | 공개 규격이 Skill과 MCP 묶음만 정합니다 | Claude Code와 opencode는 그 규격의 호환 목록에 없습니다(아래) |

#### 공개 규격인 것: MCP와 Agent Skills

MCP(Model Context Protocol)는 에이전트를 외부 도구와 데이터에 연결하는 공개 규격입니다(개념은 6.1절). 2025년 12월에 Linux Foundation 산하 Agentic AI Foundation으로 넘어갔고, `AGENTS.md`도 같은 재단 소속입니다(출처: [MCP 블로그, MCP joins the Agentic AI Foundation](https://blog.modelcontextprotocol.io/posts/2025-12-09-mcp-joins-agentic-ai-foundation/), 2025-12-09). 서버 하나를 만들어 두면 도구를 바꿔도 서버는 그대로입니다.

Agent Skills는 Anthropic이 만들어 공개 표준으로 내놓은 스킬 형식입니다(출처: [agentskills.io](https://agentskills.io/), 2026-10 확인). 여기에는 조건이 붙습니다. Claude Code는 표준에 자기 필드와 본문 기능을 더했습니다. 그래서 정확한 말은 "스킬은 그대로 옮겨진다"가 아니라 **"표준 필드와 일반 마크다운 본문만 쓴 스킬이 그대로 옮겨진다"** 입니다. Claude Code 문서는 Claude Code 밖(claude.ai, API)에서는 표준의 여섯 필드만 쓸 수 있고, 명령 실행 결과를 본문에 끼워 넣는 것 같은 전용 기능은 동작하지 않는다고 적습니다(출처: [Claude Code 문서, Skills](https://code.claude.com/docs/en/skills), 2026-10 확인). 다른 회사의 도구로 옮길 때도 같은 기준으로 보면 안전합니다. 디렉터리도 확인합니다. 문서 기준으로 `.agents/skills`는 Copilot, Codex CLI, opencode가 읽고 `.claude/skills`는 Claude Code, Copilot, opencode가 읽습니다. 네 도구가 모두 읽는 디렉터리는 없습니다.

#### 지침 파일: `AGENTS.md`를 단일 원본으로

지침 파일은 `AGENTS.md` 하나를 원본으로 둡니다. `AGENTS.md`는 필수 필드가 없는 일반 마크다운이고 Copilot, Codex CLI, opencode가 모두 직접 읽습니다. 예전에는 도구마다 파일이 따로 필요해 심볼릭 링크로 맞췄지만 이제 대부분 필요 없습니다.

Claude Code도 `AGENTS.md`를 직접 읽습니다. 다만 조건을 정확히 알아야 합니다(출처: [Claude Code 문서, Memory](https://code.claude.com/docs/en/memory#agents-md), 2026-10 확인).

- **버전.** 직접 읽기는 v2.1.277부터입니다. 문서는 "Amazon Bedrock이나 텔레메트리를 끈 세션처럼 일부 세션"은 v2.1.281 이전에는 `CLAUDE.md`만 읽었다고 적습니다. 사내 게이트웨이 연결이 그 "일부"에 드는지는 문서에 명시돼 있지 않으므로 **v2.1.281 이상**을 기준으로 삼습니다.
- **기본 동작.** 작업 디렉터리나 그 위에 `CLAUDE.md`가 없을 때만 `AGENTS.md`를 읽습니다. `.claude/CLAUDE.md`와 `CLAUDE.local.md`도 "있음"으로 칩니다. 개인용 `CLAUDE.local.md` 하나만 있어도 기본값에서는 `AGENTS.md`가 빠집니다.
- **설정.** 둘을 어떻게 읽을지는 `/config`의 Project instructions 항목으로 정합니다. 기본값은 `claude-md-or-agents-md`(`CLAUDE.md`가 없을 때만 `AGENTS.md`)이고, `claude-md-and-agents-md`로 바꾸면 둘 다 읽습니다.
- **확인.** 세션을 시작할 때 `no CLAUDE.md found; AGENTS.md loaded: …` 줄이 보이는지, `/context`의 Memory files에 `AGENTS.md`가 있는지 봅니다(v2.1.280 이상).

Claude Code 전용 지침이 따로 필요하거나 직접 읽기가 되지 않는 세션이라면, `CLAUDE.md`에 import 한 줄을 두고 그 아래에 전용 내용을 적습니다. 원본은 여전히 `AGENTS.md` 하나입니다.

```markdown
@AGENTS.md

## Claude Code

`src/can/` 아래를 고칠 때는 Plan mode로 계획을 먼저 받는다.
```

지침 파일의 계층과 작성법은 5.2절에서, 필요할 때만 읽히게 하는 방법은 5.3절에서 다룹니다.

> **발표 전 확인**: 사내 환경에서 `/config`에 Project instructions 항목이 보이는지, 세션을 시작할 때 `AGENTS.md loaded` 줄이 나오는지 실제 세션으로 확인합니다. 문서는 게이트웨이 토큰만으로 연결한 구성에서 일부 기능이 빠질 수 있다고 적습니다.

#### 도구별 형식인 것: Hook, Subagent, Plugin

훅과 서브에이전트는 도구마다 형식이 달라 옮길 때 다시 만들어야 합니다. 훅은 Copilot CLI가 `.github/hooks/*.json`, Claude Code가 `settings.json`, Codex CLI가 `hooks.json`을 쓰고 opencode는 플러그인 코드로 구현합니다. 서브에이전트 정의는 Copilot, Claude Code, opencode가 Markdown이고 Codex CLI는 TOML입니다. 서로의 형식을 읽어 주는 움직임은 있습니다. Copilot CLI는 `.claude/settings.json`의 훅과 `.claude/agents`의 정의를 읽고, Codex CLI의 훅은 Claude Code와 같은 구조를 씁니다. 그래도 한 번 만들면 어디서나 도는 수준은 아닙니다.

플러그인에는 단서가 있습니다. 2026년 8월에 공개 규격 Agent Plugins 1.0이 나와 Skill과 MCP 서버 묶음의 공통 패키지 형식을 정했고, VS Code, GitHub Copilot, Codex 등이 지원합니다. 그러나 2026년 10월 기준으로 Claude Code와 opencode는 호환 클라이언트 목록에 없습니다. 규격이 정하는 것도 Skill과 MCP뿐이어서, 훅과 에이전트 정의는 플러그인 안에서도 도구 전용 확장으로 남습니다(출처: [agent-plugins.org](https://agent-plugins.org/), 2026-10 확인).

결론은 이 구분에서 바로 나옵니다. **지식은 지침과 스킬에 두고, 도구 전용 부품은 얇게 유지합니다.** 팀의 규약, 절차, 체크리스트, 도메인 지식처럼 오래 쌓이는 것은 옮겨지는 형식에 적습니다. 훅에는 검사 로직을 직접 쓰지 않고 저장소의 스크립트를 부르는 한 줄만 둡니다. 그러면 도구를 바꿀 때 다시 쓰는 것은 그 한 줄입니다.

### 3.5 내 조건 점검표

네 축과 이식성을 내 상황에 대어 보는 표입니다. 다섯 가지를 적으면 후보가 좁혀집니다. 셋째 열은 사내 기본 환경을 예로 채웠습니다. 마지막 열을 각자 채웁니다.

| 점검 항목 | 물을 것 | 예: 사내 기본 환경 | 내 답 |
| --- | --- | --- | --- |
| 승인된 백엔드 | 코드를 보낼 수 있도록 승인된 모델 제공 경로가 무엇인가요 | GitHub Copilot Business (폐쇄망) | |
| 과금 방식 | 요청 수인가 토큰인가요? 한도와 초과 정책은 무엇인가요 | 토큰 기반 AI 크레딧, 사용자당 월 1,900 (4.1절) | |
| 터미널/IDE 선호 | 주로 어디서 일하나요? 긴 작업을 맡기나요, 짧게 주고받나요 | 각자 다릅니다 | |
| 필요한 확장 부품 | 지금 쓰거나 곧 쓸 부품이 무엇인가 (지침, Skill, MCP, Subagent) | 각자 다릅니다 (5~7장에서 정합니다) | |
| 강제 장치 필요 여부 | 요청이 아니라 강제로 지켜야 하는 규칙이 있나요 | 있습니다. 코딩 규칙 검사, 위험한 명령 차단 | |

답은 다음과 같이 도구를 좁힙니다.

- **승인된 백엔드**가 가장 먼저 거릅니다. 그 백엔드에 붙일 수 없는 도구는 다른 칸이 아무리 좋아도 후보가 아닙니다.
- **과금 방식**이 하네스의 적정 두께를 정합니다. 토큰 과금이면 기본 컨텍스트를 재고 줄일 수 있는 도구가 유리합니다(4장).
- **터미널/IDE 선호**는 대개 마지막에 정해도 됩니다. 같은 하네스가 CLI와 IDE 양쪽에 있는 경우가 많습니다(3.3절).
- **필요한 확장 부품**은 3.3절의 부품 표와 대조합니다. 지금 쓰는 부품이 옮겨지는 형식인지도 함께 봅니다(3.4절).
- **강제 장치**가 필요하면 훅을 지원하는 도구여야 합니다. 지침은 요청이고 훅은 강제입니다(5.5절).

이 표는 한 번 채우고 끝내는 것이 아닙니다. **조건이 바뀔 때 다시 채웁니다.** 다시 채울 신호는 네 축에서 나옵니다. 과금 정책이 바뀌었을 때, 새 세대 모델이 나왔을 때, 승인된 경로가 늘거나 줄었을 때, 팀에 강제해야 할 규칙이 새로 생겼을 때입니다. 3.1절의 두 번의 이동도 이 신호에서 시작했습니다.

> **발표자 노트**: 표를 채우는 데 2분을 줍니다. 도구는 하나를 주력으로 정하고 나머지는 보조로 두기를 권합니다. 두 도구를 어중간하게 나눠 쓰면 사용자 하네스를 두 벌 관리하게 됩니다.

### 핵심 정리

- 도구는 과금 구조, 모델 세대, 하네스의 두께, 손댈 수 있는 표면의 넓이라는 네 축으로 고르고, 지금의 선택은 조건이 바뀌면 다시 내리는 잠정 결론입니다.
- 도구 비교표는 스냅숏이므로 외우지 않고, 축마다 직접 확인하는 방법을 가져갑니다.
- 지식은 옮겨지는 형식(`AGENTS.md`, 표준 필드만 쓴 스킬, MCP)에 두고 도구 전용 부품(훅, 서브에이전트, 플러그인)은 얇게 유지합니다.

## 4장. 비용: 확실하게 줄일 수 있는 것부터

- **핵심 질문**: 비용을 줄이려면 무엇부터 손대야 하나요
- **도달 목표**: 모호한 가이드라인 대신 효과가 확실한 절감 항목을 찾아 적용합니다. `/context`로 자기 세션의 고정 비용을 읽고 tool search가 실제로 동작하는지 확인합니다

3장은 "네 축 중 과금 구조는 실제로 얼마의 차이를 만드는가"로 끝났습니다. 이 장은 그 차이를 숫자로 보고, 줄이는 순서를 정합니다.

논지는 네 걸음입니다. 비용 절감 가이드로 가장 많이 거론되는 것은 "항상 프런티어 모델(그 시점의 최상위 모델)을 쓰지 말고 작은 일에는 저렴한 모델을 쓰라"입니다. 맞는 말입니다. 그런데 맡기려는 일이 큰 일인지 작은 일인지는 시작 전에 모호한 경우가 많고, 잘못 고르면 재작업이 생겨 비용이 오히려 늘어납니다. 새 모델이 빠르게 나와 가이드라인을 그때마다 다시 만들어야 하는 부담도 있습니다. 그래서 결론은 이렇습니다. 모호한 가이드라인을 만드는 데 힘쓰기보다, **확실하게 비용을 줄일 수 있는 부분을 먼저 찾아 적용하는 편이 효율적입니다.** 그 첫 대상이 쓰지 않아도 매 호출에 실리는 고정 컨텍스트이고, 그중 가장 큰 것이 MCP입니다. 4.1 ~ 4.3절이 이 논지를 차례로 풀고, 4.4 ~ 4.9절이 MCP를, 4.10 ~ 4.11절이 나머지 항목과 확인 방법을 다룹니다.

### 4.1 무엇이 과금되는가

2026년 6월 1일, GitHub Copilot의 모든 요금제가 **요청 수 과금에서 토큰 과금으로** 바뀌었습니다. 요청 횟수를 세던 프리미엄 요청 단위(PRU)가 없어지고, 사용한 토큰만큼 GitHub AI Credits가 차감됩니다(출처: [GitHub Blog, GitHub Copilot is moving to usage-based billing](https://github.blog/news-insights/company-news/github-copilot-is-moving-to-usage-based-billing/), 2026-04-27. [GitHub Docs, Usage-based billing for organizations and enterprises](https://docs.github.com/en/copilot/concepts/billing-and-usage/organizations-and-enterprises/billing), 2026-10 확인).

| 항목 | 내용 |
| --- | --- |
| 과금 단위 | 입력 토큰, 출력 토큰, 캐시 토큰. 모델별 단가로 계산해 크레딧으로 환산합니다. 1 크레딧 = $0.01 |
| Copilot Business 포함량 | 사용자당 월 1,900 크레딧($19). 요금제 가격은 바뀌지 않았습니다 |
| 프로모션 | 2026년 6~8월에 월 3,000 크레딧으로 올려 주던 프로모션은 끝났습니다 |
| 크레딧을 쓰는 단위 | 사용자별이 아니라 청구 단위로 합쳐 씁니다. 이월되지 않고 매월 1일에 초기화됩니다 |
| 크레딧을 쓰는 기능 | Copilot Chat, Copilot CLI, 클라우드 에이전트, 서드파티 코딩 에이전트 등 |
| 무료로 남은 기능 | 코드 자동완성과 next edit suggestion |

실무에서 기억할 변화는 두 가지입니다.

첫째, **저가 모델 자동 폴백이 사라졌습니다.** 예전에는 한도를 다 쓰면 저가 모델로 넘어가 계속 일할 수 있었습니다. 지금 문서는 이렇게 적습니다. "There is no automatic fallback to lower-cost models when a budget is exhausted."(예산을 다 써도 저가 모델로 자동 전환되지 않는다.) 한도 뒤에 무슨 일이 일어나는지는 조직 설정이 정합니다. 조직과 엔터프라이즈는 추가 사용이 기본으로 켜져 있습니다. 관리자가 정책을 끄지 않으면 포함량을 다 쓴 뒤에 차단되는 것이 아니라 추가로 과금됩니다. 초과는 스스로 막아야 합니다(4.11절).

둘째, **1.4절의 구조가 그대로 청구서가 됩니다.** 요청 수 과금에서는 프롬프트 하나의 값이 같았습니다. 그 안에서 도구를 몇 번 부르든, 컨텍스트가 얼마나 크든 상관없었습니다. 토큰 과금에서는 매 호출이 실어 보낸 만큼 차감됩니다. 고정 영역은 호출 수만큼 곱해지고 누적 영역은 세션이 길수록 커집니다. 컨텍스트를 설계하는 일이 곧 비용을 설계하는 일이 됐습니다.

### 4.2 흔한 처방: 모델과 effort를 골라 쓰기

비용을 줄이라고 하면 가장 먼저 나오는 처방은 모델을 골라 쓰라는 것입니다. Claude Code의 비용 문서도 그렇게 권합니다.

> "Sonnet handles most coding tasks well and costs less than Opus. Reserve Opus for complex architectural decisions or multi-step reasoning."
> (Sonnet은 대부분의 코딩 작업을 잘 처리하고 Opus보다 싸다. Opus는 복잡한 아키텍처 결정이나 여러 단계의 추론에 아껴 쓴다.)
> 출처: [Claude Code 문서, Manage costs effectively](https://code.claude.com/docs/en/costs#choose-the-right-model), 2026-10 확인

같은 문서는 effort(모델이 얼마나 깊이 추론할지 정하는 설정)도 깊은 추론이 필요 없는 단순한 작업에서는 낮춰서 비용을 줄일 수 있다고 적습니다. **맞는 말입니다.** 단가 차이는 실제로 큽니다. GitHub Copilot 가격표에서 입력 100만 토큰당 단가는 Claude Opus 5.5가 $4, Sonnet 5.5가 $2, Haiku 5.5가 $0.10(입력 10만 토큰 이하 구간)입니다(출처: [GitHub Docs, Models and pricing for GitHub Copilot](https://docs.github.com/en/copilot/reference/copilot-billing/models-and-pricing), 2026-10 확인).

문제는 이 처방을 지키기가 어렵다는 데 있습니다. 이유는 세 가지입니다.

1. **일의 크기를 미리 알기 어렵습니다.** "CAN 수신 버퍼 크기 상수를 하나 바꾼다"는 작아 보입니다. 그런데 그 상수가 ISR의 처리 시간과 다른 모듈의 정적 배열 크기에 걸려 있으면 큰 일입니다. 크기는 대개 일을 해 봐야 드러납니다. 시작 전에 모델을 고르라는 것은 결과를 미리 알라는 요구에 가깝습니다.
2. **잘못 고르면 더 듭니다.** 프런티어 모델이 필요한 일을 중저가 모델에 맡기면, 틀린 결과를 검토하고 다시 시키고 결국 상위 모델로 다시 합니다. 재작업에는 토큰만 드는 것이 아닙니다. 사람의 검토 시간이 함께 듭니다. 세션 도중에 모델을 바꾸는 것도 공짜가 아닙니다. 모델마다 캐시가 따로여서 바꾼 직후의 요청은 대화 전체를 캐시 없이 다시 읽습니다(4.10절).
3. **가이드라인이 금방 낡습니다.** "이런 일에는 이 모델과 이 effort"라는 표를 만들려면 모델별로 우리 작업을 돌려 보고 비교해야 합니다. 그런데 새 모델이 나올 때마다 성능과 단가의 조합이 바뀝니다. 같은 가격표에서 Opus 5.5(입력 $4, 출력 $20)는 앞서 나온 Opus 5(입력 $5, 출력 $25)보다 쌉니다. 모델 이름으로 적어 둔 가이드라인은 그 순간 낡습니다. 그때마다 분석을 다시 하는 공수가 절감액보다 클 수 있습니다.

그래서 "어떤 상황에 어떤 모델과 effort를 쓸지"는 팀 가이드라인으로 잡기 어렵습니다. 이 처방을 버리자는 것이 아닙니다. **순서를 뒤로 미루자는 것입니다.** 판단이 필요 없는 절감을 먼저 다 적용하고, 모델 선택은 마지막에 각자의 경험으로 조정합니다(4.11절 체크리스트의 마지막 항목).

> **질문**: 최근에 간단할 줄 알고 맡겼다가 커진 작업이 있었나요? 시작 전에 그 크기를 알 수 있었나요?

### 4.3 확실한 절감의 기준

이 장에서 "확실한 절감"은 세 가지 기준을 모두 채우는 것을 말합니다.

1. **판단이 필요 없습니다.** 작업마다 "이번에는 해당하는가"를 따지지 않아도 됩니다.
2. **한 번 설정하면 계속 적용됩니다.** 습관이나 기억에 기대지 않습니다.
3. **품질을 깎지 않습니다.** 결과가 나빠질 위험과 맞바꾸는 절감이 아닙니다.

세 기준을 모두 채우는 대상은 1.4절의 그림에서 바로 나옵니다. 고정 영역은 쓰든 안 쓰든 매 호출에 실리므로 비용이 **고정 영역 × 호출 수**로 늘어납니다. 여기서 쓰지 않는 부분을 덜어 내면 모든 작업, 모든 호출에서 그만큼 줄어듭니다. 무엇을 덜어 낼지 작업마다 판단할 필요가 없고, 쓰지 않던 것이므로 품질도 깎이지 않습니다.

이 장에서 다루는 절감 항목을 세 기준에 대어 보면 순서가 정해집니다.

| 절감 항목 | 판단이 필요 없는가 | 한 번 설정하면 계속되는가 | 품질을 깎지 않는가 |
| --- | --- | --- | --- |
| MCP 도구 정의를 필요할 때만 싣기 (tool search, 4.8절) | 그렇습니다 | 그렇습니다 | 그렇습니다 |
| 쓰지 않는 MCP 서버 끊기, 지침 다이어트 (4.10절) | 처음 한 번만 판단합니다 | 그렇습니다 | 그렇습니다 |
| 캐시가 깨지지 않게 쓰기, 세션을 목적 단위로 끊기 (4.10절) | 그렇습니다 | 아닙니다. 습관입니다 | 그렇습니다 |
| 모델과 effort 골라 쓰기 (4.2절) | 아닙니다. 매번 판단합니다 | 아닙니다 | 잘못 고르면 깎습니다 |

위에서 아래로 갈수록 확실함이 줄어듭니다. 이 장의 나머지는 이 순서를 따릅니다. 먼저 고정 영역에서 가장 큰 덩어리인 MCP를 봅니다.

### 4.4 왜 MCP가 유난히 큰가

MCP(Model Context Protocol)는 에이전트를 이슈 트래커, 문서 저장소, 사내 시스템 같은 외부 도구에 연결하는 공개 규격입니다. 연결된 MCP 서버는 자기가 제공하는 도구의 목록을 에이전트에 알려 주고, 모델은 그 도구를 내장 도구처럼 호출합니다. 개념과 보안은 6.1~6.2절에서 다루고, 여기서는 비용만 봅니다.

고정 영역을 구성 요소별로 놓고 보면 MCP만 성격이 다릅니다. 아래는 Claude Code 기준이고, 부품별 로드 시점과 비용은 5.1절에서 다시 정리합니다.

| 구성 요소 | 세션을 시작할 때 실리는 것 | 크기를 정하는 사람 | 늘어나는 방식 |
| --- | --- | --- | --- |
| 시스템 프롬프트, 내장 도구 | 전체 | 도구 제작사가 다듬어 둡니다 | 고정 |
| 지침 파일 | 전체 | 내가 씁니다 | 쓴 만큼 |
| Skill | 이름과 설명만. 본문은 쓸 때 실립니다 | 스킬 작성자 | 스킬 하나에 설명 한 줄 |
| Subagent 정의 | 이름과 설명 | 내가 씁니다 | 정의 개수만큼 |
| **MCP** (tool search 없이) | **모든 도구의 정의 전체** | **서버를 만든 쪽** | 서버 수 × 도구 수 × 스키마 크기 |

MCP가 이렇게 되는 이유는 프로토콜에서 시작합니다. 에이전트는 `tools/list` 요청으로 서버의 도구 목록을 받습니다. 응답의 항목 하나하나가 이름만이 아니라 설명과 입력 스키마를 포함한 **도구 정의 전체**입니다. 아래는 MCP 스펙(2026-07-28)의 응답 예시에서 도구 하나를 옮긴 것입니다(아이콘 항목은 뺐습니다).

```json
{
  "name": "get_weather",
  "title": "Weather Information Provider",
  "description": "Get current weather information for a location",
  "inputSchema": {
    "type": "object",
    "properties": {
      "location": { "type": "string", "description": "City name or zip code" }
    },
    "required": ["location"]
  }
}
```

이것은 파라미터가 하나뿐인 가장 단순한 도구입니다. 실제 서버의 도구는 파라미터가 여럿이고 설명이 깁니다. 그리고 프로토콜에는 이름만 받거나 도구 하나의 스키마만 받는 메서드가 없습니다. 도구에 관한 메서드는 `tools/list`와 `tools/call` 둘뿐입니다(출처: [MCP 스펙 2026-07-28, Tools](https://modelcontextprotocol.io/specification/2026-07-28/server/tools), 2026-10 확인).

여기서 한 가지를 구분합니다. 받은 정의를 **전부 모델 컨텍스트에 넣는 것은 스펙의 요구가 아닙니다.** 스펙은 정의를 어떻게 주고받는지만 정합니다. 그것을 모델에 어떻게 보여 줄지는 호스트(에이전트 프로그램)가 정합니다. MCP 공식 문서는 받은 정의를 대화를 시작할 때 전부 모델에 넘기는 구현을 "naive"(순진한) 구현이라고 부릅니다(출처: [MCP 문서, Client Best Practices](https://modelcontextprotocol.io/docs/2026-07-28/develop/clients/client-best-practices), 2026-10 확인). 이 구분이 4.8절 해법의 출발점입니다. 순진한 구현에서 MCP의 고정 비용이 유난히 큰 이유는 네 가지입니다.

- **곱셈으로 늘어납니다.** 서버 하나를 붙이면 도구가 수십 개씩 한꺼번에 들어옵니다. 서버 수 × 도구 수 × 스키마 크기입니다.
- **스키마는 토큰을 많이 쓰는 형식입니다.** 중괄호, 키 이름, 타입, 파라미터마다 붙는 설명이 모두 토큰입니다.
- **사용자가 줄일 수 없습니다.** 지침 파일은 내가 고치면 되지만, 받아 쓰는 서버의 도구 설명과 스키마는 서버를 만든 쪽이 정합니다.
- **쓰지 않아도 실립니다.** 이번 작업에서 이슈 트래커를 한 번도 부르지 않아도 그 도구 정의는 매 호출에 실립니다.

규모는 Anthropic이 공개한 예로 가늠할 수 있습니다. GitHub(도구 35개, 약 26K 토큰), Slack(11개, 약 21K), Sentry(5개, 약 3K), Grafana(5개, 약 3K), Splunk(2개, 약 2K) 다섯 서버를 붙이면 도구 58개가 대화를 시작하기도 전에 약 55K 토큰을 차지합니다. 도구 하나에 수백에서 천여 토큰꼴입니다(출처: [Anthropic, Introducing advanced tool use on the Claude Developer Platform](https://www.anthropic.com/engineering/advanced-tool-use), 2025-11-24). 1.5절의 예시 화면에서 `MCP tools` 행이 가장 컸던 이유가 이것입니다.

### 4.5 얼마나 차이가 나는가

1.5절의 예시 화면은 아무 요청도 하지 않은 상태가 118k 토큰(12%)이었고 그중 `MCP tools`가 89.0k였습니다. 이 가운데 약 80K가 "있으면 좋을 것 같아" 연결해 둔 서버의 몫이라고 합시다. 그 서버들이 없으면 기본 컨텍스트는 약 40K(4%)입니다. 이 두 구성으로 같은 작업을 할 때의 비용을 계산해 봅니다.

| 가정 | 값 |
| --- | --- |
| 구성 A (필수만) | 기본 컨텍스트 40K 토큰. 100만 토큰 윈도우의 4% |
| 구성 B (A + 선택 MCP) | 기본 컨텍스트 120K 토큰. 12% |
| 작업 한 건 | 모델 호출 40회, 작업 중 컨텍스트가 260K 늘어남, 출력 60K |
| 모델과 단가 | Claude Opus 5.5. 100만 토큰당 캐시 읽기 $0.20, 캐시 쓰기(5분) $5, 출력 $20 |
| 캐시 | 작업의 절반은 앞 작업에 바로 이어서 시작하고(캐시 유효), 절반은 5분 넘게 쉰 뒤 시작합니다(캐시 만료) |

아래 수치는 측정값이 아니라 **이 가정에 따른 계산값**입니다. 단가는 Anthropic 공식 가격표의 값이고 GitHub Copilot 가격표도 같습니다(출처: [Claude 가격 문서](https://platform.claude.com/docs/en/about-claude/pricing), [GitHub Docs, Models and pricing for GitHub Copilot](https://docs.github.com/en/copilot/reference/copilot-billing/models-and-pricing), 2026-10-12 확인). 계산 과정은 부록 C에 있습니다.

| 작업당 호출 수 | A (4%) | B (12%) | 차이 |
| --- | --- | --- | --- |
| 20회 | $3.25 | $3.76 | +$0.51 (+16%) |
| 40회 | $3.93 | $4.76 | +$0.83 (+21%) |
| 80회 | $5.29 | $6.76 | +$1.47 (+28%) |

이 표에서 읽을 것은 세 가지입니다.

- **쓰지도 않은 도구 정의 때문에 작업마다 약 20%를 더 냅니다.** 호출 40회 기준으로 작업당 $0.83이고, 크레딧으로는 약 393 대 476입니다. 사용자 한 명 몫인 월 1,900 크레딧으로 환산하면 이런 작업을 할 수 있는 횟수가 약 4.8건에서 4.0건으로 줍니다.
- **호출 수가 많을수록 벌어집니다.** 추가된 80K는 캐시에서 읽더라도 호출마다 약 $0.016이 듭니다(80K × $0.20 ÷ 100만). 에이전트가 도구를 많이 부르는 작업일수록 차이가 커집니다. 고정 영역 × 호출 수가 숫자로 나타난 것입니다.
- **기본 컨텍스트에 비례합니다.** 같은 가정에서 기본 컨텍스트가 윈도우의 1%(10K)만큼 늘 때마다 작업당 약 $0.10씩 늘어납니다.

이 계산은 캐시가 정상적으로 적중한다고 가정합니다. 캐시 읽기 단가($0.20)가 캐시 쓰기 단가($5)의 25분의 1이어서 고정 영역의 반복 비용이 이 정도로 눌려 있습니다. 이 "25배"는 Opus 5.5 같은 일부 모델에 한한 값입니다. 캐시 읽기가 기본 입력 단가의 0.05배인 Opus 5.5와 Sonnet 5.5에서 그렇고, 표준 배수인 0.1배를 쓰는 모델에서는 12.5배입니다. 캐시가 만료되거나 적중하지 않으면 차이는 더 벌어집니다(4.10절).

비용만 나빠지는 것이 아닙니다. **도구가 많으면 모델이 도구를 고르는 정확도도 떨어집니다.** Claude API 문서는 쓸 수 있는 도구가 30~50개를 넘으면 맞는 도구를 고르는 능력이 떨어진다고 적습니다(출처: [Claude API 문서, Tool search tool](https://platform.claude.com/docs/en/agents-and-tools/tool-use/tool-search-tool), 2026-10 확인). Anthropic의 내부 평가에서는 도구 정의를 필요할 때만 싣게 했을 때 MCP 평가의 정확도가 Opus 4에서 49%에서 74%로, Opus 4.5에서 79.5%에서 88.1%로 올랐습니다(출처: [Anthropic, Introducing advanced tool use on the Claude Developer Platform](https://www.anthropic.com/engineering/advanced-tool-use), 2025-11-24. Anthropic의 내부 평가이고 평가 세트는 공개되지 않았습니다. 지금보다 앞선 세대 모델의 수치입니다). 이름이 비슷한 도구가 늘수록 엉뚱한 도구를 고르거나 파라미터를 틀리기 쉽습니다. MCP를 많이 붙일수록 에이전트가 유능해질 것 같지만, 순진한 구현에서는 비용과 품질이 함께 나빠집니다.

### 4.6 해법 ①: 서버를 고친다

원인이 서버가 내놓는 도구 정의의 양이라면, 첫 번째 해법은 서버 쪽에서 양을 줄이는 것입니다. 방법은 둘입니다.

**도구를 워크플로 단위로 줄입니다.** 많은 MCP 서버가 기존 REST API를 그대로 감싸서 엔드포인트마다 도구를 하나씩 만듭니다. 그래서 도구가 수십 개가 됩니다. Anthropic은 이것을 흔한 실수로 꼽고 반대 방향을 권합니다.

> "We recommend building a few thoughtful tools targeting specific high-impact workflows, which match your evaluation tasks and scaling up from there."
> (효과가 큰 특정 워크플로를 겨냥해 잘 설계한 도구 몇 개부터 만들고, 거기서 늘려 가기를 권한다.)
> 출처: [Anthropic, Writing effective tools for agents — with agents](https://www.anthropic.com/engineering/writing-tools-for-agents), 2025-09-11

같은 글의 예시는 `list_users`, `list_events`, `create_event` 세 도구 대신, 빈 시간을 찾아 일정을 잡는 `schedule_event` 하나를 만드는 것입니다. 사내 서버에 옮기면 "이슈 조회", "담당자 조회", "상태 변경"을 따로 내놓는 대신 "이 커밋을 이슈에 연결하고 상태를 리뷰 대기로 바꾼다" 같은 작업 단위 도구 하나를 내놓는 식입니다. 도구 수가 줄면 정의 토큰도 줄고, 모델이 고를 후보도 줍니다.

**서버 쪽 재설계: 3계층으로 내놓습니다.** 워크플로 단위로 묶어도 도구가 수십 개 남는 서버가 있습니다. 그때는 실제 도구를 전부 내놓는 대신 메타 도구 세 개만 내놓고 나머지는 서버 안에 둡니다. 모델이 보는 인터페이스가 발견 → 조회 → 실행 세 층이 됩니다.

```text
1층  발견:   list_categories()                   → "jira", "confluence", "bitbucket" ...
2층  조회:   describe_tool("jira.search")        → 그 작업의 입력 스키마만 반환
3층  실행:   execute_tool("jira.search", {...})  → 서버가 검증하고 실제 도구를 부른다
```

1층은 이 서버로 어떤 종류의 일을 할 수 있는지 목록만 돌려줍니다. 모델이 그중 하나를 고르면 2층이 그 작업 **하나**의 입력 스키마와 사용 주의사항만 돌려줍니다. 3층은 이름과 인자를 받아 서버 안에서 실제 도구를 호출합니다. 결과적으로 대기 상태의 컨텍스트에 실리는 것은 도구 수십 개의 정의가 아니라 메타 도구 세 개의 정의뿐입니다. 수만 토큰이 수백 토큰이 됩니다. 이 "3계층"은 MCP 문서의 공식 용어가 아니라, 도구 수를 줄이고 응답을 토큰 효율적으로 만들라는 모범 사례를 도구 정의 자체에까지 밀어붙인 설계입니다.

대가도 분명합니다. 첫째, 발견과 조회에 왕복이 1~2회 늘어납니다. 둘째, 모델이 보는 것이 "무엇이든 실행하는 도구" 하나뿐이라 클라이언트는 어떤 작업이 불릴지 호출 전에 알 수 없습니다. 도구 단위로 승인 정책을 걸거나 인자 스키마를 검증하는 일이 클라이언트 쪽에서는 불가능해지므로, 검증 책임이 전부 서버로 넘어옵니다. 3층에서 인자를 반드시 서버가 검사해야 하는 이유입니다.

Anthropic도 같은 구조를 서버 쪽 대안으로 듭니다. 서버에 `search_tools` 도구를 두어 모델이 필요한 도구를 찾게 하고, 찾아낸 정의만 싣는 방식입니다(출처: [Anthropic, Code execution with MCP](https://www.anthropic.com/engineering/code-execution-with-mcp), 2025-11-04). 이름은 달라도 하는 일은 위 3계층과 같습니다. 비용을 만드는 것은 도구가 존재한다는 사실이 아니라 **정의가 컨텍스트에 상주한다**는 사실이고, 이 패턴은 상주를 없앨 뿐 기능을 없애지 않습니다. 그렇다면 이 일을 꼭 서버가 해야 할 이유도 없습니다. 같은 구조를 클라이언트가 대신 수행하는 것이 4.8절의 tool search입니다. 먼저 서버 쪽 해법만으로는 왜 부족한지를 봅니다.

### 4.7 왜 현실에서는 적용하기 어려운가

두 방법 모두 **서버를 고칠 수 있는 사람**만 쓸 수 있습니다. 그런데 우리가 쓰는 MCP 서버는 대부분 남이 만든 것을 받아 쓰는 것입니다. 코드 호스팅, 이슈 트래커, 메신저, 문서 검색 서버가 그렇습니다. 사용자는 그 서버의 도구 수도, 설명의 길이도, 스키마도 바꿀 수 없습니다. 서버를 만든 쪽은 대개 기능을 빠짐없이 내놓는 쪽을 택하고, 그 비용은 서버를 연결한 사용자가 매 호출마다 냅니다.

그래서 4.6절은 **직접 만드는 사내 서버에만 해당하는** 해법입니다. 사내 서버를 새로 만든다면 처음부터 워크플로 단위로 설계합니다. 그러나 받아 쓰는 서버의 고정 비용은 이것으로 줄지 않습니다. 남는 선택지는 둘입니다. 쓰지 않는 서버를 끊거나, 서버는 그대로 두고 에이전트 쪽에서 싣는 시점을 미루는 것입니다. 앞의 것은 서버를 쓸 일이 생길 때마다 다시 연결해야 해서 불편합니다. 뒤의 것이 다음 절입니다.

### 4.8 해법 ②: 클라이언트가 미룬다 (tool search)

4.4절의 구분을 다시 꺼냅니다. 정의를 전부 모델에 넣는 것은 스펙의 요구가 아니라 호스트의 선택이었습니다. 그렇다면 호스트가 다르게 선택하면 됩니다. MCP 공식 문서의 Client Best Practices가 이 방식을 **progressive discovery**라는 이름으로 설명합니다.

> "The host fetches tool definitions via `tools/list` as normal, but defers injecting them into the model's context."
> (호스트는 평소처럼 `tools/list`로 도구 정의를 받아 오되, 그것을 모델의 컨텍스트에 넣는 일은 미룬다.)
> 출처: [MCP 문서, Client Best Practices](https://modelcontextprotocol.io/docs/2026-07-28/develop/clients/client-best-practices), 2026-10 확인

문서는 흔한 구현으로 catalog → inspect → execute의 세 층을 듭니다. 4.6절에서 서버가 하던 발견 → 조회 → 실행과 같은 구조이고, 그 일을 호스트가 대신 한다는 점만 다릅니다.

| 층 | 하는 일 |
| --- | --- |
| Catalog | 호스트가 검색용 메타 도구를 모델에 줍니다. 모델이 자연어로 찾으면 맞는 도구의 이름과 짧은 설명이 돌아옵니다 |
| Inspect | 모델이 후보를 정하면 그 도구 하나의 전체 정의(입력 스키마 등)만 가져옵니다 |
| Execute | 모델이 인터페이스를 다 아는 상태에서 도구를 호출합니다. 컨텍스트에는 필요했던 정의만 실렸습니다 |

정보가 없어지는 것이 아니라 싣는 시점이 뒤로 갈 뿐입니다. 임베디드 개발자는 프로젝트의 헤더 파일을 전부 외우고 코딩하지 않습니다. 필요할 때 해당 헤더를 열어 시그니처를 확인하고 부릅니다. 같은 방식입니다. 문서의 그림은 전부 미리 싣는 경우를 약 150,000 토큰, 필요할 때만 싣는 경우를 약 2,000 토큰으로 비교합니다. 측정값이 아니라 그림에 붙은 설명용 예시입니다. 언제 이 방식으로 바꿀지는 도구 정의가 컨텍스트 윈도우에서 차지하는 비율로 정하라고 하고, 그 임계값의 예로 1~5%를 듭니다.

같은 문서는 모델 제공사가 tool search를 제공하면 직접 구현하는 대신 그것을 쓸 수 있다고 안내합니다. 원문은 "When available, you may prefer the platform's tool search over a custom implementation."(제공된다면 직접 구현하는 것보다 플랫폼의 tool search를 택할 수 있다.)입니다. **코딩 에이전트의 tool search가 이 progressive discovery의 구현입니다.** Claude Code에서는 다음과 같이 동작합니다(출처: [Claude Code 문서, Scale with MCP tool search](https://code.claude.com/docs/en/mcp#scale-with-mcp-tool-search), [Agent SDK 문서, Tool search](https://code.claude.com/docs/en/agent-sdk/tool-search), 2026-10 확인).

- 세션을 시작할 때는 **도구 이름과 서버 instructions(서버가 제공하는 사용 안내문)만** 싣습니다.
- 모델이 MCP 도구가 필요하다고 판단하면 `ToolSearch` 도구로 찾습니다. 기본으로 가장 관련 있는 도구가 최대 5개까지 실립니다.
- 한 번 실린 정의는 이후 턴에서도 남아 있습니다. 압축으로 그 메시지가 요약되면 빠지고, 다시 필요할 때 다시 찾습니다.
- 찾을 때마다 왕복이 한 번 늘어납니다. 도구가 많으면 매 턴의 컨텍스트가 줄어드는 효과가 이 비용보다 큽니다.

4.5절과 같은 가정으로 계산하면 효과는 다음과 같습니다. 선택 MCP 80K를 미뤄서 평소에는 이름 약 3K만 실리고, 필요한 작업에서는 중간에 도구 두 개(4K)를 불러온다고 놓았습니다. 이것도 계산값입니다.

| 구성 | 작업당 비용 |
| --- | --- |
| A: 필수만 (4%) | $3.93 |
| B: 필수 + 선택 MCP, tool search 없음 (12%) | $4.76 |
| B + tool search, 선택 MCP를 이번 작업에서 쓰지 않음 | $3.96 |
| B + tool search, 선택 MCP의 도구 두 개를 씀 | $4.00 |

**선택 MCP를 연결한 채로도 비용이 필수만 쓸 때 수준으로 내려갑니다.** 서버를 고치지 않았고, 서버를 끊지도 않았고, 작업마다 판단할 것도 없습니다. 4.3절의 세 기준을 모두 채웁니다.

#### 설정 주의: 사내 환경에서는 기본으로 꺼져 있다

**Claude Code의 tool search는 기본으로 켜져 있습니다. 그러나 `ANTHROPIC_BASE_URL`을 바꿔 다른 호스트에 연결한 환경에서는 기본으로 꺼집니다. 사내 환경이 여기에 해당합니다. `ENABLE_TOOL_SEARCH`를 직접 설정해야 하며, 사내 환경에서 정상 동작이 확인됐습니다.**

> "Tool search is enabled by default: MCP tools are deferred and discovered on demand. Claude Code disables it when `ANTHROPIC_BASE_URL` points to a non-first-party host, since most proxies don't forward `tool_reference` blocks. Set `ENABLE_TOOL_SEARCH` explicitly to override that fallback."
> (tool search는 기본으로 켜져 있다. MCP 도구를 미뤄 두고 필요할 때 찾는다. `ANTHROPIC_BASE_URL`이 자사 것이 아닌(non-first-party) 호스트를 가리키면 Claude Code가 이를 끈다. 대부분의 프록시가 `tool_reference` 블록을 전달하지 않기 때문이다. 이 동작을 덮어쓰려면 `ENABLE_TOOL_SEARCH`를 명시적으로 설정한다.)
> 출처: [Claude Code 문서, Configure tool search](https://code.claude.com/docs/en/mcp#configure-tool-search), 2026-10 확인

사내에서는 `ANTHROPIC_BASE_URL`을 `api.githubcopilot.com`으로 바꿔 Copilot API에 연결합니다. 이 주소는 문서에 나오는 예가 아니라 사내 사례입니다. 아무 설정도 하지 않으면 연결한 MCP 서버의 모든 도구 정의가 매 호출에 실립니다. 설정은 사용자 설정 파일(`~/.claude/settings.json`)의 `env`에 둡니다. 전체 연결 설정은 부록 A에 있습니다.

```json
{
  "env": {
    "ENABLE_TOOL_SEARCH": "true"
  }
}
```

| `ENABLE_TOOL_SEARCH` 값 | 동작 |
| --- | --- |
| (설정 안 함) | 모든 MCP 도구를 미룹니다. 단 `ANTHROPIC_BASE_URL`이 자사 것이 아닌 호스트이면 전부 미리 싣습니다 |
| `true` | 모든 MCP 도구를 미룹니다. 프록시가 `tool_reference` 블록을 지원하지 않으면 요청이 실패합니다 |
| `auto` | 미룰 수 있는 정의의 합이 컨텍스트 윈도우의 10% 미만이면 미리 싣고, 10%에 이르면 전부 미룹니다 |
| `auto:N` | 임계값을 N%로 정합니다. 예: `auto:5` |
| `false` | 전부 미리 싣습니다 |

함께 알아 둘 조건이 네 가지 있습니다. 표에서 뺀 일부 클라우드 제공자 구성의 예외는 같은 문서를 참조합니다.

1. `ENABLE_TOOL_SEARCH=true`는 연결한 프록시가 `tool_reference` 블록을 지원하지 않으면 **요청이 실패합니다.** 켠 뒤에 MCP 도구를 실제로 한 번 호출해 봅니다.
2. 모델 요건이 있습니다. Claude Sonnet 4.5, Haiku 4.5, Opus 4.5 이상이어야 합니다.
3. `CLAUDE_CODE_DISABLE_EXPERIMENTAL_BETAS`가 설정돼 있으면 tool search는 꺼진 채로 남고 `ENABLE_TOOL_SEARCH`로 덮어쓸 수 없습니다. 게이트웨이의 오류를 피하려고 이 변수를 켜 둔 환경인지 확인합니다.
4. 켜고 끄는 것 말고 `auto`, `auto:N`의 임계값 방식도 있습니다. MCP 공식 문서가 든 임계값의 예는 1~5%이고 Claude Code의 `auto`는 10%입니다.

매 턴 쓰는 서버가 있다면 그 서버만 미루기에서 뺄 수 있습니다. `.mcp.json`의 해당 서버 항목에 `"alwaysLoad": true`를 두면 `ENABLE_TOOL_SEARCH` 값과 상관없이 그 서버의 도구가 처음부터 실립니다(예시는 부록 A). 문서는 매 턴 필요한 소수의 도구에만 쓰라고 권합니다. 미리 실은 만큼 다시 고정 비용이 되기 때문입니다.

**시연 순서**

1. **준비물**: 1.5절 시연과 같은 환경입니다. MCP 서버 두세 개가 연결돼 있고 `ENABLE_TOOL_SEARCH`는 설정하지 않았습니다. 터미널 창을 두 개 띄웁니다.
2. **켜기 전.** 첫째 창에서 `claude`를 실행하고 아무 요청 없이 `/context`를 입력합니다. 1.5절에서 본 화면입니다. `MCP tools` 행의 숫자를 적어 둡니다.
3. **켭니다.** 둘째 창에서 `ENABLE_TOOL_SEARCH=true claude`로 새 세션을 시작하고 `/context`를 입력합니다.
4. **짚어 줄 것 ①**: 두 창을 나란히 놓습니다. 다른 행은 거의 같고 `MCP tools`만 줄었습니다. 서버는 하나도 끊지 않았습니다.
5. **MCP 도구가 필요한 요청을 합니다.** 입력 예: `이슈 트래커에서 CAN 수신 버퍼 오버플로 관련 이슈를 찾아 제목만 보여 줘`
6. **짚어 줄 것 ②**: 모델이 먼저 `ToolSearch`를 호출하고 그다음에 MCP 도구를 호출합니다. 요청이 오류 없이 끝나면 이 환경에서 tool search가 실제로 동작한다는 뜻입니다.
7. **다시 `/context`를 실행합니다.** 방금 불러온 도구만큼만 늘었습니다. `/mcp`로 서버의 연결 상태와 서버별 도구 수도 확인합니다.
8. **시연이 안 될 때**: 켠 창에서 요청이 실패하면 프록시가 `tool_reference`를 전달하지 않는 것일 수 있습니다. 변수를 빼고 다시 시작한 뒤, 미리 찍어 둔 전후 화면이나 아래 예시로 설명합니다.

아래는 전후 차이를 설명하려고 만든 **예시이며 값은 환경마다 다릅니다.** 켜기 전의 값은 1.5절의 예시와 같습니다.

```text
                      켜기 전                 켠 뒤
  Context Usage    118k / 1M (12%)        33k / 1M (3%)
  MCP tools         89.0k   8.9%           3.5k   0.4%
  (다른 행은 거의 그대로다)
```

예시에서 켠 뒤가 4.5절의 구성 A(4%)보다도 낮은 것은 필수 서버의 정의까지 모두 미뤘기 때문입니다. 필수 서버를 `alwaysLoad`로 두면 그만큼 다시 올라가 A와 비슷해집니다.

> **발표 전 확인**: 위 예시는 실측이 아닙니다. tool search를 켠 뒤의 `/context` 화면이 어떻게 보이는지는 문서에 직접 서술이 없습니다. 문서로 확인되는 것은 미뤄 둔 도구 정의가 사용량 계산에서 빠진다는 것까지입니다. 발표 환경에서 전후를 실제로 찍어 이 예시를 바꿉니다. 게이트웨이가 토큰 수를 세는 `count_tokens` 엔드포인트를 제공하지 않으면 `/context`의 수치는 문자 수로 어림한 근사치라는 점도 함께 말합니다.

### 4.9 다른 코딩 에이전트의 유사 옵션

4.8절은 Claude Code를 기준으로 설명했습니다. 같은 기능이 다른 도구에도 있지만 이름과 기본값, 끄는 방법이 다릅니다. 3.4절의 관점에서, 도구를 옮기면 이 항목부터 다시 확인합니다.

#### GitHub Copilot CLI

**tool search가 기본으로 켜져 있습니다.** 따로 켤 것이 없는 대신 CLI가 자동으로 판단합니다. 프롬프트를 넣을 때마다 그 시점의 도구 수를 세고, 대략 30개 미만이면 전부 싣습니다. 그 이상이면 built-in 도구(`grep`, `glob`, `bash`, `edit` 등)만 미리 싣고 MCP를 비롯한 외부 도구는 보류합니다. 문서의 표현은 "Below roughly 30 tools, the savings you get from tool search aren't worth it."(도구가 대략 30개 미만이면 tool search로 얻는 절감이 그만한 값을 하지 못한다.)입니다.

**한 번 불러온 도구는 대화가 끝날 때까지 남습니다.** 원문은 "Those tools then stick around for the rest of the conversation."입니다. 압축되면 빠졌다가 다시 찾는 Claude Code와 다른 점입니다.

끄고 켜는 설정은 세 층입니다.

| 범위 | 파일 | 값 |
| --- | --- | --- |
| 전체 끄기 | 개인 설정 `~/.copilot/settings.json` | `"toolSearch": false` |
| 서버별 예외 | `~/.copilot/mcp-config.json`의 `deferTools` | `"auto"`(기본) · `"never"`(항상 미리 싣습니다) |
| 커스텀 에이전트 | `.github/agents/*.md`의 frontmatter | `deferred-tool-loading: true` |

`deferTools`는 `/mcp edit`의 **Defer Tools** 항목에서도 바꿀 수 있습니다. Claude Code의 `alwaysLoad`(4.8절)에 해당하는 설정입니다.

```json
{
  "mcpServers": {
    "my-server": {
      "type": "stdio",
      "command": "npx",
      "args": ["-y", "@example/mcp-server"],
      "deferTools": "never",
      "tools": ["*"]
    }
  }
}
```

커스텀 에이전트는 쓸 도구를 이름으로 나열하는데, 그렇게 나열한 목록은 기본적으로 미루기 대상이 아닙니다. frontmatter에 `deferred-tool-loading: true`를 넣어야 그 목록도 검색 대상으로 돌아갑니다.

모델 요건도 있습니다. Claude는 Mythos Preview, Fable, Haiku 4.5 이상, Sonnet 4.0 이상, Opus 4.0 이상이고 GPT는 5.4 이후입니다. 그 밖의 모델을 고르면 tool search가 동작하지 않고 모든 도구가 처음부터 실립니다. 사내는 Copilot Business 환경이므로, 하네스를 Copilot CLI로 두는 경우 이 절이 먼저 확인할 항목입니다(출처: [GitHub Docs, Loading tools on demand with tool search](https://docs.github.com/en/copilot/concepts/agents/copilot-cli/tool-search), 2026-10 확인).

#### OpenAI Codex CLI

Codex에도 BM25 기반 `tool_search`가 들어 있어, MCP 도구를 바로 노출할지(direct) 검색 뒤로 미룰지(deferred) 나누어 다룹니다. 다만 **이 동작을 정리한 공식 문서가 없습니다.** 아래는 설정 레퍼런스와 공개 저장소에서 확인되는 범위입니다.

- defer된 MCP 도구가 검색될 때 서버 instructions가 그 서버의 설명으로 쓰입니다. Codex 문서도 instructions를 "server-wide guidance alongside the server's tools"(서버의 도구들과 함께 쓰이는 서버 전체 안내)로 설명하고 앞 512자를 자체 완결적으로 쓰라고 권합니다. Claude Code와 마찬가지로 **서버 instructions의 품질이 검색 성공률을 좌우합니다**(4.8절).
- compaction이 일어나면 검색 결과가 버려지고 이후에는 다시 검색합니다. 이 점은 Claude Code와 같고 Copilot CLI와 다릅니다.
- MCP 서버 설정은 `~/.codex/config.toml`의 `[mcp_servers.<이름>]` 섹션에서 합니다. 프로젝트 단위로 두려면 `.codex/config.toml`을 씁니다.
- **defer 동작 관련 세부 옵션 키는 버전에 따라 바뀌고 있습니다.** 설정 참조에는 `tool_search`, `tool_search_always_defer_mcp_tools`가 특정 모드에서 거부되는 "retired switches"로 올라 있습니다. 쓰고 있는 버전의 Codex 설정 참조에서 확인합니다.

출처: [Codex 설정 참조](https://learn.chatgpt.com/docs/config-file/config-reference), [Codex 문서, Model Context Protocol](https://learn.chatgpt.com/docs/extend/mcp), `openai/codex` 저장소 소스와 공개 이슈, 2026-10 확인

#### opencode

opencode V1에는 이 기능이 없습니다. 연결한 서버의 도구 정의는 모두 처음부터 실립니다(출처: [opencode 문서, MCP servers](https://opencode.ai/docs/mcp-servers/), 2026-10 확인).

### 4.10 그 밖의 확실한 절감

tool search 다음으로 손댈 것은 세 가지입니다. 캐시가 깨지지 않게 쓰는 것, 지침 파일을 줄이는 것, 세션을 목적 단위로 끊는 것입니다.

#### Prompt caching: 만료되면 비싼 단가로 다시 쓴다

매 호출이 앞부분을 똑같이 다시 보내므로, API는 같은 앞부분(prefix)을 캐시해 두고 할인 단가로 계산합니다. Claude Code가 알아서 하는 일이라 사용자가 켤 것은 없습니다. 알아야 할 것은 **캐시가 언제 깨지는가**입니다.

| 구분 (Claude Opus 5.5, 100만 토큰당) | 단가 | 언제 적용되나 |
| --- | --- | --- |
| 기본 입력 | $4 | 캐시를 쓰지 않을 때 |
| 캐시 쓰기 (5분) | $5 | 처음 보내는 부분, 캐시가 만료되거나 무효화된 뒤 다시 보내는 부분 |
| 캐시 쓰기 (1시간) | $8 | 1시간짜리 캐시를 골랐을 때 |
| 캐시 읽기 | $0.20 | 캐시가 살아 있는 동안 같은 앞부분을 다시 보낼 때 |
| 출력 | $20 | 모델이 생성한 토큰 |

단가는 Anthropic 공식 가격표의 값입니다(출처: [Claude 가격 문서](https://platform.claude.com/docs/en/about-claude/pricing), 2026-10-12 확인). GitHub Copilot 가격표의 Opus 5.5 단가도 입력 $4, Cached input $0.20, Cache write $5, 출력 $20으로 같고, 1시간 쓰기 단가는 Copilot 표에 없습니다.

캐시가 살아 있으면 30만 토큰짜리 컨텍스트를 다시 보내는 데 $0.06이 듭니다. 캐시가 만료된 뒤라면 같은 내용을 캐시 쓰기 단가로 다시 써야 해서 $1.50이 듭니다(단가를 곱한 단순 계산입니다). 고정 영역이 클수록 만료 한 번의 값이 커집니다.

캐시의 수명에 대해 알아 둘 것은 세 가지입니다.

- **기본 수명은 5분입니다.** API 키 방식에서 Claude Code가 요청하는 기본값이 5분입니다. Claude 구독 요금제는 플랜에 포함된 사용량 안에서 메인 대화에 1시간이 적용되지만, 사내 환경에는 해당하지 않습니다(출처: [Claude Code 문서, Prompt caching](https://code.claude.com/docs/en/prompt-caching#cache-lifetime), 2026-10 확인).
- **수명은 요청이 시작된 시점부터 잽니다.** Claude API 문서의 표현은 "The lifetime is measured from the start of the request that writes or reads the cache entry, not from the end of its response."(수명은 캐시 항목을 쓰거나 읽는 요청이 시작된 시점부터 잰다. 응답이 끝난 시점부터가 아니다.)입니다. 응답을 만드는 데 4분이 걸렸다면 다음 요청은 그 뒤 1분 안에 시작해야 캐시에 닿습니다. 캐시를 읽을 때마다 수명은 다시 시작됩니다(출처: [Claude API 문서, Prompt caching](https://platform.claude.com/docs/en/build-with-claude/prompt-caching), 2026-10 확인).
- **게이트웨이를 거치면 캐시 동작 자체가 게이트웨이에 달려 있습니다.** Claude Code 문서는 `ANTHROPIC_BASE_URL`을 바꾼 구성에 대해 "whether caching works depends on the gateway"(캐싱이 동작하는지는 게이트웨이에 달려 있다)라고 적습니다. 게이트웨이가 Claude Code가 보내는 캐시 표식(`cache_control`)을 지우면서 성공을 돌려주면, 대화 전체가 매 턴 캐시 없는 입력으로 과금됩니다.

사내 경로에 대해서는 확인된 것과 확인되지 않은 것을 구분합니다. GitHub Copilot의 모델 단가표에는 Anthropic 모델의 캐시 요금(Cached input, Cache write)이 따로 명시돼 있습니다. 여기까지는 사실입니다. Copilot API가 Claude Code의 캐시 표식을 그대로 전달해 캐시가 실제로 적중하는지는 확인되지 않았습니다.

> **발표 전 확인**: 사내 경로(Claude Code에서 Copilot API로)에서 캐시가 실제로 적중하는지 실측합니다. 방법은 둘입니다. `claude -p "hello" --output-format json`을 두 번 이어서 실행해 두 번째 결과의 `usage`에서 `cache_read_input_tokens`가 0이 아닌지 봅니다. 또는 세션에서 `/usage`를 실행해 `Prompt cache (main)` 줄의 적중 비율을 봅니다(v2.1.251 이상). 적중하지 않는다면 4.5절과 4.8절의 계산값은 이 환경에 맞지 않고, 고정 영역을 줄이는 효과는 계산보다 훨씬 커집니다.

캐시가 깨지는 상황은 사용 습관과 설정에서 나옵니다(출처: [Claude Code 문서, Prompt caching](https://code.claude.com/docs/en/prompt-caching#actions-that-invalidate-the-cache), 2026-10 확인).

| 상황 | 무슨 일이 일어나나 | 대응 |
| --- | --- | --- |
| 다음 요청까지 5분 넘게 쉽니다 | 고정 영역과 그때까지의 대화를 캐시 쓰기 단가로 다시 씁니다 | 같은 맥락의 후속 요청은 이어서 보냅니다. 오래 쉬고 다른 주제를 시작할 때는 새 세션으로 시작합니다 |
| 작업 중 도구 실행이 5분을 넘습니다 (느린 타깃 빌드, 긴 테스트) | 실행이 끝난 뒤의 호출이 그때까지의 전부를 다시 씁니다 | 피하기 어렵습니다. 다시 쓰이는 양을 줄이려면 고정 영역이 작아야 합니다 |
| tool search가 꺼진 상태에서 세션 중에 MCP 서버를 연결하거나 끕니다 | 도구 정의가 바뀌어 캐시가 무효화됩니다 | 서버를 켜고 끄는 일은 세션을 시작하기 전에 합니다. tool search를 켜면 영향이 없습니다 |
| 세션 중에 모델을 바꿉니다 | 모델마다 캐시가 따로여서 대화 전체를 캐시 없이 다시 읽습니다 | 모델은 세션을 시작할 때 정합니다 |

4.5절의 가정으로 계산하면, 선택 MCP 80K를 더 실은 구성 B는 캐시가 한 번 만료될 때마다 구성 A보다 $0.40을 더 냅니다(80K × $5 ÷ 100만). 5분 넘는 빌드가 작업 중에 한 번 끼면 두 구성의 차이는 작업당 $0.83에서 $1.22로 벌어집니다(계산값). 느린 타깃 빌드가 일상인 임베디드 환경에서 캐시 만료는 드문 일이 아닙니다. 그래서 순서가 중요합니다. **만료를 피하려 애쓰기 전에, 만료될 때 다시 쓰이는 고정 영역부터 줄입니다.**

#### 지침 다이어트

지침 파일은 고정 영역입니다. 세션을 시작할 때 전체가 실리고 그 세션의 모든 호출에 따라갑니다. 지침에 넣은 한 문단은 호출 수만큼 곱해집니다. Claude Code 문서는 `CLAUDE.md`를 200줄 아래로 유지하고, PR 리뷰나 마이그레이션처럼 특정 작업에만 쓰는 절차는 스킬로 옮기라고 권합니다. 스킬의 본문은 호출될 때만 실리기 때문입니다(출처: [Claude Code 문서, Manage costs effectively](https://code.claude.com/docs/en/costs#move-instructions-from-claude-md-to-skills), 2026-10 확인). 줄이는 것은 비용만을 위한 일이 아닙니다. 2.5절에서 본 대로 겹치고 부딪치는 지시는 모델이 정리하느라 사고 토큰을 더 쓰게 만듭니다. 무엇을 남기고 무엇을 뺄지는 5.2절에서, 필요할 때만 읽히게 하는 방법은 5.3~5.4절에서 다룹니다.

#### 세션을 목적 단위로 끊기

고정 영역을 줄였으면 남는 것은 누적 영역입니다. 대화와 도구 결과는 스스로 줄지 않습니다. 40번째 호출은 앞의 39번이 쌓은 것을 전부 싣고 갑니다. 버그 수정을 끝낸 세션에서 그대로 다른 기능을 시작하면, 새 작업의 모든 호출이 앞 작업의 기록을 끌고 갑니다.

대응은 단순합니다. **한 세션은 한 목적에 쓰고, 목적이 바뀌면 새 세션으로 시작합니다.** Claude Code에서는 `/clear`가 그 일을 합니다. 같은 비용 문서는 관련 없는 작업으로 넘어갈 때 낡은 컨텍스트가 이후의 모든 메시지에서 토큰을 낭비한다고 적습니다. 이것은 설정이 아니라 습관이어서 4.3절의 둘째 기준에는 못 미칩니다. 대신 비용과 품질 저하를 함께 줄입니다. 긴 세션에서 품질이 떨어지는 문제(1.4절)가 같은 뿌리에서 나오기 때문입니다. 세션 관리의 요령은 7.5절에서 다룹니다.

### 4.11 관측과 체크리스트

줄였는지는 재 봐야 압니다. 관측과 통제는 세션과 조직, 두 층에서 합니다.

| 층 | 수단 | 무엇을 보나 |
| --- | --- | --- |
| 세션 | `/context` (항목별로 보려면 `/context all`) | 지금 컨텍스트를 무엇이 얼마나 차지하나요? 고정 영역의 크기 |
| 세션 | `/usage` (별칭 `/cost`, `/stats`) | 이 세션이 쓴 토큰과 비용 추정, 캐시 적중 비율 |
| 조직 | 크레딧 대시보드 (GitHub의 청구·사용량 화면) | 실제로 차감된 크레딧 |
| 조직 | 예산 한도와 추가 사용 정책 | 한도를 넘었을 때 차단할지 과금할지 |

세션 층에서 주의할 점이 있습니다. Claude Code의 `/usage`가 보여 주는 금액은 Claude Code가 토큰 수에 정가를 곱해 **로컬에서 계산한 추정치**입니다. 사내처럼 Copilot을 거치는 환경에서는 실제 차감액이 아닙니다. 차감액은 GitHub 쪽 화면에서 봅니다. 같은 화면의 `Prompt cache (main)` 줄은 API 응답의 캐시 토큰 값으로 계산하므로 게이트웨이를 거쳐도 쓸 수 있습니다(출처: [Claude Code 문서, Manage costs effectively](https://code.claude.com/docs/en/costs), 2026-10 확인). Copilot CLI에도 `/usage`와 `/context`가 있고, `/usage`는 모델별 토큰 합계와 크레딧 소비를 보여 줍니다.

조직 층에서는 예산을 겁니다. GitHub은 사용자 단위, 코스트 센터 단위, 조직 단위, 엔터프라이즈 단위의 예산과 한도를 제공합니다. 사용자 단위 예산을 다 쓰면 조직의 크레딧에 여유가 있어도 그 사용자의 Copilot 사용이 멈춥니다. 4.1절에서 본 대로 조직은 추가 사용이 기본으로 켜져 있으므로, 포함량 안에서만 쓰게 하려면 관리자가 정책을 꺼야 합니다(출처: [GitHub Docs, Usage-based billing for organizations and enterprises](https://docs.github.com/en/copilot/concepts/billing-and-usage/organizations-and-enterprises/billing), 2026-10 확인).

> **발표 전 확인**: 우리 조직의 추가 사용 정책(켜짐 또는 꺼짐)과 사용자별 예산 설정을 관리자에게 확인해 발표에서 알려 줍니다. 각자 크레딧 사용량을 어느 화면에서 보는지도 미리 찍어 둡니다.

체크리스트는 **확실한 것 먼저** 순서입니다. 위에서부터 적용하고, 아래로 갈수록 습관과 판단이 필요합니다.

| 순서 | 할 일 | 성격 | 관련 절 |
| --- | --- | --- | --- |
| 1 | `/context`로 고정 영역을 잽니다. 가장 큰 행을 확인합니다 | 측정 | 1.5절 |
| 2 | tool search가 실제로 동작하는지 확인합니다. 사내 환경이면 `ENABLE_TOOL_SEARCH`를 설정합니다 | 한 번 설정 | 4.8절 |
| 3 | 매 턴 쓰는 서버만 `alwaysLoad`로 두고, 쓰지 않는 MCP 서버는 세션을 시작하기 전에 끊습니다. CLI로 되는 일에는 MCP를 붙이지 않습니다 | 한 번 설정 | 4.8절, 6.1절 |
| 4 | 지침 파일을 줄입니다. 특정 작업용 절차는 스킬로 옮깁니다 | 한 번 정리 | 5.2~5.4절 |
| 5 | 캐시가 실제로 적중하는지 `/usage`로 확인합니다 | 측정 | 4.10절 |
| 6 | 조직의 예산 한도와 추가 사용 정책을 확인합니다 | 한 번 설정 (관리자) | 4.11절 |
| 7 | 세션을 목적 단위로 끊습니다. 모델과 MCP 연결은 세션을 시작할 때 정합니다 | 습관 | 7.5절 |
| 8 | 출력이 많은 조사성 작업은 서브에이전트로 격리합니다 | 판단 | 6.3절 |
| 9 | 첫 요청에 요구 사항과 완료 기준을 충분히 적습니다 | 습관 | 12.5절 |
| 10 | 모델과 effort를 골라 씁니다 | 매번 판단 | 4.2절 |

10번을 마지막에 둔 것은 중요하지 않아서가 아닙니다. 1~6번은 한 번 해 두면 모든 작업에서 효과가 나고 틀릴 일이 없습니다. 10번은 작업마다 판단해야 하고 틀리면 비용이 늡니다. 확실한 것을 다 적용한 뒤에, 각자 익숙한 작업에서부터 조심스럽게 조정합니다.

### 핵심 정리

- 토큰 과금에서는 고정 영역 × 호출 수가 그대로 청구되므로, 판단이 필요 없고 한 번 설정하면 계속 적용되며 품질을 깎지 않는 절감부터 적용합니다.
- 고정 영역에서 가장 큰 것은 MCP 도구 정의이고, 받아 쓰는 서버는 고칠 수 없으므로 클라이언트의 tool search로 줄이며, 사내 환경에서는 `ENABLE_TOOL_SEARCH`를 직접 설정해야 합니다.
