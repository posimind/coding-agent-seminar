# Part 2. HITL이 필요한 이유 ② 설계와 개발자 (13\~15장)

---

## 13장. 한계에서 개입 지점으로

- **핵심 질문**: 사람을 어디에 두고, 어디에서는 빼도 되나요
- **도달 목표**: 자기 팀의 자동/승인 경계선을 그리고, 반복되는 판단을 자동 검증으로 내립니다

9\~12장에서 네 가지 한계를 하나씩 봤습니다. 장마다 "사람이 개입할 지점"이 따로 나왔으므로, 그대로 두면 "결국 전부 사람이 봐야 한다"는 말처럼 들립니다. 이 장은 네 결론을 8.1절의 개입 지점 4단계(요청 → 계획 → 실행 → 검증) 위에 한 장으로 겹쳐 놓습니다. 겹쳐 보면 사람이 꼭 있어야 하는 자리와 비워도 되는 자리가 갈립니다. HITL(Human in the Loop)을 설계한다는 것은 이 두 자리를 구분하는 일입니다.

순서는 이렇습니다. 먼저 한계가 요구하는 자리를 표로 모읍니다(13.1). 다음으로 실행 단계의 승인을 어디에 둘지 기준을 정합니다(13.2). 한계와 무관하게 사람이 남아야 하는 두 이유를 더합니다(13.3). 마지막으로, 사람이 같은 판단을 되풀이하지 않도록 한 번 내린 결정을 기계가 확인하는 규칙으로 내립니다(13.4).

### 13.1 한계 × 개입 지점

아래 표는 네 한계가 개입 지점 4단계 중 어디에 사람을 요구하는지 모은 것입니다. ◎는 주된 개입 지점, ○는 보조 지점입니다. 빈칸은 그 한계 때문에 사람이 서야 할 이유가 뚜렷하지 않은 자리입니다. 연구 결과가 아니라 9.6, 10.4, 11.6, 12.4절의 결론을 이 세미나가 종합한 정리입니다.


| 한계                    | 요청 (의도·제약)                          | 계획 (접근 승인)                     | 실행 (위험 행동 허가)                | 검증 (품질 판정)                              |
| --------------------- | ----------------------------------- | ------------------------------ | ---------------------------- | --------------------------------------- |
| ① 전부 볼 수 없다 (9장)      | ◎ 검색에 걸리지 않는 연결과 암묵지를 미리 알려 줍니다     | ◎ 영향 범위와 조사 수준을 정합니다           |                              | ○ 전체 빌드·링크·정적 분석으로 읽지 않은 범위를 확인합니다      |
| ② 모르면 지어낸다 (10장)      | ◎ 사내 API·내부 규정처럼 공개 데이터에 없는 자료를 줍니다 | ○ 계획이 근거 없는 전제 위에 서 있지 않은지 봅니다 | ○ 틀린 첫 답 위에 설명이 쌓이면 세션을 끊습니다 | ◎ 확신에 찬 어조와 "완료" 보고를 컴파일과 실존 확인으로 검증합니다 |
| ③ 채점되는 것만 잘한다 (11장)   | ◎ 무엇을 만들지, 완료 기준, 팀의 선호를 정합니다       | ◎ 설계안을 고릅니다                    | ○ 테스트 코드가 수정되는지 감시합니다        | ◎ 테스트만 통과하는 답인지, 흔한 답일 뿐인지 판정합니다        |
| ④ 묻지 않고 빈칸을 채운다 (12장) | ◎ 빠진 의도와 제약을 구현 전에 드러냅니다 (가장 쌉니다)   | ◎ 계획에 담긴 가정을 확인합니다             |                              | ○ 여기서 발견하면 가장 비쌉니다                      |


표를 세로로 읽으면 개입 지점마다 무게가 다릅니다.


| 개입 지점 | ◎   | ○   | 읽는 법                                                   |
| ----- | --- | --- | ------------------------------------------------------ |
| 요청    | 4   | 0   | 네 한계가 모두 여기서 시작합니다. 사람만 가진 정보를 넣는 자리이고 가장 쌉니다          |
| 계획    | 3   | 1   | 코드가 쓰이기 전에 방향을 고치는 마지막 자리입니다. Plan mode(7.5절)가 그 구현입니다 |
| 실행    | 0   | 2   | ◎가 없습니다. ○ 두 개도 허가가 아니라 진행 중 감시입니다                     |
| 검증    | 2   | 2   | ②·③에서는 주된 자리입니다. ①은 기계가 많은 부분을 대신하고, ④는 여기서 잡으면 늦습니다   |


**요청**은 네 줄이 모두 ◎입니다. 공통점은 사람이 주지 않으면 에이전트가 어디에서도 얻을 수 없는 정보라는 것입니다. "이 핸들러는 ISR(인터럽트 서비스 루틴)에서 호출된다"는 연결(①), 사내 진단 API의 헤더(②), "동적 할당 금지" 같은 팀의 규칙과 완료 기준(③), 요청문에서 빠진 제약(④)이 그렇습니다. 기준이 사람 머릿속에만 있으면 어떤 자동 검증도 그것을 찾지 못합니다(12.4절).

**계획**은 ①·③·④가 ◎입니다. 영향 범위와 조사 수준을 정하고, 설계안을 고르고, 계획에 묻힌 가정을 확인합니다. 코드가 한 줄도 쓰이지 않은 시점이라 고치는 비용이 계획 문서 수정에 그칩니다.

**검증**은 한계마다 성격이 다릅니다. ②와 ③에서는 주된 자리입니다. 확신에 찬 어조와 "완료" 보고는 근거가 아니고, 테스트 통과는 정답의 증명이 아니기 때문입니다. ①에서는 ○입니다. 전체 빌드, 링크, 정적 분석이 에이전트가 읽지 않은 범위를 기계적으로 드러내 주므로 사람은 그 결과를 읽으면 됩니다. ④에서도 ○인데 이유가 다릅니다. 검증 단계에서 오해를 발견하면 코드를 다시 써야 하므로, 이 자리를 주된 방어선으로 삼으면 가장 비싸게 배웁니다.

**실행**에는 ◎가 하나도 없습니다. ○ 두 개는 틀린 첫 답 위에 설명이 쌓일 때 세션을 끊는 일(10.4절)과 테스트 코드 수정을 감시하는 일(11.6절)입니다. 둘 다 "이 명령을 실행해도 되는가"를 허가하는 일이 아니라 진행 중에 이상 신호를 보는 일입니다.

가로로 읽으면 ①과 ④는 앞쪽(요청·계획)에 몰려 있고, ②와 ③은 앞뒤 양쪽에 걸칩니다. 이 표에서 가져갈 것은 두 가지입니다. 첫째, 네 한계는 주로 **요청·계획·검증**에 사람을 요구합니다. 사람의 시간은 실행 중간의 승인 버튼보다 앞과 뒤에 쓰는 편이 효과가 큽니다. 둘째, 그런데도 도구는 실행 중에 승인을 묻습니다(7.5절의 권한 모드). 이 승인은 네 한계에서 나온 것이 아닙니다. 되돌릴 수 없는 행동, 책임, 보안이라는 다른 이유에서 나옵니다. 13.2절과 13.3절이 그 이유를 다룹니다.

### 13.2 경계선 긋기

실행 단계의 승인을 어디에 둘지 정하는 기준은 한 문장입니다.

> **되돌릴 수 있으면 자동, 되돌릴 수 없으면 승인.**

이 기준을 **양방향 문**과 **일방통행 문**이라는 말로도 부릅니다. 아마존의 2015년 주주 서한에 나오는 구분입니다. 들어갔다가 마음에 들지 않으면 다시 나올 수 있는 결정이 양방향 문(two-way door)이고, 지나가면 돌아올 수 없는 결정이 일방통행 문(one-way door)입니다. 서한은 양방향 문은 빠르게, 일방통행 문은 신중하게 결정하라고 권합니다(출처: [Amazon, 2015 Letter to Shareholders](https://www.sec.gov/Archives/edgar/data/1018724/000119312516530910/d168744dex991.htm), 2016-04).

에이전트의 도구 호출에 이 기준을 대면 다음과 같습니다. 1장에서 본 대로 에이전트가 하는 일은 모두 도구 호출이고, 목적에 따라 되돌릴 수 있는 정도가 다릅니다.


| 도구 호출의 목적 | 도구 예      | 되돌릴 수 있는가        | 기본값             |
| --------- | --------- | ---------------- | --------------- |
| 탐색        | 파일 읽기, 검색 | 부작용이 없습니다        | 자동              |
| 편집        | 파일 수정, 생성 | git으로 복구할 수 있습니다 | 작업 브랜치 안에서는 자동  |
| 실행        | 셸 명령      | 명령에 따라 다릅니다      | 명령별로 나눕니다       |
| 위임        | 서브에이전트    | 하위 호출에 따라 다릅니다   | 하위 호출의 기준을 따릅니다 |


탐색까지 매번 승인받게 하면 에이전트는 아무 일도 못 합니다. 사람 쪽에도 문제가 생깁니다. 승인 요청이 너무 잦으면 내용을 읽지 않고 누르게 됩니다. Claude Code 문서도 이를 prompt fatigue라고 부르고, 자주 쓰는 안전한 명령을 허용 목록에 올리는 기능을 완화 수단으로 듭니다(출처: [Claude Code 문서, Security](https://code.claude.com/docs/en/security), 2026-10 확인). 승인은 아껴야 무게가 실립니다.

판단이 필요한 곳은 "명령에 따라 다르다"고 적힌 실행입니다. 차량·임베디드 팀이라면 경계선은 대략 다음과 같이 그어집니다.


| 자동 (양방향 문)               | 승인 필요 (일방통행 문)                                    |
| ------------------------ | ------------------------------------------------- |
| 파일 읽기, 검색, 심볼 조회         | 사외 전송: 메일, 메신저, 외부 API 호출, 사외 저장소로 push           |
| 작업 브랜치 안의 로컬 편집          | force push, 브랜치 삭제, 공유 브랜치에 직접 push               |
| 호스트 빌드, 단위 테스트, 정적 분석 실행 | 타깃 보드 플래싱, 시험 장비나 실차를 움직이는 명령                     |
| 브랜치 생성, 로컬 커밋            | 릴리스 태그, 배포 패키지 생성과 서명, OTA(무선 업데이트) 배포            |
| 이슈·로그·문서 조회              | 캘리브레이션 값이나 비휘발성 메모리 쓰기, 진단 명령으로 ECU(전자제어장치) 상태 변경 |
|                          | 서명 키·자격증명·툴체인 설정 변경, 대량 파일 삭제                     |


표를 자기 팀에 맞게 고칠 때 볼 것이 두 가지 있습니다.

- **되돌릴 수 있는지는 비용으로 판단합니다.** 커밋은 `git revert`로 되돌릴 수 있지만, 이미 차량에 내려간 업데이트와 이미 보낸 메일은 되돌릴 수 없습니다. 기술적으로 되돌릴 수 있어도 비용이 큰 행동은 승인 쪽에 둡니다. 수십 분이 걸리는 타깃 크로스 빌드를 "사람이 요청할 때만"으로 두는 것이 그 예입니다(14.3절).
- **경계선은 설정으로 구현합니다.** 왼쪽 열은 권한 설정의 허용 목록에, 오른쪽 열은 승인 또는 차단 규칙에 넣습니다(7.5절). 반드시 지켜져야 하는 줄은 훅으로 강제합니다(5.5절).

> **질문**: 우리 팀 저장소에서 에이전트가 묻지 않고 해도 되는 일과 반드시 물어야 하는 일을 세 개씩 적는다면 무엇인가요?

같은 기준이 14.5절에서 PR(Pull Request) 단위로 다시 나옵니다. 도구 호출 하나가 아니라 변경 묶음 전체에 문 유형을 붙여 리뷰의 깊이를 정하는 데 씁니다.

### 13.3 한계 밖의 두 이유

13.1절의 표가 설명하지 못한 것이 있습니다. 모델이 네 한계를 모두 넘어선다고 가정해도 사람이 남아야 하는 이유가 둘 있습니다. 책임과 보안입니다.

**책임.** 코드를 생성한 쪽이 아니라 **머지한 사람**이 책임을 집니다. 차량 소프트웨어에서는 여기에 기능안전과 법규 책임이 따라붙습니다. "AI가 짰다"는 어떤 감사에서도 답이 되지 않습니다. 책임은 모델의 성능과 무관하게 사람에게 남으므로, 책임질 사람이 내용을 알고 승인하는 지점은 없앨 수 없습니다. 그 지점이 검증 단계의 PR 리뷰이고, 14장이 다루는 병목이 바로 여기서 생깁니다.

**보안.** 에이전트는 사용자의 지시만 읽지 않습니다. 이슈 코멘트, README, 웹페이지, 로그, 외부에서 들여온 소스처럼 도구로 읽어 온 글도 같은 컨텍스트에 들어갑니다. 그 글에 지시가 심겨 있으면 에이전트가 따를 수 있습니다. 이것이 간접 프롬프트 인젝션입니다(6.2절). 원칙은 6.2절에서 본 한 문장입니다. 도구가 읽어 온 것은 데이터이지 명령이 아닙니다.

```text
사용자가 채팅으로 준 지시           →  명령
파일·웹페이지·이슈에서 읽어 온 것   →  데이터
```

"이슈 목록을 처리해 줘"는 목록을 읽을 권한을 준 것이지, 목록에 적힌 문장을 실행할 권한을 준 것이 아닙니다. 그러나 모델이 이 구분을 항상 지킨다고 보장할 수는 없습니다. 그래서 속았을 때 피해가 큰 행동, 곧 사외 전송과 자격증명 접근과 파괴적 명령을 실행 단계의 승인으로 묶어 둡니다. 13.2절 표의 오른쪽 열 첫 줄이 사외 전송인 이유입니다. Claude Code도 웹에서 내용을 가져오는 `curl`, `wget` 같은 명령은 기본으로 자동 승인하지 않습니다(출처: [Claude Code 문서, Security](https://code.claude.com/docs/en/security), 2026-10 확인).


| 이유  | 무엇을 지키는가                 | 모델이 좋아지면 사라지는가                               | 사람이 서는 자리                |
| --- | ------------------------ | -------------------------------------------- | ------------------------ |
| 책임  | 결과에 답할 사람이 내용을 알고 승인합니다  | 사라지지 않습니다. 책임은 성능과 무관하게 사람에게 있습니다            | 검증(머지 승인), 일방통행 문의 실행 승인 |
| 보안  | 남이 쓴 글이 명령으로 실행되지 않게 합니다 | 줄 수는 있어도 없어진다고 볼 근거가 없습니다. 입력을 만드는 쪽이 공격자입니다 | 실행(사외 전송, 자격증명, 파괴적 명령)  |


이제 13.1절 표의 실행 열이 비어 있던 까닭이 채워집니다. 실행 단계의 승인은 에이전트의 실력이 모자라서 두는 것이 아닙니다. 되돌릴 수 없는 행동(13.2), 책임, 보안 때문에 둡니다. 그래서 모델이 좋아져도 이 승인은 없어지지 않고, 반대로 되돌릴 수 있는 행동에는 처음부터 둘 필요가 없습니다.

### 13.4 판단을 검증 가능한 제약으로

여기까지 모으면 사람의 자리가 꽤 많습니다. 그러나 HITL은 사람이 매번 모든 코드를 보라는 뜻이 아닙니다. 사람이 한 번 내린 결정을 기계가 확인하는 규칙으로 만들어 두면, 다음부터는 그 규칙이 사람 대신 판정합니다. 11.2절에서 본 대로 자동으로 채점되는 일은 에이전트가 잘 지킵니다. 사람은 채점 기준을 만들고, 에이전트는 그 안에서 일합니다.

2.4절의 제1원칙과 같은 이야기입니다. 에이전트가 실수하면 그 실수를 다시 할 수 없게 만드는 장치를 만듭니다. 같은 지적을 두 번 하고 있다면 채팅창에 다시 설명할 것이 아니라 아래 표의 어느 한 줄로 내려야 합니다.


| 결정의 성격             | 내릴 곳           | 2.3절의 분류 | 예                                           |
| ------------------ | -------------- | -------- | ------------------------------------------- |
| 기계가 판정할 수 있는 규칙    | 테스트, 린터, CI 체크 | 계산적 센서   | `app/` 코드는 `drivers/` 헤더를 직접 include하지 않습니다 |
| 일어나기 전에 멈춰야 하는 행동  | Hook (5.5절)    | 계산적 센서   | 테스트 파일 수정, 공개 헤더 변경, force push             |
| 판단이 필요한 원칙과 도메인 제약 | 지침, Skill      | 추론적 가이드  | "이벤트 핸들러는 ISR에서 호출된다. 블로킹 호출을 넣지 않는다"       |
| 그렇게 정한 이유          | 설계 결정 기록(ADR)  | 가이드의 근거  | 왜 계층을 나눴고 무엇을 포기했는가                         |


고르는 순서는 위에서 아래입니다. 기계가 강제할 수 있으면 강제하고, 강제할 수 없는 판단만 글로 남깁니다. 지침은 요청이고 훅과 테스트는 강제이기 때문입니다(5.5절). "조심해서 확인한다"는 사람의 기억에 기대는 방식이라 바쁜 날 무너집니다. 훅과 테스트는 매번 같은 방식으로 실행됩니다. HITL은 다짐이 아니라 코드로 구현합니다.

설계 규칙 테스트의 예를 하나 봅니다. 팀이 "app 계층은 드라이버를 직접 부르지 않고 HAL(하드웨어 추상화 계층) 인터페이스만 쓴다"고 정했다고 합시다. 리뷰 때마다 지적하는 대신 아래 스크립트를 pre-commit과 CI에 넣습니다.

```bash
#!/usr/bin/env bash
# tools/check_layering.sh
# 팀 결정: app/ 계층은 drivers/ 헤더를 직접 include하지 않는다. hal/ 인터페이스만 쓴다.
hits=$(grep -rnE '^[[:space:]]*#[[:space:]]*include[[:space:]]*[<"]drivers/' \
        src/app --include='*.c' --include='*.h')
if [ -n "$hits" ]; then
    echo "계층 규칙 위반: app/ 은 drivers/ 헤더를 직접 include할 수 없다." >&2
    echo "고치는 법: hal/ 의 인터페이스 헤더를 include한다. 필요한 기능이 hal/ 에 없으면 멈추고 사람에게 묻는다." >&2
    echo "$hits" >&2
    exit 1
fi
```

이 스크립트에서 볼 것은 세 가지입니다.

- **판단이 채점 기준으로 바뀌었습니다.** "계층을 지켜라"는 사람의 판단이 컴파일 오류처럼 자동으로 판정되는 규칙이 됐습니다. 리뷰어는 이 지적을 다시 하지 않아도 됩니다.
- **실패 메시지에 고치는 법을 적었습니다.** 센서는 에이전트가 읽고 스스로 고칠 수 있는 신호를 낼 때 효과가 큽니다(2.3절). 위반 위치만 알려 주는 메시지보다 다음 행동을 알려 주는 메시지가 낫습니다.
- **예시는 단순한 문자열 검사입니다.** 실무에서는 빌드 시스템에서 계층별 include 경로를 제한하거나 의존성 분석 도구를 쓰는 편이 정확합니다.

한 가지를 더 챙깁니다. 에이전트가 검사 스크립트나 테스트를 고쳐서 통과시키는 길이 남아 있으면 규칙은 보상 해킹(11.2절)의 대상이 됩니다. 검사 스크립트와 테스트 파일의 수정은 훅으로 멈춰 사람의 확인을 받게 합니다. 훅을 쓰는 법과 예시 코드는 5.5절에서 다뤘습니다.

모든 판단이 규칙으로 내려가지는 않습니다. "앞으로 기능을 추가하기 쉬운 구조인가"는 여전히 사람이 봅니다. 무엇을 규칙으로 만들지 고르는 일도 사람의 몫입니다. 그래도 방향은 분명합니다. 사람의 자리는 매번 판정하는 곳에서 **판정 기준을 만드는 곳**으로 옮겨 갑니다.

### 핵심 정리

- 네 가지 한계는 주로 요청·계획·검증에 사람을 요구하고, 그중 요청 단계의 개입이 가장 쌉니다.
- 실행 단계의 승인은 되돌릴 수 없는 행동, 책임, 보안 때문에 두며, 되돌릴 수 있는 행동은 자동으로 둡니다.
- 사람이 한 번 내린 결정은 테스트·훅·지침으로 내려 같은 판단을 두 번 하지 않습니다.

## 14장. 사례: PR 리뷰 병목과 이를 줄이려는 시도

- **핵심 질문**: AI 도입 후 가장 먼저 막히는 곳은 어디이고, 업계는 그것을 어떻게 풀어 보고 있나요
- **도달 목표**: PR 리뷰가 왜 대표적인 HITL 병목인지 설명하고, 한 가지 해결 시도를 참고해 자기 팀에 맞는 부분을 가려냅니다

13장의 끝에서 물은 것은 개입 지점 중 어디가 가장 먼저 막히는가였습니다. 답은 검증 단계의 PR 리뷰입니다. 에이전트를 도입한 팀에서 가장 자주 거론되는 병목은 쏟아지는 코드와 PR입니다. PR 리뷰는 HITL의 대표 지점이고, 코드에 대한 책임을 사람이 지므로 뺄 수 없습니다(13.3절). 그런데 사람이 리뷰에 쓸 수 있는 시간에는 물리적 한계가 있습니다. 뺄 수도 없고 늘릴 수도 없는 자리이므로 이곳이 전체 흐름의 주 병목이 됩니다.

이 장은 **정답을 제시하는 장이 아니라 사례를 공유하는 장**입니다. 병목을 풀려는 여러 노력 가운데 하나로 맷 포콕(Matt Pocock)의 3겹 리뷰를 소개합니다. 한 실무자의 방법론이고 통제된 실험으로 검증된 것이 아니므로 14.8절에서 한계를 함께 놓습니다. 듣는 동안 "우리 팀에 맞는 부분은 어디인가"를 가려내면 됩니다.

### 14.1 병목: 쏟아지는 코드와 PR

에이전트가 들어오면 코드를 쓰는 시간은 분 단위로 줄고, 한 사람이 여러 세션을 동시에 돌릴 수도 있습니다. 반면 사람이 코드를 읽고 이해하는 속도는 그대로입니다. 내가 쓰지 않은 코드는 읽는 데 더 오래 걸립니다. 그래서 **만들어지는 속도가 검토되는 속도를 넘습니다.**

측정 사례가 둘 있습니다. 같은 업체가 1년 간격으로 낸 것입니다.

**2025년.** 엔지니어링 지표 분석 업체 Faros AI는 1,255개 팀, 개발자 1만 명 이상의 텔레메트리를 분석해, AI 도입률이 높은 팀의 개발자가 PR을 98% 더 병합했지만 PR 리뷰 시간도 91% 늘었다고 보고했습니다. 보고서는 이를 "a critical bottleneck: human approval"(핵심 병목은 사람의 승인)이라고 적었습니다(출처: [Faros AI, The AI Productivity Paradox Report 2025](https://www.faros.ai/blog/ai-software-engineering), 2025-07-23).

**2026년.** 같은 업체의 후속 보고서는 표본을 개발자 약 2만 2천 명, 4,000개 팀으로 넓히고, 2년치 텔레메트리를 같은 조직 안에서 AI 저채택 집단과 고채택 집단으로 나눠 비교했습니다. 1년 전보다 숫자가 커졌습니다.


| 지표 (고채택 팀)    | 변화     |
| ------------- | ------ |
| 작업 처리량        | +33.7% |
| 완료한 에픽        | +66.2% |
| PR 병합률        | +16.2% |
| PR 크기         | +51%   |
| 중간 PR 리뷰 시간   | **5배** |
| PR당 버그        | +28%   |
| PR당 장애        | 3배     |
| 코드 재작업(churn) | 10배    |
| 주당 배포         | −11.7% |


(출처: [Faros AI, The AI Engineering Report 2026: The Acceleration Whiplash](https://www.faros.ai/research/ai-acceleration-whiplash), 2026년 2분기)

읽을 때 세 가지를 감안합니다. 첫째, 인과가 아니라 상관관계입니다. 둘째, 지표 분석 도구를 파는 업체의 보고서이고 두 보고서 모두 방법의 한계가 공개돼 있지 않습니다. 셋째, 2026년 보고서는 "핵심 병목은 사람의 승인"이라고 명시하지 않습니다. 그 표현은 2025년 보고서의 것입니다.

그래도 두 해가 가리키는 방향은 같습니다. **앞쪽의 생성은 빨라지고 뒤쪽의 검토와 품질 지표는 나빠집니다.** 리뷰 시간이 91% 증가에서 5배로 벌어졌다는 것은 이 병목이 1년 사이에 완화되지 않았다는 뜻입니다. 주당 배포가 오히려 줄었다는 수치도 같은 이야기입니다. 앞을 빠르게 만들어도 뒤가 막히면 전체 흐름은 빨라지지 않습니다.

속도 차이가 쌓이면 둘 중 하나가 일어납니다.


| 결과            | 겉으로 보이는 모습                         | 실제로 일어나는 일                                |
| ------------- | ---------------------------------- | ----------------------------------------- |
| 대기열이 쌓입니다     | 리뷰를 기다리는 PR이 늘고 병합까지 걸리는 시간이 길어집니다 | 기다리는 동안 다른 변경과 충돌하고, 작성자와 리뷰어 모두 맥락을 잃습니다 |
| 형식적 승인으로 변합니다 | 대기열이 줄고 지표가 좋아 보입니다                | 읽지 않은 코드가 승인됩니다. 리뷰를 했다는 기록만 남습니다         |


둘째가 더 위험합니다. 병목이 풀린 것처럼 보이기 때문입니다. 승인한 사람은 읽지 않은 코드의 책임을 집니다(13.3절). 게다가 병합된 코드는 다음 작업에서 에이전트가 읽고 따라 하는 컨텍스트가 됩니다. 질이 낮은 코드가 한 번 들어가면 그것을 본뜬 코드가 이어서 들어옵니다.

정리하면 이 자리의 조건은 두 문장입니다. **책임 때문에 사람을 뺄 수 없고, 시간 때문에 다 볼 수 없습니다.** 여기에 한 가지가 더 얹힙니다. 리뷰 시간이 같은 지적의 반복에 쓰입니다. "이 프로젝트는 이 패턴을 쓰지 않는다"는 말을 PR마다 다시 합니다.

이 조건에서 팀이 고를 수 있는 길은 둘이고, 결과가 정반대입니다.


|             | 승인 지점을 줄인다                      | 검증을 자동화한다                           |
| ----------- | ------------------------------- | ----------------------------------- |
| 하는 일        | 리뷰 없이 병합되는 범위를 넓히거나 승인 요건을 낮춥니다 | 사람 앞에 기계 검증을 세워 사람에게 오는 양과 종류를 줄입니다 |
| 검증의 총량      | 줄어듭니다                           | 늘어납니다. 기계가 전부 보고 사람은 걸러진 것을 봅니다     |
| 사람이 덜 보는 이유 | 보지 않기로 했기 때문입니다                 | 기계가 먼저 걸렀기 때문입니다                    |
| 결함이 발견되는 곳  | 통합 시험, 현장                       | 커밋 전, PR 전                          |
| 책임          | 본 적 없는 코드의 책임이 남습니다             | 본 것에 대해 책임집니다                       |


사람이 보는 양이 줄어든다는 점은 같습니다. 다른 것은 줄어든 만큼의 검증이 사라졌는가, 기계로 옮겨 갔는가입니다. 흔한 실수가 앞쪽입니다. 방향은 뒤쪽이어야 하고, 13.4절의 "판단을 검증 가능한 제약으로"가 그 원리입니다. 14.2절부터 볼 사례는 뒤쪽 길을 구체적인 구조로 만든 것입니다.

### 14.2 해결 시도의 하나: 3겹 구조

맷 포콕은 발표 "Fixing the PR Bottleneck"에서 사람 앞에 두 겹의 제동 장치를 세우는 구조를 제시했습니다. 자동 체크, 자동 리뷰, 사람 리뷰로 이어지는 **3겹 구조**입니다.

먼저 이 사례의 위상을 분명히 합니다. 3겹 구조는 한 실무자의 방법론이고 통제된 실험으로 검증된 것이 아닙니다. 또 이 장의 설명은 영상 원본을 직접 대조한 것이 아니라 **영상 요약본과 2차 정리 글**에 근거합니다. 스킬의 세부 동작만 공개 저장소의 `SKILL.md` 원문으로 확인했습니다(출처: [발표 영상](https://www.youtube.com/watch?v=LlgiOCmFG_w), [mattpocock/skills](https://github.com/mattpocock/skills), 2026-10-12 확인).

> **발표자 노트**: 맷 포콕은 TypeScript 강의(Total TypeScript)로 알려진 영국의 개발자 교육자이고, 지금은 AI Hero에서 코딩 에이전트 실무를 가르칩니다. 12.5절의 grill-me 스킬을 만든 사람입니다. 요약본에 섞여 있던 부정확한 내용 세 가지는 본문에 옮기지 않았습니다. ① 표준 파일명은 `coding-standards.mmd`가 아니라 `CODING_STANDARDS.md`입니다. ② `show-me` 스킬은 포콕이 아니라 HumanLayer의 Dex Horthy가 만들었습니다. ③ "깊이 = 구현 줄 수 ÷ 인터페이스 줄 수"는 저장소 원문이 채택하지 않는다고 밝힌 정의입니다. "리뷰 에이전트가 댓글 대신 커밋한다"는 발표의 주장이며, 공개된 `code-review` 스킬 본문은 보고 절차까지만 기술합니다.

> **발표 전 확인**: 영상 원본(22분 34초)을 직접 보고 이 장의 서술과 대조합니다. 대조하기 전에는 "요약본 기준"이라고 밝히고 말합니다.

발표의 출발점은 이렇습니다. 포콕은 에이전트와 결정론적 코드가 일을 시작시키는 시스템을 "소프트웨어 공장"이라 부릅니다. 공장의 속도만 올리고 제동 장치를 달지 않으면 저품질 코드를 쏟아내는 슬롭 캐논(Slop Cannon)이 됩니다. 그래서 목표를 "사람 리뷰를 없앤다"로 잡지 않습니다. 사람에게 도달하는 PR은 이미 기계가 걸러 낸 것이어야 하고, 사람이 한 번 한 지적은 다시 사람에게 돌아오지 않아야 합니다.

```text
 구현 에이전트 ──▶ [1겹 자동 체크] ──▶ [2겹 자동 리뷰] ──▶ [3겹 사람 리뷰] ──▶ 병합
   (동작하게)      린트·타입·테스트    리뷰 에이전트가     위험도에 따라
                   실패하면 되돌림     표준 검사 후 고침   깊이를 조절
                          ▲                   ▲                   │
                          │                   │                   │
                          └───────────────────┴─── 회고 ◀─────────┘
                          기계적 위반 → 자동 체크 추가
                          판단 문제   → CODING_STANDARDS.md 갱신
```


| 겹        | 누가               | 비용     | 잡는 것                          | 못 잡는 것                 |
| -------- | ---------------- | ------ | ----------------------------- | ---------------------- |
| 1. 자동 체크 | 린터, 컴파일러, 테스트 러너 | CPU    | 문법, 타입, 금지 패턴, 회귀             | 테스트 자체의 거짓말, 설계 품질     |
| 2. 자동 리뷰 | 별도 컨텍스트의 리뷰 에이전트 | 토큰     | 코딩 표준 위반, 코드 스멜, 스펙 누락과 범위 초과 | 표준에 적히지 않은 암묵지, 사업상 판단 |
| 3. 사람 리뷰 | 엔지니어             | 사람의 시간 | 되돌릴 수 없는 결정, 요구사항과의 정합        | (마지막 방어선)              |


설계 원칙은 하나입니다. 아래 겹일수록 쌉니다. 그러므로 **위 겹에서 발견한 문제를 가능한 한 아래 겹으로 내려보냅니다.** 사람이 리뷰에서 한 지적이 기계적인 것이면 1겹의 체크가 되고, 판단이 필요한 것이면 2겹의 표준 문서에 들어갑니다. 2.3절의 말로 옮기면 1겹은 계산적 센서, 2겹은 추론적 센서입니다. 사람을 없애는 구조가 아니라 사람 앞에 두 겹을 세우는 구조이고, 13.4절의 원리를 PR 흐름에 적용한 것입니다.

### 14.3 1겹: 자동 체크

1겹은 린트, 타입 검사, 테스트입니다. CPU만 쓰므로 가장 쌉니다. 다만 CI(지속적 통합)가 초록색이라는 것이 병합해도 된다는 뜻은 아닙니다. 에이전트는 구현과 테스트를 함께 쓰고, 그러면 통과해도 아무것도 증명하지 못하는 테스트가 생깁니다. 발표는 이를 세 유형으로 나눕니다.


| 유형          | 무엇인가                            | 왜 문제인가                             |
| ----------- | ------------------------------- | ---------------------------------- |
| 동어반복 테스트    | 구현에 적은 값을 테스트가 그대로 다시 단언합니다     | 요구사항이 아니라 구현을 검증합니다. 구현이 틀려도 통과합니다 |
| 구조 민감성 테스트  | 동작이 아니라 소스 파일의 내부 구조나 순서를 확인합니다 | 리팩터링만 해도 깨지고, 동작이 망가져도 통과할 수 있습니다  |
| 실패하지 않는 테스트 | 의존성을 가짜로 지나치게 대체합니다             | 실제 환경의 오류 경로를 한 번도 타지 않습니다         |


```c
/* 동어반복: 구현의 상수를 테스트가 그대로 되읽는다 */
#define CAN_RETRY_LIMIT 3
TEST(can, retry_limit) { ASSERT_EQ(CAN_RETRY_LIMIT, 3); }

/* 바람직한 형태: 인터페이스를 통해 관찰할 수 있는 동작을 검증한다 */
TEST(can, gives_up_after_three_failed_sends) {
    fake_bus_fail_always();
    ASSERT_EQ(can_send(&msg), CAN_ERR_TIMEOUT);
    ASSERT_EQ(fake_bus_send_count(), 3);
}
```

포콕은 이를 에이전트의 부정행위가 아니라 **구현에 지나치게 결합된 테스트**로 봅니다. 원인이 결합이므로 해법도 프롬프트가 아니라 설계에 있다는 것입니다. 여기서 드는 개념이 깊은 모듈(deep module)입니다. John Ousterhout의 『A Philosophy of Software Design』에서 온 말로, 작은 인터페이스 뒤에 많은 동작을 숨긴 모듈을 가리킵니다. 모듈이 깊으면 호출자와 테스트가 같은 인터페이스를 지나가므로, 내부 구조에 손을 대는 테스트를 쓸 여지가 줄어듭니다. 위 예시의 둘째 테스트가 `can_send()` 하나로 재시도 동작을 확인하는 것이 그 모습입니다. 설계론 자체는 이 세미나의 범위를 넘으므로 개념만 짚습니다.

1겹에 무엇을 올릴지는 13.4절의 기준 그대로입니다. 위반이 기계적이면(금지 API, include 방향, 파일 위치 규칙) 문서에 쓰지 않고 체크로 만듭니다. 린트·타입·테스트를 돌리는 pre-commit 훅이나 CI 잡이 아예 없는 저장소라면 그것을 만드는 일이 첫 작업입니다.

차량·임베디드 환경에는 조건이 하나 더 있습니다. 타깃 빌드가 느립니다. 1겹이 한 번에 수십 분씩 걸리면 에이전트가 고치고 확인하는 반복이 성립하지 않습니다. 그래서 검증을 층으로 나누고 **빠른 층부터 만듭니다.**

```text
[빠른 층]  구문·타입 검사, 린트       수 초      에이전트가 편집할 때마다
[중간 층]  호스트 빌드 + 단위 테스트  분 단위    에이전트가 작업 단위마다
[느린 층]  타깃 크로스 빌드           수십 분    사람이 요청할 때만
[최상위]   HIL 검증                   시간 단위  사람만
```

시간은 예시이며 프로젝트마다 다릅니다. HIL(Hardware-in-the-Loop)은 실제 하드웨어를 연결해서 하는 검증입니다. 볼 것은 세 가지입니다. 호스트에서 빌드하고 테스트할 수 있는 중간 층을 만드는 일 자체가 하네스 투자입니다. `compile_commands.json`을 만들어 두면 에이전트가 심볼을 더 정확히 찾습니다. 지침에는 "타깃 빌드는 사람이 요청할 때만"이라고 적어 둡니다(13.2절의 "되돌릴 수 있어도 비용이 큰 행동").

### 14.4 2겹: 자동 리뷰

2겹은 구현 에이전트와 분리된 리뷰 에이전트입니다. 나누는 이유는 두 가지입니다. 첫째, 모델은 자기 결과물을 신뢰성 있게 평가하지 못합니다. 그래서 생성자와 검증자를 나누고 검증자에게는 생성 과정을 보여 주지 않습니다(6.3절). 둘째, 구현 에이전트는 이미 과부하입니다. 탐색, 코드 작성, 디버깅을 한 컨텍스트에서 합니다. 여기에 코딩 표준까지 얹으면 컨텍스트 압박이 가장 큰 곳에 짐을 더 싣는 셈입니다. 리뷰 에이전트는 diff를 받으므로 탐색이 필요 없고 디버깅도 거의 하지 않습니다.

포콕은 일을 둘로 나눕니다. 구현 에이전트는 스펙과 티켓, 최소한의 `AGENTS.md`만 읽고 **동작하게** 만드는 데 집중합니다. 리뷰 에이전트는 별도 컨텍스트에서 `CODING_STANDARDS.md`를 읽고 **좋게** 만드는 일을 맡습니다. TDD(테스트 주도 개발)의 Red-Green-Refactor에서 앞의 두 단계와 마지막 단계를 서로 다른 에이전트에게 준 셈입니다.

역할이 나뉘면 코딩 표준을 두는 자리도 달라집니다. 항상 로드되는 지침을 줄이고 필요한 시점에 필요한 에이전트만 읽게 한다는 점에서 2.5절과 5.2절의 과잉 제약 논의와 같은 방향입니다.


| 두는 곳                      | 언제 읽히는가           | 무엇을 두는가                               |
| ------------------------- | ----------------- | ------------------------------------- |
| `AGENTS.md` / `CLAUDE.md` | 모든 에이전트의 컨텍스트에 항상 | 극히 아껴 씁니다. 주로 다른 파일을 가리키는 포인터         |
| `CODING_STANDARDS.md`     | 구현 때가 아니라 리뷰 때    | 판단이 필요한 규칙만. 예: 파일 간 일관성, 주변 코드와의 어울림 |
| 린터 규칙, pre-commit, CI     | 커밋할 때마다           | 기계가 강제할 수 있는 규칙 전부 (1겹)               |


리뷰 에이전트는 diff를 두 축으로 봅니다.


| 축              | 질문                      | 보고 내용                                           |
| -------------- | ----------------------- | ----------------------------------------------- |
| 표준 (Standards) | 저장소에 문서화된 코딩 표준을 따르나요   | 위반 위치와 근거 규칙, 코드 스멜(판단 사항으로 표기)                 |
| 스펙 (Spec)      | 원래 이슈와 스펙이 요구한 것을 구현했나요 | 누락과 부분 구현, 요청하지 않은 동작(범위 초과), 구현은 됐으나 틀려 보이는 부분 |


저장소의 `code-review` 스킬은 두 축을 병렬 서브에이전트로 돌려 서로의 컨텍스트를 오염시키지 않게 하고, 결과를 합치지 않고 나란히 보고합니다. 표준은 다 지켰지만 엉뚱한 것을 구현한 코드와, 요구대로 구현했지만 팀 규약을 어긴 코드가 서로를 가리지 않게 하려는 것입니다. 저장소가 아무것도 문서화하지 않았을 때 쓰는 기본 목록도 있습니다. Martin Fowler의 『Refactoring』 3장에서 고른 코드 스멜 12종입니다. 저장소의 표준이 이 목록보다 우선하고, 도구가 이미 강제하는 것은 건너뜁니다.

운영 원칙으로 발표가 드는 것은 두 가지입니다.

- **직접 만듭니다.** 범용 리뷰 서비스는 팀 맥락을 몰라 오탐이 많다는 이유로, 팀의 표준을 담은 리뷰를 직접 구성하라고 권합니다.
- **댓글이 아니라 커밋.** 리뷰 에이전트가 댓글을 달면 사람이 읽고 판단하고 다시 지시해야 하므로 사람의 일이 늘어납니다. 그래서 기본 출력은 수정 커밋이고, 댓글은 사람의 결정이 필요한 열린 질문에만 씁니다. 다만 이것은 발표의 주장입니다. 공개된 `code-review` 스킬 본문은 두 축의 결과를 보고하는 절차까지만 기술하므로, 커밋 권한과 범위는 팀이 직접 정해야 합니다.

### 14.5 3겹: 사람 리뷰

두 겹을 지나온 PR만 사람에게 옵니다. 3겹의 목표는 사람 리뷰를 좁고 빠르게 만드는 것이고, 수단은 세 가지입니다.

#### Merge Danger로 리뷰 깊이를 정한다

13.2절의 양방향 문과 일방통행 문을 PR 단위에 적용합니다. PR 본문 끝에 문 유형과 영향 범위를 적어, 리뷰어가 얼마나 깊이 읽어야 하는지 먼저 알게 합니다.


| 문 유형   | 뜻                | 예                                                   | 리뷰 방식  |
| ------ | ---------------- | --------------------------------------------------- | ------ |
| 양방향 문  | 싸게 되돌릴 수 있습니다    | 대부분의 기능 변경, 리팩터링, 테스트 추가                            | 신속 리뷰  |
| 일방통행 문 | 되돌리기 어렵거나 파괴적입니다 | 저장 데이터 포맷 변경, 외부에 공개된 인터페이스 변경, 현장에 나가면 회수할 수 없는 변경 | 엄격한 리뷰 |


저장소의 `pr` 스킬이 쓰는 PR 본문 틀은 세 부분입니다. 아래는 원문에서 선택 항목을 뺀 것입니다.

```markdown
## Summary

<diagram, diff-sketch, or tree>

## Evidence

- **Before:** <screenshot/output/failing test run>
  **After:** <screenshot/output/passing test run>

## Merge Danger

**Door:** <one-way or two-way>

**Blast Radius:** <one-word description>
```

Summary에는 그림이나 diff 스케치나 트리를, Evidence에는 변경 전후의 화면·출력·테스트 실행을, Merge Danger에는 문 유형을 적고 영향 범위(Blast Radius)를 한 단어로 적습니다.

#### 그림과 의사코드로 된 PR

`pr` 스킬의 Summary 지침은 HumanLayer의 Dex Horthy가 만든 `show-me` 스킬에서 가져온 것입니다. 원칙은 한 문장입니다. "Pick the smallest view that makes the key point clear."(요점이 분명해지는 가장 작은 뷰를 고른다.) 로직은 의사코드로, 런타임 제어 흐름은 호출 트리로, 파일의 책임이나 넓은 리팩터링은 얕은 파일 트리로, 컴포넌트 사이의 상호작용과 데이터 흐름은 Mermaid 다이어그램으로 보여 줍니다. 기존 구조 위의 변경이라면 그 트리나 의사코드에 `diff`를 입힙니다.

증거에도 등급이 있습니다. 화면이 바뀌는 변경은 스크린샷이 가장 좋고, 그다음이 테스트 결과나 콘솔 출력 같은 실행 기반 증거입니다. 이전에는 실패하고 지금은 통과하는 바로 그 테스트를 보여 줍니다. 화면이 없는 임베디드 코드라면 호스트 테스트의 실행 결과, 타깃 로그, 정적 분석 결과가 이 자리를 채웁니다. 긴 설명문 대신 구조가 한눈에 보이는 표현을 고르면 리뷰어가 읽을 양이 줄고, 15.3절에서 볼 "이해가 썩는" 문제에도 도움이 됩니다.

#### 회고로 지적을 아래 겹에 되먹인다

포콕의 표현으로, 사람 리뷰는 코드만 검토하는 일이 아니라 **그 코드를 만든 시스템을 검토하는 일**입니다. 저장소의 `retro` 스킬은 지정한 세션의 기록을 읽고 에이전트 환경의 개선 후보를 심각도순으로 제안합니다. 살피는 범주는 네비게이션, 자동 체크, 코딩 표준, 전역 지침, 도구 경제성, 무효 지침, 정보 접근의 일곱 가지입니다.

리뷰 병목과 직접 닿는 범주는 둘입니다. 자동 체크는 "이 실수를 잡을 체크가 가능했는가, 이미 있는데 연결이 안 됐는가"를 묻습니다. 코딩 표준은 "리뷰 에이전트의 규칙을 더하거나, 지우거나, 명확하게 고칠 것인가"를 묻습니다. 나머지 범주는 에이전트가 필요한 파일과 정보를 쉽게 찾았는지, 지침 파일에서 옮기거나 지울 것이 있는지, 비싼 도구 호출을 줄일 수 있는지를 봅니다.

판단 순서는 13.4절과 같습니다. 기계적 위반이면 체크를 만들고, 판단 문제일 때만 표준 문서에 씁니다. 규칙을 쓰는 것보다 체크를 만드는 것이 기본값입니다. 이 되먹임이 돌아야 "사람이 한 번 한 지적은 다시 사람에게 돌아오지 않는다"가 성립합니다. 2.4절의 제1원칙을 팀 단위로 구현한 것입니다.

### 14.6 전체 흐름으로 보기

세 겹을 작업 흐름 전체에 펴면 여덟 단계가 됩니다. 7.5절에서 익힌 순서(계획을 승인하고, 구현을 맡기고, 검증을 거쳐 리뷰한다)에 앞쪽의 정렬과 뒤쪽의 회고가 붙고, 자동 검증이 두 겹으로 나뉜 모습입니다.


| 단계       | 하는 일                                   | 개입 지점 (8.1절) | 사람 개입                        |
| -------- | -------------------------------------- | ------------ | ---------------------------- |
| 0. 정렬    | 요구를 인터뷰로 구체화하고 스펙으로 만듭니다 (12.5절)       | 요청           | **필수.** 과소명세는 여기서만 싸게 잡힙니다   |
| 1. 분해    | 스펙을 작은 티켓으로 나눕니다                       | 계획           | 검토                           |
| 2. 구현    | 합의된 인터페이스에서 테스트를 먼저 쓰고 구현합니다           | 실행           | 없음                           |
| 3. 체크    | 타입 검사와 단일 테스트를 자주, 전체 테스트를 끝에 한 번 돌립니다 | 검증 (1겹)      | 없음                           |
| 4. 리뷰    | 표준과 스펙 두 축을 검사하고 고칩니다                  | 검증 (2겹)      | 열린 질문에만                      |
| 5. PR    | 요약, 증거, Merge Danger를 붙입니다             | 검증           | 없음                           |
| 6. 사람 리뷰 | 문 유형에 따라 깊이를 조절합니다                     | 검증 (3겹)      | 양방향 문은 신속, 일방통행 문은 **필수·엄격** |
| 7. 회고    | 지적을 체크와 표준으로 내려보냅니다                    | 흐름 밖         | 제안 승인                        |


이 구조에서도 사람이 남는 자리는 셋입니다.

1. **앞쪽의 정렬.** 스펙이 틀리면 세 겹을 모두 통과한 틀린 결과물이 나옵니다. 어떤 자동 검증도 사람 머릿속에만 있는 기준을 찾지 못합니다(12.4절).
2. **뒤쪽의 일방통행 문.** 되돌릴 수 없는 변경은 책임질 사람이 내용을 알고 승인합니다(13.3절).
3. **흐름 밖의 회고.** 무엇을 체크로 내리고 무엇을 표준에 적을지 정하는 일은 사람이 합니다.

13.1절의 표와 겹쳐 보면 같은 그림입니다. 사람은 앞(요청·계획)과 뒤(검증)에 남고 가운데(구현)에서 빠집니다.

이 흐름을 2.2절에서 지평선으로 소개한 루프의 눈으로 볼 수도 있습니다. 루프를 조립할 때 판단이 가장 어려운 것은 "무엇으로 통과를 판정하는가"와 "언제 사람에게 넘기는가"이고, 3겹 구조는 이 둘에 대한 한 가지 답입니다. 통과는 1겹 자동 체크와 2겹 리뷰 에이전트가 판정합니다. 사람에게 넘기는 조건은 일방통행 문, 리뷰 에이전트의 열린 질문, 반복 횟수나 예산의 상한 도달입니다. 세션이 끊겨도 남아야 하는 상태는 스펙과 티켓, `CODING_STANDARDS.md`, PR 본문에 둡니다. 회고는 루프를 고치는 루프여서, 한 번 돌 때마다 검증이 강해집니다.

두 가지를 덧붙입니다. 신속 리뷰는 자동 병합이 아닙니다. 이 구조의 주장은 사람 리뷰를 줄이자는 것이지 없애자는 것이 아닙니다. 요약본에 따르면 포콕도 "자동 리뷰만으로는 부족하다"와 "그래도 사람 리뷰는 해야 한다"가 둘 다 참이라고 말합니다. 그리고 이 흐름을 사람 없이 반복 실행할 때 생기는 문제(무엇이 깨우는가, 언제 멈추는가, 어떻게 실패하는가)는 개론의 범위를 넘으므로 부록 C로 보냅니다.

### 14.7 참고해 적용한다면

이 사례에서 가져올 것이 있다면 순서는 **아래 겹부터**입니다. 검증 없이 속도만 올리면 틀린 결과가 더 빨리 쌓일 뿐입니다.

1. **가드레일 확인.** 린트·타입·테스트를 돌리는 pre-commit 훅이나 CI 잡이 있는지 봅니다. 없으면 이것이 첫 작업입니다. 임베디드라면 14.3절의 빠른 층과 중간 층이 여기에 해당합니다.
2. **테스트 점검.** 기존 테스트에서 14.3절의 세 유형을 찾습니다.
3. **표준 문서 작성.** 최근 리뷰에서 반복된 지적만 옮깁니다. 기계적인 것은 체크로, 판단 사항만 문서로 나눕니다.
4. **리뷰 에이전트 연결.** 구현이 끝나면 별도 서브에이전트가 diff를 검사하게 합니다. 처음에는 보고만 받고, 신뢰가 쌓이면 커밋 권한을 줍니다.
5. **PR 템플릿 적용.** 요약, 증거, Merge Danger를 붙입니다. 그 전에 팀의 일방통행 문 목록을 합의합니다.
6. **회고 주기 정착.** 주기를 정해 PR과 리뷰를 모아 회고합니다. 회고의 결과물은 체크 추가나 표준 갱신이어야 합니다.

문 유형은 에이전트가 PR마다 판정하지만, 무엇이 일방통행 문인지는 팀이 정해 표준에 적어 둡니다. 차량·임베디드 조직이라면 다음이 후보입니다.

- 저장 데이터 포맷, 파티션 레이아웃, 영속 설정 스키마의 변경
- 외부에 공개된 인터페이스의 변경: HAL, IPC 메시지, 진단 프로토콜
- 부트 체인, 보안 키, 서명 설정의 변경
- OTA로 현장에 나가면 회수할 수 없는 변경
- 빌드 툴체인이나 컴파일러 플래그처럼 전체 산출물에 퍼지는 변경

효과는 직접 확인합니다. 발표에는 효과 수치가 없습니다(14.8절). 지표는 둘을 짝으로 봅니다.


| 지표              | 무엇을 보는가                    | 읽는 법                                    |
| --------------- | -------------------------- | --------------------------------------- |
| 반복 지적 비율        | 이전 리뷰에서 이미 나온 지적이 다시 나온 비율 | 효과 지표입니다. 회고가 작동하면 0에 가까워집니다            |
| 병합 후 되돌림·핫픽스 건수 | 사람 리뷰를 줄인 대가를 치르고 있나요      | 안전 지표입니다. 늘어나면 걸러지지 않은 것이 통과하고 있다는 뜻입니다 |


하나만 보면 안 됩니다. 리뷰 시간과 반복 지적이 줄었는데 되돌림이 늘고 있다면, 검증이 자동화된 것인지 14.1절의 형식적 승인으로 바뀐 것인지 구분할 수 없습니다. 보조로는 PR당 사람 리뷰 시간, 사람이 처음 발견한 결함의 유형(기계적 유형이 계속 나오면 1겹이 약한 것입니다), 리뷰 에이전트 커밋이 되돌려진 비율(표준이 모호하다는 신호다)을 봅니다. 하네스를 고쳤을 때 나아졌는지를 재는 일반적인 방법, 곧 대표 과제 세트와 1회 통과율과 개입 횟수 같은 eval(평가)은 부록 C에서 다룹니다.

### 14.8 이 사례의 한계

마지막으로 이 사례를 어떤 무게로 받아들일지 정리합니다.


| 한계                       | 내용                                                                                      | 그래서                                |
| ------------------------ | --------------------------------------------------------------------------------------- | ---------------------------------- |
| 정답이 아닙니다                 | 병목을 풀려는 여러 시도 가운데 하나입니다. 주로 웹 개발의 예시로 설명된 방법이라 느린 빌드, 하드웨어 의존, 규격 준수 같은 우리 조건이 전제에 없습니다 | 구조를 통째로 옮기지 않고 맞는 부분만 가져옵니다        |
| 효과 수치가 없는 한 실무자의 방법론입니다  | 통제된 실험의 결과가 아니고, 발표에 효과 수치가 제시되지 않았습니다. 이 장의 서술도 요약본에 근거합니다                             | 14.7절의 지표로 직접 확인합니다                |
| 리뷰 에이전트도 같은 모델입니다        | 구현 에이전트와 같은 맹점을 공유할 수 있습니다. 컨텍스트 분리는 과부하를 풀어 줄 뿐 독립적인 판단을 보장하지 않습니다(11.4절)              | 결정론적인 1겹이 바닥을 받쳐야 합니다              |
| 문 유형 판정이 틀릴 수 있습니다       | 일방통행 문을 양방향으로 잘못 분류하면 가장 위험한 변경이 가장 가볍게 리뷰됩니다                                           | 일방통행 문 목록을 경로·파일 패턴 기반의 체크로 이중화합니다 |
| 앞단(요청 단계)의 HITL은 줄지 않습니다 | 이 구조가 덜어 내는 것은 검증 단계의 반복 리뷰입니다. 스펙이 틀리면 세 겹을 모두 통과한 틀린 결과물이 나옵니다                        | 정렬 단계(12.5절)에 쓰는 시간은 줄이지 않습니다      |


운영하면서 생기는 문제도 두 가지 있습니다. 에이전트가 체크를 통과하려고 테스트를 약하게 고치는 보상 해킹은 이 구조에서도 가능하므로, 테스트 삭제나 완화가 들어간 diff는 반드시 확인하는 항목으로 둡니다(13.4절). 그리고 회고가 규칙을 더하기만 하면 표준 문서가 또 하나의 과잉 제약이 됩니다. 회고의 범주에 규칙 삭제와 무효 지침이 들어 있는 이유입니다.

> **질문**: 지난 한 달 동안 리뷰에서 두 번 이상 한 지적은 무엇인가요? 그중 기계가 판정할 수 있는 것은 몇 개인가요?

### 핵심 정리

- PR 리뷰는 책임 때문에 사람을 뺄 수 없고 시간 때문에 다 볼 수 없는 자리여서 가장 먼저 막힙니다.
- 승인 지점을 줄이는 대신 검증을 자동화하고, 사람 리뷰에서 나온 지적을 아래 겹으로 내려보내 반복을 없앱니다.
- 3겹 구조는 검증된 정답이 아니라 한 실무자의 사례이므로, 맞는 부분만 가져와 지표로 직접 확인합니다.

## 15장. AI 시대에 개발자로 살아남기

- **핵심 질문**: 무엇에 시간을 써야 하나요
- **도달 목표**: 네 가지 한계에 대응하는 자기 역량 항목을 하나 이상 정합니다

14장의 흐름에서 개발자는 가운데(구현)에서 빠지고 앞(정렬)과 뒤(판정), 그리고 흐름 밖(회고)에 남았습니다. 그렇다면 개발자가 하는 일은 무엇으로 바뀌나요? 이 장은 불안을 키우려는 장이 아닙니다. 무엇에 시간을 쓸지를 구체적으로 정하는 장입니다.

답의 근거는 Part 2에서 이미 봤습니다. 에이전트가 못 하는 일이 네 가지 한계로 정리돼 있으므로, 그 한계를 뒤집으면 사람에게 필요한 역량이 나옵니다. 먼저 값이 떨어지는 능력과 오르는 능력을 나누고(15.1), 네 한계에서 역량 지도를 읽습니다(15.2). 이어서 그 역량을 깎아 먹는 위험을 보고(15.3), 내일부터 할 일로 닫습니다(15.4).

### 15.1 값이 떨어지는 능력, 오르는 능력

가르는 기준은 11.2절에서 본 Verifier's Rule입니다. 채점하기 쉬운 일일수록 AI가 먼저 잘하게 됩니다. 그러므로 컴파일러와 테스트와 검색이 바로 판정해 주는 능력부터 값이 떨어집니다.


| 값이 떨어지는 능력             | 왜 떨어지는가                                |
| ---------------------- | -------------------------------------- |
| 문법과 API 레퍼런스 암기        | 컴파일러와 문서가 바로 판정합니다. 에이전트가 가장 잘하는 영역입니다 |
| 보일러플레이트를 빨리 치는 속도      | 생성 속도는 이미 사람의 타이핑을 넘었습니다               |
| "이 라이브러리를 써 봤다"는 경험 자체 | 사용법은 자료를 주면 에이전트가 따라 합니다               |
| 검색으로 답이 나오는 문제의 해결     | 검색과 요약은 에이전트의 기본 동작입니다                 |


값이 떨어진다는 말이 필요 없다는 뜻은 아닙니다. 문법을 모르면 에이전트가 쓴 코드를 읽고 판정할 수 없습니다. 0.3절에서 본 오해 "코딩을 몰라도 된다"가 틀린 이유입니다. 달라지는 것은 이 능력만으로는 더 이상 차이가 나지 않는다는 점입니다.

반대로 채점이 어렵거나, 채점 기준 자체를 만들어야 하는 능력은 값이 오릅니다.


| 값이 오르는 능력      | 무엇인가                                | 앞에서 본 근거                               |
| -------------- | ----------------------------------- | -------------------------------------- |
| ① 문제 정의와 명세화   | 애매한 요구를 검증 가능한 조건으로 바꿉니다            | 요청의 질이 그대로 산출물의 질이 됩니다 (12장)           |
| ② 검증 설계        | 무엇이 맞는지 판정하는 장치를 만듭니다               | 판단을 제약으로 내리는 일입니다 (13.4절)              |
| ③ 아키텍처와 도메인 깊이 | 차량 네트워크, 기능안전, 실시간 제약, 하드웨어 특성을 압니다 | 공개 데이터에 드물고 실물 검증이 필요한 영역입니다 (9장, 11장) |
| ④ 읽는 속도        | 남이나 에이전트가 쓴 코드를 빠르고 정확하게 판정합니다      | 리뷰가 병목입니다 (14장)                        |
| ⑤ 책임질 수 있는 판단력 | 되돌릴 수 없는 결정을 내리고 그 결과에 답합니다         | 책임은 사람에게 남습니다 (13.3절)                  |


①의 차이를 예로 보면 이렇습니다. "CAN 수신 버퍼 구현해 줘"와 "고정 크기 64프레임 링 버퍼, 동적 할당 금지, ISR에서 호출되는 단일 생산자·단일 소비자, 가득 차면 가장 오래된 프레임을 버린다"는 같은 기능을 가리키지만 결과물이 전혀 다릅니다(12.1절). 뒤의 문장은 도메인을 아는 사람만 쓸 수 있습니다.

③은 우리 조직에 특히 해당합니다. 차량·임베디드의 제약은 공개 데이터에 드물어서 에이전트가 흔한 답으로 채우기 쉽습니다(11.1절). 그만큼 그 제약을 아는 사람의 판단이 값집니다. ④는 앞으로 하루 일과에서 비중이 가장 커질 것으로 보는 활동입니다. 쓰는 속도가 아니라 읽고 판정하는 속도가 일의 속도를 정합니다.

### 15.2 한계에서 읽는 역량 지도

15.1절의 목록을 Part 2의 네 가지 한계에 맞춰 다시 놓으면 지도가 됩니다. 에이전트가 구조적으로 못 하는 일의 반대편에 사람이 채워야 할 역량이 있습니다.


| 한계                    | 에이전트가 못 하는 것                 | 사람에게 필요한 역량      | 이번 주에 해 볼 일                                                          |
| --------------------- | ---------------------------- | ---------------- | -------------------------------------------------------------------- |
| ① 전부 볼 수 없다 (9장)      | 검색에 걸리지 않는 연결과 암묵지를 스스로 알아내기 | **도메인·아키텍처 지식**  | 내 모듈에서 검색에 걸리지 않는 연결을 다섯 개 적어 지침 파일에 넣습니다                            |
| ② 모르면 지어낸다 (10장)      | 모를 때 모른다고 말하기                | **검증 습관**        | 에이전트가 말한 API와 옵션을 헤더나 문서에서 직접 찾아봅니다. "완료" 보고를 받으면 빌드와 테스트 출력을 직접 봅니다 |
| ③ 채점되는 것만 잘한다 (11장)   | 정답이 없는 선택을 하고 채점 기준을 만들기     | **설계 판단과 검증 설계** | 설계 제안을 받으면 다른 안 두 개와 각각의 대가를 요구하고, 고른 이유를 적습니다. 팀 규칙 하나를 체크로 내립니다    |
| ④ 묻지 않고 빈칸을 채운다 (12장) | 요청에서 빠진 것을 알아채고 묻기           | **명세화**          | 요청을 보내기 전에 완료 기준과 범위 밖 항목을 한 줄씩 적습니다. 인터뷰 스킬을 한 번 써 봅니다              |


**전부 볼 수 없다 → 도메인·아키텍처 지식.** 에이전트는 읽은 범위 안에서만 판단합니다. ISR에서 호출되는 핸들러, 생성 코드, 빌드 설정에 따라 달라지는 경로는 사람이 알려 줘야 하고, 알려 주려면 알아야 합니다. 시스템 전체의 구조와 "왜 이렇게 만들어졌는가"를 아는 사람이 에이전트의 컨텍스트 밖 기억이 됩니다.

**지어낸다 → 검증 습관.** 확신에 찬 어조는 근거가 아닙니다(10.4절). 이것은 지식이라기보다 습관입니다. 근거를 요구하고, 실존을 확인하고, 실행 결과를 직접 봅니다. 15.1절의 읽는 속도가 이 습관의 바탕입니다.

**채점되는 것만 잘한다 → 설계 판단과 검증 설계.** 둘은 한 쌍입니다. 에이전트의 설계 제안은 그 상황의 최선이 아니라 많이 선호되는 답일 수 있습니다(11.4절). 그것을 우리 프로젝트의 제약에 비춰 고르는 일이 설계 판단입니다. 고른 결과를 테스트와 체크로 바꿔 에이전트가 지키게 하는 일이 검증 설계입니다(13.4절).

**묻지 않는다 → 명세화.** 에이전트는 빈칸을 묻지 않고 채웁니다. 빈칸을 줄일 수 있는 쪽은 사람입니다. 완벽한 요청을 쓰라는 뜻이 아닙니다. 무엇이 빠졌는지 드러나게 하는 절차를 갖추라는 뜻입니다(12.5절).

네 줄을 한 문장으로 줄이면 이렇습니다. 개발자의 가치는 코드를 빨리 쓰는 데서 **무엇이 좋은지 정하고, 그것을 확인할 수 있게 만드는 능력**으로 옮겨 갑니다. 에이전트가 배운 "평균적으로 좋은 것"을 우리 프로젝트의 "실제로 좋은 것"에 맞추는 일이 사람의 몫입니다.

> **질문**: 네 줄 가운데 지금 내가 가장 약한 줄은 어디인가요? 그 줄에서 이번 분기에 할 일을 하나 적습니다.

### 15.3 이해가 썩지 않게

15.2절의 역량에는 공통 전제가 있습니다. 코드와 시스템을 이해하고 있어야 합니다. 그런데 에이전트를 잘 쓸수록 이 전제가 흔들립니다.

Addy Osmani는 루프 엔지니어링(2.2절)을 소개한 글에서, 자동화가 좋아질수록 쉬워지기는커녕 더 날카로워지는 문제를 짚었습니다. 그중 둘이 여기에 해당합니다(출처: [Addy Osmani, Loop Engineering](https://addyosmani.com/blog/loop-engineering/), 2026-06-07).

> "Your understanding still rots if you allow it. The faster the loop ships code you did not write, the bigger the gap between what exists and what you actually get."
> (내버려 두면 이해는 썩는다. 내가 쓰지 않은 코드를 루프가 빨리 출하할수록, 존재하는 것과 내가 실제로 아는 것 사이의 간극이 커진다.)
>
> "And the comfortable posture is the dangerous one."
> (그리고 편안한 자세가 위험한 자세다.)
> 출처: [Addy Osmani, Loop Engineering](https://addyosmani.com/blog/loop-engineering/), 2026-06-07

그는 이 간극을 이해 부채(comprehension debt)라고 부릅니다. 루프가 알아서 돌면 의견을 갖기를 그만두고 나온 것을 그대로 받고 싶어지는데, 그 상태가 가장 위험하다는 것입니다.

이것이 HITL에 치명적인 이유는 Part 2의 개입 지점이 모두 이해를 전제로 하기 때문입니다.


| 이해가 썩으면             | 무너지는 것                      |
| ------------------- | --------------------------- |
| 숨은 연결을 모릅니다         | 요청 단계에서 알려 줄 것이 없습니다 (9.6절) |
| 틀린 답을 알아보지 못합니다     | 검증이 형식적 승인이 됩니다 (14.1절)     |
| 설계 제안을 비교할 기준이 없습니다 | 흔한 답을 그대로 받습니다 (11.4절)      |
| 설명할 수 없는 코드를 머지합니다  | 책임을 질 수 없습니다 (13.3절)        |


HITL은 사람이 그 자리에 있기만 하면 성립하는 것이 아닙니다. **판단할 수 있는 사람**이 있어야 성립합니다. 이해 없이 승인 버튼만 누르는 사람은 흐름 안에 있어도 없는 것과 같습니다.

같은 도구가 정반대로 쓰입니다. Osmani의 말로는 한 사람은 깊이 이해하는 일을 더 빨리 하려고 쓰고, 다른 사람은 이해하지 않으려고 씁니다. 그리고 덧붙입니다. "The loop doesn’t know the difference. You do."(루프는 그 차이를 모른다. 사람은 안다.)

이해를 지키는 방법으로 이 세미나가 권하는 것은 세 가지입니다.

- **병합하기 전에 읽습니다.** 읽을 수 없는 양이면 PR을 나누게 합니다. 그림과 의사코드로 된 PR(14.5절)은 리뷰어의 시간뿐 아니라 이해도 지킵니다.
- **요약을 받는 데서 멈추지 않습니다.** 에이전트의 설명을 읽은 뒤 자기 말로 한 문단으로 다시 설명해 봅니다. 막히는 곳이 이해가 빈 곳입니다.
- **핵심 경로는 직접 따라가 봅니다.** 인터럽트에서 응용 계층까지처럼 시스템의 뼈대가 되는 흐름은 에이전트의 요약에 맡기지 않습니다.

### 15.4 실천 조언과 마무리

내일부터 지킬 것은 네 가지입니다.

1. **설명할 수 없는 코드는 머지하지 않습니다.** 유일한 절대 규칙입니다. 책임(13.3절)과 이해(15.3절)가 이 한 줄에 모입니다.
2. **시키기 전에 30초만 스스로 생각합니다.** 무엇이 맞는지 감이 없으면 틀린 답도 알아볼 수 없습니다.
3. **에이전트의 실패를 기록합니다.** 같은 실패가 두 번 나오면 지침이나 체크로 내립니다(13.4절). 그 기록이 곧 하네스 자산이 됩니다.
4. **배율기로 씁니다.** 에이전트는 기초를 건너뛰게 해 주는 도구가 아니라 기초를 가진 사람의 배율기입니다. 배율은 곱셈이고, 0에 곱하면 0입니다.

개인의 요령으로 끝나면 안 되는 이유가 있습니다. 지침, 스킬, 훅, 체크, 표준 문서는 한 사람의 실패 기록을 팀 전체의 재발 방지로 바꾸는 형태입니다. 그래서 **하네스는 개인의 요령이 아니라 팀의 자산**이고, 코드처럼 버전 관리하고 리뷰합니다. 3.4절에서 본 대로 지식을 지침과 스킬에 두면 도구가 바뀌어도 자산은 남습니다. 앞으로의 차이는 누가 더 좋은 프롬프트를 쓰는가가 아니라 누가 더 좋은 하네스를 가졌는가에서 납니다.

세미나 전체를 두 줄로 줄이면 다음과 같습니다.


| 단원                   | 가져갈 것                                                                    |
| -------------------- | ------------------------------------------------------------------------ |
| Part 1. 코딩 에이전트 도구   | 에이전트는 루프와 컨텍스트로 동작하고, 결과의 차이는 하네스에서 납니다. 도구는 판단 축으로 고르고, 자산은 옮길 수 있게 둡니다 |
| Part 2. HITL이 필요한 이유 | 네 가지 한계가 사람의 자리를 정합니다. 사람은 요청·계획·검증에 서고, 반복되는 판단은 장치로 내립니다               |


두 단원은 하나의 선입니다. Part 1에서 만든 환경이 Part 2에서 정한 사람의 자리를 구현하고, Part 2에서 사람이 내린 판단은 다시 Part 1의 부품으로 내려갑니다.

### 핵심 정리

- 채점하기 쉬운 능력은 값이 떨어지고, 문제 정의·검증 설계·도메인 깊이·읽는 속도·판단은 값이 오릅니다.
- 네 가지 한계를 뒤집으면 도메인·아키텍처 지식, 검증 습관, 설계 판단과 검증 설계, 명세화라는 역량 지도가 나옵니다.
- 이해 없이 승인하는 사람은 HITL이 되지 못하므로, 설명할 수 없는 코드는 머지하지 않습니다.

**세미나를 마치며**: 에이전트가 코드를 쓰는 동안, 나는 요청·계획·실행·검증 가운데 어느 자리에서 무엇을 판단하는 사람이 될 것인가요
