## 0장. 세미나 안내

- **핵심 질문**: 자동완성과 에이전트는 무엇이 다르고, 이 세미나에서 무엇을 가져가는가
- **도달 목표**: 두 단원의 목적과 전체 흐름을 안다

코딩에 AI를 쓰는 방식은 몇 년 사이 세 번 바뀌었다. 이 장은 그 변화에서 달라진 것이 무엇인지 짚고, 세미나의 두 단원이 각각 무엇에 답하는지를 미리 보여 준다.

### 0.1 세 세대

세대가 바뀔 때마다 AI의 성능만 달라진 것이 아니다. 사람이 맡는 역할이 달라졌다.


| 세대  | 형태       | AI가 하는 일                                | 사람의 역할                      |
| --- | -------- | --------------------------------------- | --------------------------- |
| 1세대 | 인라인 자동완성 | 다음에 올 코드를 제안한다                          | 코드를 쓴다. 제안을 받아들이거나 버린다      |
| 2세대 | 채팅       | 질문에 답하고 코드 조각을 만든다                      | 질문하고, 답을 복사해 붙이고, 직접 실행해 본다 |
| 3세대 | 에이전트     | 도구를 써서 파일을 읽고, 고치고, 빌드하고, 결과를 보고 다시 고친다 | 일을 맡기고, 조종하고, 결과를 검증한다      |


1세대와 2세대에서 AI는 텍스트를 내놓고 끝난다. 그 코드를 실행하고 결과를 확인하는 일은 사람이 한다. 3세대는 AI가 **실행 결과를 스스로 관찰하고 다음 행동을 정하는 반복**을 가진다. 이 반복이 있는가가 자동완성·채팅과 에이전트를 가르는 기준이다. 반복의 구조는 1.1절에서 그림으로 본다.

세대가 넘어갈수록 사람이 직접 타이핑하는 양은 줄어든다. 대신 무엇을 맡길지 정하고 결과가 맞는지 판정하는 일이 늘어난다. 사람의 일이 없어지는 것이 아니라 자리가 옮겨 간다.

### 0.2 이 세미나가 다루는 것

> 프롬프트를 잘 쓰는 법이 아니라, **에이전트가 일할 환경과 사람의 자리를 정하는 법**

에이전트의 결과는 지시문 한 줄의 솜씨보다, 에이전트가 무엇을 읽고 어떤 도구를 쓰며 무엇으로 검증받는지에 더 크게 좌우된다. 그래서 Part 1은 에이전트가 일하는 환경을 다룬다. 그런데 환경을 다 갖춰도 전부 맡길 수는 없다. Part 2는 그 이유가 되는 AI의 한계를 보고, 그 한계에서 사람이 있어야 할 자리를 찾는다.


| 단원                       | 답하는 질문                        | 듣고 나면 할 수 있는 것                                     |
| ------------------------ | ----------------------------- | -------------------------------------------------- |
| **Part 1. 코딩 에이전트 도구**   | 에이전트는 어떻게 동작하고, 무엇으로 구성되는가    | 자기 개발 환경에 맞는 도구를 고르고, 필요한 부품만 골라 셋업한다              |
| **Part 2. HITL이 필요한 이유** | 왜 전부 맡길 수 없고, 사람은 어디에 있어야 하는가 | AI의 한계를 근거로 개입 지점을 정하고, 워크플로를 보완하며, 자기 역량의 방향을 잡는다 |


HITL(Human in the Loop)은 자동화된 흐름의 정해진 지점에 사람의 판단을 넣는 것을 말한다. 정확한 정의는 8.1절에서 한다.

다루지 않는 것도 미리 밝혀 둔다. 모델별 벤치마크 순위, 프롬프트 문구 모음, 사람 없이 에이전트를 반복 실행하는 방법의 상세는 이 세미나의 범위가 아니다. 마지막 주제는 부록 C에 읽을거리로만 남겼다.

### 0.3 흔한 오해 세 가지

시작하기 전에 자주 듣는 말 세 가지를 먼저 짚는다. 셋 다 이 세미나가 반대 방향으로 답하는 말이다.


| 오해                    | 실제                                                                        | 다루는 곳           |
| --------------------- | ------------------------------------------------------------------------- | --------------- |
| "에이전트를 쓰면 코딩을 몰라도 된다" | 반대다. 코드를 직접 쓰는 양은 줄지만, 결과가 맞는지 판정하는 능력은 더 많이 요구된다                         | Part 2 전체, 15장  |
| "좋은 프롬프트가 핵심이다"       | 2024년까지의 이야기다. 지금은 지시문보다 컨텍스트와 하네스, 곧 에이전트가 일하는 환경이 결과를 가른다               | 2장              |
| "우리 코드는 특수해서 안 된다"    | 특수할수록 지침과 검증 장치를 갖췄을 때 효과가 크다. 공개된 자료에 없는 규칙은 알려 주지 않으면 에이전트가 알 수 없기 때문이다 | 5장, 9.7절, 10.5절 |


> **질문**: 지금 쓰고 있는 AI 도구는 세 세대 중 어디에 해당하는가. 그 도구가 낸 결과를 마지막으로 직접 검증한 것은 언제인가.

### 0.4 전체 지도

세미나는 도입, 두 단원, 부록으로 이루어진다. Part 1은 원리에서 선택으로, 선택에서 셋업으로 내려간다. Part 2는 사람이 개입하는 지점의 지도를 먼저 그리고, 네 가지 한계를 차례로 본 다음, 그 한계에서 사람의 자리와 개발자의 역량을 끌어낸다.

```text
도입   0장      왜 지금, 무엇을 가져가는가
Part 1 1~2장    원리    에이전트 루프, 컨텍스트, 하네스
       3~4장    선택    도구를 고르는 축과 갈아탈 수 있는 구조, 확실한 비용 절감(MCP와 tool search)
       5~7장    셋업    확장 부품과 조합, 기본 사용 습관, 내 환경 구성
                ── 다리: "환경을 다 갖추면 전부 맡겨도 되는가?" ──
Part 2 8장      지도    HITL의 정의와 네 개의 개입 지점
       9~12장   한계    전부 못 본다 / 지어낸다 / 채점되는 것만 잘한다 / 묻지 않는다
       13~14장  설계    사람을 어디에 둘지, 그리고 사례: PR 리뷰 병목을 줄이려는 시도
       15장     사람    AI 시대에 개발자로 살아남기
```

두 단원은 하나의 선으로 이어진다. Part 1의 핵심 개념인 **컨텍스트 윈도우**와 **검증 장치(센서)** 가 Part 2에서 각각 "전부 볼 수 없다"와 "채점되는 것만 잘한다"라는 한계의 출발점이 된다. Part 2에서 찾은 해법은 다시 Part 1의 부품(지침, Skill, Hook, Subagent)으로 구현한다. 그래서 Part 1을 들을 때는 "이 부품이 나중에 어떤 한계를 막는 데 쓰이는가"를, Part 2를 들을 때는 "이 한계를 어떤 부품으로 줄일 수 있는가"를 함께 떠올리면 좋다.

### 핵심 정리

- 에이전트는 실행 결과를 스스로 관찰하고 반복한다는 점에서 자동완성·채팅과 다르고, 그만큼 사람의 역할은 타이핑에서 조종과 검증으로 옮겨 간다.
- 이 세미나는 프롬프트 작성법이 아니라 에이전트가 일할 환경(Part 1)과 사람이 개입할 자리(Part 2)를 다룬다.
- 두 단원은 컨텍스트 윈도우와 검증 장치(센서)라는 두 개념으로 이어진다.

**다음 장으로**: 에이전트가 "일한다"는 것은 실제로 무슨 일이 일어나는 것인가

## 용어 통일표

같은 대상을 자료마다 다르게 부르는 경우가 많다. 이 세미나에서는 아래 표기로 통일한다. 다른 자료를 읽다가 오른쪽 열의 표기를 만나면 같은 뜻으로 읽으면 된다. 전체 용어 설명은 부록 D에 있다.


| 이 세미나의 표기                   | 뜻                                                                                                                    | 다른 자료에서 보이는 표기                    | 처음 나오는 곳 |
| --------------------------- | -------------------------------------------------------------------------------------------------------------------- | --------------------------------- | -------- |
| 계산적 센서 / 추론적 센서             | 결과를 결정적으로 판정하는 검증 장치(테스트, 린터, 정적 분석) / 모델이 해석해 판정하는 검증 장치(리뷰 에이전트)                                                   | 연산형 센서 / 추론형 센서                   | 2.3절     |
| 보상 해킹                       | 점수만 올리는 꼼수. 목적은 이루지 않은 채 채점만 통과하는 답을 내는 것                                                                            | 꼼수, 테스트 조작                        | 11.2절    |
| 과소명세                        | 요청에 필요한 정보가 빠져 있거나 모호한 상태                                                                                            | 요청 명세의 불완전성                       | 12.1절    |
| 자동 채점(RLVR)                 | 답이 맞는지를 프로그램이 판정해 보상을 주는 학습 방식                                                                                       | 검증기, 채점기, Verifier                | 10.2절    |
| 개입 지점 4단계                   | 요청 → 계획 → 실행 → 검증. 사람이 개입할 수 있는 네 지점                                                                                 | 계획·실행·결과 3층위                      | 8.1절     |
| tool search (defer loading) | 코딩 에이전트(클라이언트)가 도구 정의를 필요할 때만 컨텍스트에 싣는 기능. MCP 공식 문서의 progressive discovery(catalog → inspect → execute 3계층)가 같은 원리다 | progressive discovery, 지연 로드, 3계층 | 4.8절     |
| 서버 쪽 재설계                    | MCP 서버가 메타 도구 몇 개만 노출하도록 서버를 다시 만드는 방식. tool search와 구분해 부른다                                                         | 3계층 패턴                            | 4.6절     |


함께 알아 두면 좋은 기본 용어는 다음과 같다.


| 용어       | 뜻                                                          | 처음 나오는 곳 |
