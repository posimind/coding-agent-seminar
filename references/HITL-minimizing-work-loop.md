# HITL-minimizing-work-loop

> 휴먼인루프를 최소화하는 워크 루프 만들기: 맷 포콕의 3겹 리뷰(자동 체크 · 자동 리뷰 · 사람 리뷰)
> 작성일: 2026-10-12

## 요약

에이전트가 코드를 빠르게 만들수록 병목은 사람 리뷰로 옮겨 간다. 맷 포콕(Matt Pocock)은 발표 "Fixing the PR Bottleneck"에서 이 병목을 푸는 방법으로 **사람 앞에 두 겹의 제동 장치를 세우는 구조**를 제시했다.

- **1겹 자동 체크**: 린트·타입·테스트. CPU만 쓰므로 가장 싸다. 다만 초록색 CI가 "병합해도 된다"는 뜻은 아니다. 에이전트가 쓴 테스트는 거짓말을 할 수 있다.
- **2겹 자동 리뷰**: 구현 에이전트와 분리된 리뷰 에이전트가 팀의 코딩 표준으로 diff를 검사하고, 댓글 대신 **수정 커밋**을 남긴다.
- **3겹 사람 리뷰**: 되돌리기 어려운 변경에 집중한다. 그리고 리뷰에서 나온 지적을 회고(Retro)로 아래 두 겹에 되먹인다.

핵심은 사람을 없애는 것이 아니라 **사람의 위치를 옮기는 것**이다. 사람은 매 PR의 코드를 읽는 자리에서, 코드를 만드는 시스템을 고치는 자리로 이동한다. 같은 지적을 두 번 하지 않게 되면 HITL은 자연히 줄어든다.

이 문서는 다른 `HITL-*` 문서와 짝을 이룬다. 그 문서들은 "왜 사람이 필요한가"를 다루고, 이 문서는 "그 사람의 개입을 어디에 남기고 어디서 덜어낼 것인가"를 다룬다.

## 2. 문제 정의: 제동 장치 없는 공장

포콕은 에이전트와 결정론적 코드가 일을 시작시키는 시스템을 "소프트웨어 공장"이라 부른다. 공장의 속도만 올리고 제동 장치를 달지 않으면 저품질 코드가 쏟아지는 **슬롭 캐논(Slop Cannon)** 이 된다. 나쁜 코드는 다음 에이전트가 읽는 컨텍스트가 되어 더 나쁜 코드를 낳고, 코드베이스의 엔트로피가 빠르게 올라간다.

이때 흔한 대응은 "사람이 전부 리뷰한다"이다. 그러나 이 방식은 두 가지 이유로 무너진다.

- 생성 속도가 리뷰 속도를 넘어서면 리뷰 대기열이 쌓이거나, 리뷰가 형식적인 승인으로 변한다.
- 사람이 같은 지적("이 프로젝트는 이 패턴을 쓰지 않는다")을 PR마다 반복한다. 이 반복이 HITL 비용의 대부분이다.

그래서 목표는 "사람 리뷰를 없앤다"가 아니라 다음과 같이 잡는다.

> **사람에게 도달하는 PR은 이미 기계가 걸러낸 것이어야 하고, 사람이 한 번 한 지적은 다시 사람에게 돌아오지 않아야 한다.**

## 3. 3겹 구조 한눈에 보기

```text
 구현 에이전트 ──▶ [1겹 자동 체크] ──▶ [2겹 자동 리뷰] ──▶ [3겹 사람 리뷰] ──▶ 병합
   (동작하게)        린트·타입·테스트      리뷰 에이전트가       위험도에 따라
                    실패 시 되돌림        표준 검사 후 커밋      깊이를 조절
                         ▲                     ▲                     │
                         │                     │                     │
                         └──────── 회고(Retro) ◀──────────────────────┘
                          기계적 위반 → 자동 체크 추가
                          판단 문제   → CODING_STANDARDS.md 갱신
```

| 겹 | 누가 | 비용 | 잡는 것 | 못 잡는 것 |
| --- | --- | --- | --- | --- |
| 1. 자동 체크 | 린터·컴파일러·테스트 러너 | CPU | 문법, 타입, 금지 패턴, 회귀 | 테스트 자체의 거짓말, 설계 품질 |
| 2. 자동 리뷰 | 별도 컨텍스트의 리뷰 에이전트 | 토큰 | 코딩 표준 위반, 코드 스멜, 스펙 누락·범위 초과 | 표준에 적히지 않은 암묵지, 비즈니스 판단 |
| 3. 사람 리뷰 | 엔지니어 | 사람 시간 | 되돌릴 수 없는 결정, 요구사항과의 정합 | (마지막 방어선) |

아래 겹일수록 싸다. 그래서 설계 원칙은 하나다. **위 겹에서 발견된 문제를 가능한 한 아래 겹으로 내려보낸다.**

세미나 본문의 용어로 옮기면 1겹은 결정적 검증자(연산형 센서), 2겹은 별도 검증 에이전트(추론형 센서)다. 본문의 "자기 채점 금지" 원칙과 같은 이야기다.

## 4. 1겹: 자동 체크와 깊은 모듈

### 4.1 자동 체크가 거짓말하는 세 가지 방식

에이전트는 구현과 테스트를 함께 쓴다. 그러면 테스트가 통과해도 아무것도 증명하지 못하는 경우가 생긴다.

| 유형 | 무엇인가 | 왜 문제인가 |
| --- | --- | --- |
| 동어반복 테스트 | 구현에 적은 값을 테스트가 그대로 다시 단언한다 | 요구사항이 아니라 구현을 검증한다. 구현이 틀려도 통과한다 |
| 구조 민감성 테스트 | 동작이 아니라 소스 파일의 내부 구조·순서를 확인한다 | 리팩토링만 해도 깨진다. 동작이 망가져도 통과할 수 있다 |
| 실패하지 않는 테스트 | 의존성을 가짜로 과도하게 대체한다 | 실제 환경의 오류 경로를 한 번도 타지 않는다 |

```c
/* 동어반복: 구현의 상수를 테스트가 그대로 되읽는다 */
#define CAN_RETRY_LIMIT 3
TEST(can, retry_limit) { ASSERT_EQ(CAN_RETRY_LIMIT, 3); }

/* 바람직한 형태: 인터페이스를 통해 관찰 가능한 동작을 검증한다 */
TEST(can, gives_up_after_three_failed_sends) {
    fake_bus_fail_always();
    ASSERT_EQ(can_send(&msg), CAN_ERR_TIMEOUT);
    ASSERT_EQ(fake_bus_send_count(), 3);
}
```

포콕은 이를 에이전트의 부정행위가 아니라 **구현에 과도하게 결합된 테스트**로 본다. 원인이 결합이므로 해법도 프롬프트가 아니라 설계에 있다.

### 4.2 해법: 깊은 모듈

John Ousterhout의 『A Philosophy of Software Design』에서 온 개념이다. **작은 인터페이스 뒤에 많은 동작을 숨긴 모듈**이 깊은 모듈이다. 반대로 인터페이스가 구현만큼 복잡한 모듈은 얕은 모듈이다.

깊은 모듈이 테스트 문제를 푸는 이유는 단순하다. 호출자와 테스트가 **같은 인터페이스**를 지나가게 되므로, 에이전트가 내부 구조에 손을 대는 테스트를 쓸 여지가 줄어든다. `codebase-design` 스킬은 이를 "인터페이스가 곧 테스트 표면이다. 인터페이스 너머를 테스트하고 싶다면 모듈 모양이 잘못된 것"이라고 정리한다.

같은 스킬이 팀 공용 어휘로 정의하는 용어는 다음과 같다.

| 용어 | 뜻 | 누가 이득을 보나 |
| --- | --- | --- |
| 깊이(Depth) | 인터페이스 한 단위를 배워서 쓸 수 있는 동작의 양 | — |
| 레버리지(Leverage) | 구현 하나가 여러 호출처와 여러 테스트에서 값을 한다 | 호출자 |
| 지역성(Locality) | 변경·버그·지식·검증이 한곳에 모인다. 한 번 고치면 전부 고쳐진다 | 유지보수자 |
| 심(Seam) | 그 자리를 편집하지 않고 동작을 바꿀 수 있는 지점. 모듈의 인터페이스가 놓이는 위치 (Michael Feathers) | 테스트 작성자 |

실무에 바로 쓸 수 있는 판별법도 두 가지 있다.

- **삭제 테스트**: 모듈을 지웠다고 상상한다. 복잡도가 사라지면 단순 전달자였고, 호출처 여러 곳에 복잡도가 다시 나타나면 제 몫을 하던 모듈이다.
- **어댑터 개수**: 어댑터가 하나면 가상의 심이고, 둘이면 진짜 심이다. 실제로 바뀌는 것이 없으면 심을 만들지 않는다.

저장소에는 이를 코드베이스에 적용하는 `improve-codebase-architecture` 스킬도 있다. 모듈을 깊게 만들 후보를 찾아 HTML 보고서로 보여 준다.

### 4.3 자동 체크에 올릴 것

회고 스킬의 분류 기준이 여기서 유용하다. 위반이 **기계적**이면(고정된 문법 패턴, 금지 API, import 형태, 파일 위치 규칙) 표준 문서에 쓰지 말고 결정론적 체크로 만든다. 린터 커스텀 규칙, pre-commit 훅, CI 잡 중 가장 싼 것을 고른다. 또한 린트·타입·테스트를 돌리는 pre-commit 훅이나 CI 잡이 **아예 없는 저장소는 그 자체가 결함**이다.

## 5. 2겹: 자동 리뷰와 역할 분리

### 5.1 구현 에이전트는 이미 과부하다

구현 에이전트는 탐색, 코드 작성, 디버깅을 한 컨텍스트에서 한다. 여기에 코딩 표준까지 얹으면 컨텍스트 압박이 가장 큰 곳에 짐을 더 싣는 셈이다. 리뷰 에이전트는 정반대다. diff를 받으므로 탐색이 필요 없고 디버깅도 거의 하지 않는다.

그래서 포콕은 일을 둘로 나눈다. Red-Green-Refactor에 대응시키면 이렇다.

| 단계 | 담당 | 목표 | 읽는 지침 |
| --- | --- | --- | --- |
| Red → Green | 구현 에이전트 | 동작하게 만든다 | 스펙·티켓, 최소한의 `AGENTS.md` |
| Refactor | 리뷰 에이전트(별도 서브에이전트, 별도 컨텍스트) | 좋게 만든다 | `CODING_STANDARDS.md` |

### 5.2 코딩 표준은 어디에 두나

- `AGENTS.md` / `CLAUDE.md`: 모든 에이전트의 컨텍스트에 항상 들어간다. 그래서 극히 아껴 쓰고, 주로 다른 파일을 가리키는 **네비게이션 포인터**만 둔다.
- `CODING_STANDARDS.md`: 구현 때가 아니라 **리뷰 때** 읽는다. 1,000줄을 넘으면 docs 폴더로 나누고 포인터를 둔다.
- 표준 문서에는 **판단이 필요한 규칙**만 남긴다(파일 간 일관성, 주변 스타일과의 어울림 등). 기계가 강제할 수 있는 것은 4.3절대로 체크로 내린다.

이 배치는 세미나 본문 4.5절의 과잉 제약(Overconstraining) 논의와 같은 방향이다. 항상 로드되는 지침을 줄이고, 필요한 시점에 필요한 에이전트만 읽게 한다.

### 5.3 리뷰 에이전트의 구성

저장소의 `code-review` 스킬은 diff를 두 축으로 검사하고, 두 축을 **병렬 서브에이전트**로 돌려 서로의 컨텍스트를 오염시키지 않게 한다.

| 축 | 질문 | 보고 내용 |
| --- | --- | --- |
| Standards | 저장소의 문서화된 코딩 표준을 따르는가 | 위반 위치와 근거 규칙, 코드 스멜(판단 사항으로 표기) |
| Spec | 원래 이슈·스펙이 요구한 것을 구현했는가 | 누락·부분 구현, 요청하지 않은 동작(범위 초과), 구현은 됐으나 틀려 보이는 부분 |

Standards 축에는 저장소가 아무것도 문서화하지 않았어도 적용되는 기본 목록이 있다. Fowler의 『Refactoring』 3장 코드 스멜 12종이다(불분명한 이름, 중복 코드, 기능 편애, 산탄총 수술, 추측성 일반화 등). 규칙은 두 가지다. 저장소의 표준이 기본 목록보다 우선하고, 도구가 이미 강제하는 것은 건너뛴다.

### 5.4 두 가지 운영 원칙

**직접 만든다.** 포콕은 범용 리뷰 서비스를 사는 대신 팀의 표준을 담은 리뷰를 직접 구축하라고 권한다. 범용 리뷰어는 팀 맥락을 몰라 오탐이 많다는 이유다.

**댓글이 아니라 커밋.** 리뷰 에이전트가 댓글을 달면 사람이 읽고 판단하고 다시 지시해야 한다. 사람의 일이 늘어난다. 그래서 기본값은 수정 커밋이고, 댓글은 정말로 사람의 결정이 필요한 열린 질문에만 쓴다.

> 참고: 공개된 `code-review` 스킬의 본문은 두 축의 결과를 나란히 **보고**하는 절차로 되어 있다. "리뷰 에이전트가 커밋한다"는 발표의 운영 원칙이며, 커밋 권한과 범위는 팀이 직접 구성해야 한다.

## 6. 3겹: 사람 리뷰를 좁고 빠르게

### 6.1 Merge Danger: 문 유형으로 리뷰 깊이를 정한다

AWS에서 쓰는 일방통행 문/양방향 문 개념으로 PR을 분류한다.

| 문 유형 | 뜻 | 예 | 리뷰 방식 |
| --- | --- | --- | --- |
| 양방향 문(Two-way door) | 싸게 되돌릴 수 있다 | 대부분의 기능 변경, 리팩토링 | 신속 리뷰 |
| 일방통행 문(One-way door) | 되돌리기 어렵거나 파괴적이다 | 데이터 손실, 비싼 마이그레이션, 대량 메일 발송 | 엄격한 리뷰 |

PR 본문 하단에 이 요약을 자동으로 붙여, 리뷰어가 얼마나 깊이 읽어야 하는지 먼저 알게 한다. 저장소 `pr` 스킬의 PR 본문 템플릿은 세 부분이다.

```markdown
## Summary
<다이어그램, diff 스케치, 또는 트리>

## Evidence
- **Before:** <스크린샷/출력/실패한 테스트 실행>
  **After:** <스크린샷/출력/통과한 테스트 실행>

## Merge Danger
**Door:** <one-way 또는 two-way>
**Blast Radius:** <한 단어로 영향 범위>
```

### 6.2 긴 글 대신 그림과 의사코드

`pr` 스킬의 Summary 지침은 HumanLayer의 Dex Horthy가 만든 `show-me` 스킬에서 가져왔다. 원칙은 "요점을 전달하는 가장 작은 뷰를 고른다"이다.

| 보여 줄 것 | 표현 |
| --- | --- |
| 로직·알고리즘 | 의사코드 |
| 런타임 제어 흐름 | 호출 트리 |
| 파일 책임, 넓은 리팩토링 | 얕은 파일 트리 |
| 컴포넌트 상호작용, 데이터 흐름 | Mermaid 다이어그램 |
| 기존 구조 위의 변경 | 트리·의사코드에 대한 `diff` |

증거에도 등급이 있다. 화면 변경은 스크린샷이 가장 좋고, 그다음이 실행 기반 증거(테스트 결과, 콘솔 출력)다. "이전에는 실패하고 지금은 통과하는 바로 그 테스트"를 보여 준다.

### 6.3 회고(Retro): 사람 리뷰를 시스템 개선으로 바꾼다

포콕의 표현으로, 사람 리뷰는 코드만 검토하는 것이 아니라 **그 코드를 만든 시스템을 검토하는 일**이다. `retro` 스킬은 세션 하나, PR 하나, 또는 일주일 치 PR과 리뷰를 입력으로 받아 에이전트 **환경**의 개선 후보를 심각도순으로 제안한다.

| 범주 | 질문 | 언제 본다 |
| --- | --- | --- |
| 네비게이션 | 에이전트가 필요한 파일을 쉽게 찾았는가. 포인터가 필요한가 | 정보를 찾는 데 오래 걸렸을 때 |
| 자동 체크 | 이 실수를 잡을 체크가 가능했는가. 이미 있는데 연결이 안 됐는가 | 체크로 잡을 수 있는 실수가 나왔을 때 |
| 코딩 표준 | 리뷰 에이전트에 규칙을 추가·삭제·명확화할 것인가 | 리뷰 에이전트가 놓쳤을 때 |
| 전역 `AGENTS.md` | 표준이나 체크로 옮길 지침이 있는가 | 파일이 비대할 때 |
| 도구 경제성 | 비싼 도구 호출을 줄일 수 있는가 | 토큰 비효율적인 호출이 있었을 때 |
| 무효 지침(No-ops) | 행동을 바꾸지 못하는 지침이 있는가 | 지침 파일이 크고 다루기 어려울 때 |
| 정보 접근 | 에이전트가 볼 수 없었던 핵심 정보가 있는가(개발 서버 로그 등) | 결정적 정보가 없었을 때 |

회고의 판단 순서는 4.3절과 같다. **기계적 위반이면 체크를 만들고, 판단 문제일 때만 표준 문서에 쓴다.** 규칙을 쓰는 것보다 체크를 만드는 것이 기본값이다.

## 7. HITL을 최소화하는 워크 루프 조립

### 7.1 전체 흐름과 사람의 위치

저장소의 스킬 흐름을 단계로 펴면 다음과 같다. 사람이 반드시 있어야 하는 자리는 **앞쪽의 정렬**과 **뒤쪽의 일방통행 문**, 그리고 **루프 바깥의 회고**다.

| 단계 | 하는 일 | 관련 스킬 | 사람 개입 |
| --- | --- | --- | --- |
| 0. 정렬 | 요구를 인터뷰로 구체화하고 스펙으로 만든다 | `grill-me`, `to-spec` | **필수** (과소명세는 여기서만 싸게 잡힌다) |
| 1. 분해 | 스펙을 세로 조각 티켓으로 나눈다 | `to-tickets` | 검토 |
| 2. 구현 | 합의된 심에서 TDD로 구현한다 | `implement`, `tdd` | 없음 |
| 3. 자동 체크 | 타입체크·단일 테스트를 자주, 전체 테스트를 끝에 한 번 | pre-commit, CI | 없음 |
| 4. 자동 리뷰 | 표준·스펙 두 축 검사 후 수정 커밋 | `code-review` | 열린 질문에만 |
| 5. PR 작성 | 요약·증거·Merge Danger를 붙인다 | `pr` | 없음 |
| 6. 사람 리뷰 | 문 유형에 따라 깊이를 조절한다 | — | 양방향 문: 신속 / 일방통행 문: **필수·엄격** |
| 7. 회고 | 지적을 체크와 표준으로 내려보낸다 | `retro` | 제안 승인 |

`implement` 스킬 원문이 2~4단계를 한 문단으로 묶어 둔다. "가능하면 합의된 심에서 `tdd`를 쓴다. 타입체크와 단일 테스트 파일을 자주 돌리고 전체 테스트는 끝에 한 번 돌린다. 끝나면 `code-review`를 호출한다."

### 7.2 세미나의 루프 공식에 대응시키기

본문 3.6절의 최소 루프에서 판단이 필요한 줄은 `verifier.passes`와 `escalate_to_human`이었다. 3겹 구조는 이 두 줄에 대한 구체적인 답이다.

```python
for step in range(MAX_STEPS):
    implement_agent.work(ticket, state)            # 동작하게 (Red-Green)

    if not automated_checks.pass_():               # 1겹: 결정적 검증
        continue                                   #   실패 출력을 넣고 재시도

    review = review_agent.review(diff, standards, spec)   # 2겹: 별도 컨텍스트
    review.commit_fixes()                          #   댓글이 아니라 커밋
    if review.changed_code:
        continue                                   #   고쳤으면 1겹부터 다시

    pr = open_pr(summary, evidence, merge_danger)  # 사람 친화적 PR
    if pr.door == "one-way" or review.open_questions:
        return escalate_to_human(pr)               # 3겹: 엄격 리뷰
    return fast_track_review(pr)                   # 3겹: 신속 리뷰

return escalate_to_human(state)                    # 스텝 캡 도달
```

| 루프 구성 요소 (본문 3.6) | 이 구조에서의 실체 |
| --- | --- |
| 검증 | 1겹 자동 체크 + 2겹 리뷰 에이전트 |
| 에스컬레이션 조건 | 일방통행 문, 리뷰 에이전트의 열린 질문, 스텝·예산 캡 |
| 외부 상태 | 스펙·티켓(이슈 트래커), `CODING_STANDARDS.md`, PR 본문 |
| 루프를 개선하는 루프 | 회고. 한 번 돌 때마다 검증자가 강해진다 |

`fast_track_review`가 "자동 병합"이 아니라는 점에 주의한다. 발표의 주장은 사람 리뷰를 **줄이는** 것이지 없애는 것이 아니다. 포콕 본인도 "자동 리뷰가 부족하다"와 "그래도 사람 리뷰는 해야 한다"는 둘 다 참이라고 말한다.

### 7.3 도입 순서

아래 겹부터 세운다. 본문의 경고("하네스 없는 루프는 검증 없이 빨리 도는 기계다")와 같은 이유다.

1. **가드레일 확인**: 린트·타입·테스트를 돌리는 pre-commit 훅 또는 CI 잡이 있는지 본다. 없으면 이것이 첫 작업이다.
2. **테스트 감사**: 기존 테스트에서 동어반복·구조 민감성·실패 불가 유형을 찾는다. 많이 나오는 모듈이 깊게 만들 후보다.
3. **`CODING_STANDARDS.md` 작성**: 최근 PR 리뷰에서 반복된 지적만 옮긴다. 기계적인 것은 체크로, 판단 사항만 문서로 나눈다. 전역 지침에 있던 스타일 규칙도 이쪽으로 뺀다.
4. **리뷰 에이전트 연결**: 구현이 끝나면 별도 서브에이전트가 diff를 검사하게 한다. 처음에는 보고만 받고, 신뢰가 쌓이면 커밋 권한을 준다.
5. **PR 템플릿 적용**: 요약·증거·Merge Danger 세 부분. 팀의 일방통행 문 목록을 먼저 합의한다.
6. **회고 주기 정착**: 주 단위로 PR과 리뷰를 모아 회고한다. 결과물은 반드시 체크 추가나 표준 갱신이어야 한다.

### 7.4 일방통행 문 목록 예시

문 유형 판정은 에이전트가 하지만, 무엇이 일방통행 문인지는 팀이 정해 표준에 적어 둔다. 임베디드·플랫폼 조직이라면 다음이 후보다.

- 저장 데이터 포맷, 파티션 레이아웃, 영속 설정 스키마 변경
- 외부로 공개된 인터페이스(HAL, IPC 메시지, 진단 프로토콜) 변경
- 부트 체인, 보안 키, 서명 설정 변경
- OTA로 현장에 나가면 회수할 수 없는 변경
- 빌드 툴체인·컴파일러 플래그 등 전체 산출물에 퍼지는 변경

### 7.5 줄어들고 있는지 확인하는 지표

| 지표 | 의미 |
| --- | --- |
| 반복 지적 비율 | 이전 리뷰에서 이미 나온 지적이 다시 나온 비율. 회고가 작동하면 0에 가까워진다 |
| PR당 사람 리뷰 시간 | 양방향 문 PR에서 줄어야 한다 |
| 사람이 처음 발견한 결함의 유형 | 기계적 유형이 계속 나오면 1겹이 약한 것이다 |
| 병합 후 되돌림·핫픽스 건수 | 사람 리뷰를 줄인 대가를 치르고 있는지 보는 안전 지표 |
| 리뷰 에이전트 커밋의 되돌림 비율 | 표준이 모호하거나 틀렸다는 신호 |

## 8. 한계와 주의점

- **리뷰 에이전트도 같은 모델이다.** 구현 에이전트와 같은 맹점을 공유할 수 있다. 컨텍스트 분리는 과부하를 풀어 줄 뿐, 독립적인 판단을 보장하지 않는다. 그래서 결정론적인 1겹이 바닥을 받쳐야 한다.
- **문 유형 판정이 틀릴 수 있다.** 일방통행 문을 양방향으로 잘못 분류하면 가장 위험한 변경이 가장 가볍게 리뷰된다. 7.4절의 목록은 경로·파일 패턴 기반의 결정론적 체크로 이중화하는 것이 안전하다.
- **보상 해킹.** 에이전트가 체크를 통과하려고 테스트를 약하게 고치는 것은 여전히 가능하다. 테스트 파일 삭제·완화가 포함된 diff는 리뷰 에이전트의 필수 확인 항목으로 둔다.
- **표준 문서의 비대화.** 회고가 규칙을 추가만 하면 `CODING_STANDARDS.md`가 또 다른 과잉 제약이 된다. 회고 범주에 "삭제·명확화"와 "무효 지침"이 들어 있는 이유다.
- **앞단의 HITL은 줄지 않는다.** 이 구조가 덜어내는 것은 결과물 검증 단계의 반복 리뷰다. 요청을 구체화하는 정렬 단계는 오히려 더 중요해진다. 스펙이 틀리면 3겹이 전부 통과한 틀린 결과물이 나온다.
- **근거의 성격.** 3겹 구조는 한 실무자의 방법론이며 통제된 실험 결과가 아니다. 효과 수치는 발표에 제시되지 않았다. 7.5절의 지표로 직접 확인해야 한다.

## 10. 적용 체크리스트

- [ ] 린트·타입·테스트를 돌리는 pre-commit 훅 또는 CI 잡이 있다
- [ ] 테스트가 모듈의 인터페이스를 통해 동작을 검증한다(상수 재단언, 소스 구조 확인, 과도한 대체가 없다)
- [ ] 팀이 모듈·인터페이스·심·지역성·레버리지를 같은 뜻으로 쓴다
- [ ] 코딩 표준이 전역 지침이 아니라 `CODING_STANDARDS.md`에 있고, 판단 사항만 담는다
- [ ] 리뷰는 구현과 다른 컨텍스트의 에이전트가 하고, 표준과 스펙 두 축을 본다
- [ ] 리뷰 에이전트의 기본 출력은 수정 커밋이고, 댓글은 열린 질문에만 쓴다
- [ ] 모든 PR에 요약(그림·의사코드), 전후 증거, Merge Danger가 있다
- [ ] 팀의 일방통행 문 목록이 합의되어 있고, 해당 PR은 사람이 엄격히 리뷰한다
- [ ] 주기적으로 회고하고, 결과가 체크 추가나 표준 갱신으로 이어진다
- [ ] 반복 지적 비율과 병합 후 되돌림 건수를 추적한다
