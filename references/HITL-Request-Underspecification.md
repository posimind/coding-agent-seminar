# HITL-Request-Underspecification

> 휴먼인루프가 필요한 이유: 요청 명세의 불완전성 문제
> 작성일: 2026-09-26

## 요약

요청이 불완전하면 AI는 묻기보다 추측으로 빈칸을 채우고, 그 추측이 사용자의 실제 요구와 어긋난 만큼 결과물이 빗나간다. 이 주장은 대체로 사실이며, 2024~2026년 연구들이 이를 수치로 뒷받침한다.

- 코드 LLM은 요구사항이 모호·불완전해도 60% 이상 질문 없이 바로 코드를 생성했고, 정답률(Pass@1)은 35~52% 떨어졌다 (HumanEvalComm).
- 에이전트가 사용자와 상호작용해 누락 정보를 얻으면 SWE 과제 성공률이 비상호작용 대비 최대 74% 올랐다. 다만 모델은 "정보가 부족한 요청"을 스스로 잘 구분하지 못했다 (Ambig-SWE, ICLR 2026).
- 원인으로는 한 턴 단위로 응답을 평가하는 RLHF 선호 데이터가 "완결돼 보이는 추측성 답"을 "미완의 확인 질문"보다 선호하게 만든다는 분석이 있다.

따라서 요청 단계에서 사람이 개입해 목표를 구체화하는 것은 휴먼인루프(HITL)의 독립된 한 축이다. grill-me 같은 인터뷰 스킬, Claude Code의 인터뷰→스펙 워크플로, Spec Kit의 clarify 단계가 이를 제도화한 수단이다.

## 1. 문제 정의: 요청 명세의 불완전성

사람이 머릿속에 가진 요구사항 전체를 한 번의 요청문에 빠짐없이 담는 것은 거의 불가능하다. 이 격차를 연구에서는 과소명세(underspecification)라 부른다.

소프트웨어 요구공학은 요구사항 결함을 세 가지로 나눈다. HumanEvalComm 연구도 같은 분류를 그대로 썼다.

| 유형 | 의미 | 코딩 에이전트 요청 예시 |
| --- | --- | --- |
| 불완전(Incomplete) | 필요한 정보가 빠짐 | "로그 수집 기능 추가해줘" — 저장 위치, 보존 기간, 포맷 없음 |
| 모호(Ambiguous) | 여러 해석이 가능 | "정렬해줘" — 오름차순/내림차순, 안정 정렬 여부 불명 |
| 불일치(Inconsistent) | 설명끼리 충돌 | 설명은 "최신순", 예시 출력은 오래된 순 |

핵심은 요청자가 누락을 **자각하지 못한다**는 점이다. 전문가일수록 도메인 상식(예: "차량 SW니까 당연히 동적 할당 금지")을 말할 필요 없는 전제로 여긴다. 이 암묵지가 요청문에서 빠지면, AI 입장에서는 그 제약이 존재하지 않는 것과 같다.

mattpocock/skills의 README도 가장 흔한 실패 유형으로 "에이전트가 내가 원한 것을 하지 않았다"를 꼽는다. 그는 이를 개발자와 요청자 사이에 늘 있던 오정렬(misalignment)이 AI 시대에 그대로 재현된 것으로 본다.

## 2. 왜 AI는 묻지 않고 빈칸을 채우는가

"AI는 사용자를 만족시키도록 학습되어 알아서 채운다"는 직관은 연구로 상당 부분 뒷받침된다. 다만 원인은 "의도적 목적성"보다 **학습 방식에서 생긴 경향**으로 보는 것이 정확하다.

**(1) 단일 턴 선호 평가의 편향.** Zhang 등(ICLR 2025)은 최신 LLM이 모호한 요청에 확인 질문 없이 사용자 의도를 가정하고 바로 답한다고 지적했다. 원인으로 RLHF 선호 데이터 수집 방식을 든다. 평가자는 "다음 한 턴"만 보고 응답 순위를 매기므로 확인 질문의 가치를 판단하기 어렵다. 그 결과 완결돼 보이는 추측성 답이 미완의 질문보다 선호되는 편향이 생길 수 있다. 저자들은 이를 "추측(speculate)"이라고 표현했으므로, 확정된 인과가 아닌 유력한 가설로 인용해야 한다.

**(2) 아첨(sycophancy) 경향.** Anthropic의 Sharma 등(2023)은 RLHF로 학습된 주요 AI 어시스턴트 5종 모두가 사용자 믿음에 맞춘 응답을 하는 경향을 보였다고 보고했다. 사람의 선호 판단 자체가 사용자 견해와 일치하는 응답을 더 높게 평가했기 때문이다. 이는 "사용자를 기쁘게 하는 응답"이 보상받는 구조를 보여준다. 단, 이 논문은 확인 질문 회피를 직접 다루지 않으므로 간접 근거로만 쓴다.

**(3) 행동 기본값(Default to Action).** Ambig-SWE 연구진은 현재 모델이 정보가 심하게 부족해도 비상호작용, 즉 바로 실행하는 쪽을 기본값으로 삼는다고 결론지었다. 일부 오픈 모델은 상호작용을 강하게 권유해도 질문하지 않았다.

아래는 "빈칸 채우기"가 실제로 어떻게 보이는지 보여주는 예시다.

```python
# 요청: "사용자 목록을 정렬하는 함수 만들어줘"
# 에이전트가 암묵적으로 채운 가정들 (사용자는 이 가정을 본 적 없음)
def sort_users(users):
    # 가정 1: 정렬 기준은 이름     (실제 요구: 최근 로그인 시각)
    # 가정 2: 오름차순               (실제 요구: 내림차순)
    # 가정 3: 원본 리스트 변경 허용  (실제 요구: 불변 유지)
    users.sort(key=lambda u: u.name)
    return users
```

코드는 실행되고 테스트도 그럴듯하게 통과할 수 있다. 문제는 가정이 **코드 속에 조용히 묻힌다**는 점이다. 사용자는 결과를 받고 나서야 어긋남을 발견한다.

## 3. 연구 근거

세 연구가 같은 결론을 가리킨다. 모델은 정보 부족을 잘 감지하지 못하고, 감지하지 못하면 성능이 크게 떨어지며, 사람과 대화하면 상당 부분 회복된다.

| 연구 | 대상 | 핵심 결과 |
| --- | --- | --- |
| [Ambig-SWE](https://arxiv.org/abs/2502.13069) (Vijayvargiya, Neubig 등, ICLR 2026) | SWE-Bench Verified의 과소명세 변형, 에이전트 | 모델은 명확한 지시와 과소명세 지시를 잘 구분하지 못함. 상호작용 시 성공률이 비상호작용 대비 최대 74% 향상. 그래도 완전 명세 대비 격차는 남음 |
| [HumanEvalComm](https://arxiv.org/abs/2406.00215v2) (Wu & Fard, UBC) | HumanEval 164문제를 모호·불완전·불일치로 변형 | 60% 이상의 응답이 질문 없이 코드 생성. Pass@1 35~52%, 테스트 통과율 17~35% 하락 |
| [Modeling Future Conversation Turns](https://arxiv.org/abs/2410.13788) (Zhang, Knox, Choi, ICLR 2025) | 모호한 오픈도메인 QA | 다음 턴 결과까지 고려한 선호 학습으로 F1 5% 향상, 질문 필요 여부 판단 정확도 3% 향상 |

**해석 시 주의점**

- "최대 74%"는 특정 모델·설정의 최대치다. 모든 경우의 평균 효과로 인용하면 과장이 된다.
- HumanEvalComm의 모델군은 2024년 코드 LLM 중심이다. 최신 프런티어 모델은 질문 빈도가 더 높을 수 있다. 그러나 2026년 Ambig-SWE 최종판에서도 "기본값은 비상호작용"이라는 결론이 유지됐다.
- 세 연구 모두 "질문하면 좋아진다"만이 아니라 **언제 물을지 판단하는 능력**이 병목이라고 본다. 이것이 사람이 요청 단계에 개입해야 하는 직접적 근거다.

## 4. 상업 개발에서 추측 채움이 만드는 비용

목표가 느슨한 요청("재미있는 웹페이지 하나")에서는 AI의 추측이 오히려 가치가 될 수 있다. 반면 상업 개발은 인터페이스 계약, 성능·안전 요구, 조직 코딩 규칙처럼 **정답이 이미 정해진 결정**이 대부분이다. 여기서 추측은 곧 결함 후보가 된다.

Claude Code 공식 문서도 같은 구분을 한다. 탐색 중이거나 되돌릴 여유가 있을 때는 모호한 프롬프트가 유용하다. 하지만 Claude는 의도를 추론할 뿐 마음을 읽지는 못하므로, 파일·제약·기존 패턴을 명시하라고 권한다.

비용은 발견 시점이 늦을수록 커진다.

| 발견 시점 | 비용 |
| --- | --- |
| 요청 단계(인터뷰) | 질문 몇 개에 답하는 시간 |
| 계획 검토 단계 | 계획 수정, 재계획 토큰 |
| 구현 완료 후 리뷰 | 코드 재작성, 컨텍스트 오염, 재시도 |
| 통합·양산 이후 | 결함 수정, 재검증, 일정 지연 |

임베디드·차량 SW 예시로 보면 차이가 분명하다.

```c
/* 요청: "CAN 메시지 수신 버퍼 구현해줘" */

/* 에이전트가 채운 기본값 — 일반 리눅스 앱 기준 */
typedef struct {
    can_frame_t *frames;      /* malloc 동적 할당      */
    size_t cap;               /* 가득 차면 realloc 확장 */
    pthread_mutex_t lock;     /* 뮤텍스로 보호          */
} can_rx_buf_t;

/* 실제 요구 — 말하지 않은 암묵지 */
/* - 동적 할당 금지 (MISRA/안전 코딩 규칙)                */
/* - 고정 크기 링버퍼, 오버플로 시 가장 오래된 프레임 폐기  */
/* - ISR에서 호출되므로 lock-free 단일 생산자/단일 소비자  */
#define CAN_RX_DEPTH 64u
typedef struct {
    can_frame_t frames[CAN_RX_DEPTH];
    volatile uint32_t head, tail;
} can_rx_ring_t;
```

첫 번째 구현은 "동작하는 코드"지만 이 도메인에서는 쓸 수 없다. 요청문에 제약 세 줄만 있었다면 피할 수 있었던 재작업이다.

## 5. 휴먼인루프 관점에서의 위치

휴먼인루프는 흔히 "위험한 행동 승인"이나 "결과 검토"로만 이해된다. 요청 명세 문제는 그보다 앞선 **의도 정렬 단계**의 개입이 필요하다는 점에서 별개의 축이다.

| 개입 시점 | 사람이 제공하는 것 | 예시 |
| --- | --- | --- |
| 요청 단계 (이 문서의 주제) | 의도, 제약, 판단 기준 | 인터뷰 스킬, 스펙 작성, 확인 질문 응답 |
| 계획 단계 | 접근 방식 승인 | 플랜 모드 검토, 설계 선택 |
| 실행 단계 | 위험 행동 허가 | 권한 승인, 파괴적 명령 차단 |
| 검증 단계 | 품질 판정 | 코드 리뷰, 수용 테스트 |

요청 단계 개입이 특별한 이유는 두 가지다.

1. **대체 불가능한 정보원.** 테스트, 린터, 리뷰 에이전트는 "정해진 기준"과의 차이를 잡는다. 하지만 기준 자체가 사용자 머릿속에만 있으면 어떤 자동 검증도 이를 찾을 수 없다. grilling 스킬도 사실(fact)은 에이전트가 직접 찾고, 결정(decision)만 사용자에게 묻도록 역할을 나눈다.
2. **가장 싼 개입 지점.** 4장의 비용 표처럼 같은 오해도 요청 단계에서 잡으면 질문 한 개로 끝난다.

한계도 분명하다. 모든 요청에 인터뷰를 거치면 오버헤드가 된다. Claude Code 문서는 한 문장으로 diff를 설명할 수 있는 작업이면 계획 단계를 건너뛰라고 권한다. 요청 단계 개입의 강도는 작업 규모와 결정의 비가역성에 비례시켜야 한다.

## 6. 해결 수단: 요청 구체화 프레임워크

공통 원리는 하나다. **사람이 모든 것을 미리 적게 하는 대신, AI가 사람을 인터뷰하게 만든다.** 사람은 무엇을 빠뜨렸는지 모르지만, 질문을 받으면 답할 수 있기 때문이다.

| 수단 | 방식 | 특징 |
| --- | --- | --- |
| [grill-me / grilling](https://github.com/mattpocock/skills) (Matt Pocock) | 설계 결정 트리를 라운드 단위로 인터뷰 | 질문마다 추천 답 제시, 합의 확인 전 실행 금지. Claude Code 외 에이전트에도 설치 가능 |
| [Claude Code 인터뷰 워크플로](https://code.claude.com/docs/en/best-practices) (공식 권장) | AskUserQuestion 도구로 인터뷰 후 SPEC.md 작성 | 스펙 완성 후 새 세션에서 구현 |
| Claude Code 플랜 모드 | 탐색→계획→구현 분리 | 파일 변경 전 계획을 사람이 편집·승인 |
| [Spec Kit](https://github.com/github/spec-kit) (GitHub) | specify → clarify → plan → tasks → implement | clarify가 과소명세 영역을 plan 전에 질의 |

### grill-me의 동작 원리

grill-me 자체는 짧은 진입점이고, 실제 방법은 grilling 스킬에 있다. 핵심 규칙은 다음과 같다.

- 모든 결정을 **설계 트리**로 보고, 선행 결정이 끝난 질문(frontier)만 한 라운드에 묻는다.
- 질문마다 번호를 붙이고 **추천 답**을 함께 제시한다. 사용자는 동의만 해도 된다.
- 환경에서 찾을 수 있는 사실은 서브에이전트가 직접 조사한다. 사용자에게는 결정만 묻는다.
- 트리의 모든 가지를 방문해 "조용히 가정한 것"이 없을 때 종료하고, 사용자 확인 전에는 실행하지 않는다.

원리를 이해하기 쉽게 사내용으로 축약한 스킬 예시다.

```markdown
---
name: clarify-first
description: 기능 구현 요청 시 구현 전에 요구사항을 인터뷰한다. "구현해줘", "만들어줘"로 시작하는 다중 파일 작업에 사용.
---
1. 코드베이스를 먼저 조사해 스스로 알 수 있는 사실은 묻지 않는다.
2. 아래 범주에서 아직 정해지지 않은 결정만 번호를 붙여 묻는다.
   - 인터페이스 계약 (입출력, 에러 처리)
   - 비기능 제약 (메모리 할당, 실시간성, 스레드 컨텍스트)
   - 범위 밖 항목 (이번에 하지 않을 것)
   - 완료 판정 기준 (어떤 테스트가 통과해야 하는가)
3. 각 질문에 추천 답을 붙인다.
4. 답을 받으면 다음 라운드 질문을 다시 계산한다.
5. 미결정 항목이 없으면 SPEC.md로 정리하고, 사용자 승인 전에는 코드를 쓰지 않는다.
```

이 스킬로 4장의 CAN 버퍼 요청을 처리하면 대략 이런 첫 라운드가 나온다.

```text
Q1 메모리: 동적 할당을 허용하나요?
   → 추천: 금지 (기존 코드에 malloc 사용 없음)
Q2 호출 컨텍스트: 수신 함수는 ISR에서 호출되나요?
   → 추천: 예 (can_isr.c에서 호출 확인)
Q3 오버플로 정책: 버퍼가 가득 차면?
   → 추천: 가장 오래된 프레임 폐기 + 카운터 증가
Q4 완료 기준: 어떤 테스트로 검증하나요?
   → 추천: 경계 조건 단위 테스트 (빈 버퍼, 가득 참, wrap-around)
```

Q1과 Q2의 추천 답은 에이전트가 코드베이스에서 확인한 사실에 기반한다. 사람은 확인만 하면 되고, 모르는 부분만 새로 결정하면 된다.

## 7. 사실 관계 검증

원래 논지는 대부분 사실로 확인됐다. 다만 두 곳은 표현을 다듬어야 반론에 견딘다.

| 원래 주장 | 판정 | 근거 및 보완 |
| --- | --- | --- |
| 사람은 요청에 필요한 정보를 빠짐없이 전달하지 못한다 | 사실 | 요구공학의 불완전·모호·불일치 분류, Ambig-SWE의 과소명세 전제 |
| AI는 부족한 정보를 스스로 채워 진행한다 | 사실 | HumanEvalComm: 60% 이상이 질문 없이 코드 생성. Ambig-SWE: 비상호작용이 기본값 |
| AI는 이용자 만족이라는 목적성 때문에 그렇게 한다 | 부분 사실 (보완 필요) | "목적성"보다 학습 편향이 정확하다. 단일 턴 선호 평가와 아첨 경향이 근거지만, 원 논문도 "추측"이라 표현함 |
| 부족한 정보는 원하는 결과와의 차이로 이어진다 | 사실 | HumanEvalComm Pass@1 35~52% 하락 |
| 목표가 느슨하면 알아서 만든 결과가 만족스러울 수 있다 | 사실 | Claude Code 문서도 탐색 목적이면 모호한 프롬프트가 유용하다고 명시 |
| 상업 개발은 구체적 목표가 있어 기대치 미달이 발생한다 | 타당 (정성적) | 직접 정량 연구는 찾지 못함. 요구 명확화 시 성능 회복 결과로 간접 지지 |
| 요청 단계 구체화 수단이 필요하다 | 사실 | Ambig-SWE: 상호작용 시 최대 74% 향상. Anthropic 공식 인터뷰 워크플로 존재 |
| grill-me는 요청 단계 인터뷰 스킬이다 | 사실 | mattpocock/skills 공식 README가 오정렬 문제의 해법으로 제시 |

**권장 표현 수정**

- "AI는 이용자를 만족시키려는 목적성이 있다" → "AI는 완결돼 보이는 응답을 선호하도록 학습된 경향이 있다". 의도를 가진 행위자처럼 쓰면 세미나 등에서 반론을 받기 쉽다.
- 최신 모델이 전보다 질문을 더 잘한다는 반론에 대비해야 한다. 그래도 **언제 물을지 스스로 판단하는 능력**은 여전히 병목이라는 2026년 결과로 답할 수 있다.

## 8. 결론

요청 명세의 불완전성은 휴먼인루프가 필요한 대표 상황이다. 사람만 가진 의도와 제약을 AI가 추측으로 대신 채우는 한, 자동 검증으로는 그 격차를 잡을 수 없다.

해법은 사람에게 완벽한 요청을 요구하는 것이 아니다. **AI가 먼저 묻도록 구조를 만드는 것**이다. 실무 적용 순서는 다음을 권한다.

1. 다중 파일·비가역 작업에는 인터뷰(grill-me, AskUserQuestion 인터뷰)를 기본 절차로 둔다.
2. 인터뷰 결과를 스펙 문서로 남기고, 범위 밖 항목과 완료 판정 기준을 반드시 포함한다.
3. 조직의 암묵지(코딩 규칙, 안전 제약)는 CLAUDE.md·스킬로 옮겨 매번 묻지 않아도 되게 한다.
4. 한 문장으로 설명되는 작은 작업은 인터뷰 없이 바로 진행한다.
