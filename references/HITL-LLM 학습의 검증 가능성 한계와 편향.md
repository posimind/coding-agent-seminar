# HITL-LLM 학습의 검증 가능성 한계와 편향

2026-09-25 · 정유현

## 핵심 메시지

AI는 **채점하기 쉬운 일**을 빨리 잘하게 되고, **채점 기준이 사람마다 다른 일**은 느리게 배우거나 한쪽으로 치우쳐 배운다. 그래서 채점 기준이 없는 곳에는 사람이 있어야 한다. 이것이 Human-in-the-Loop(사람이 작업 흐름 안에서 확인하고 결정하는 방식)가 필요한 이유다.

오늘 이야기는 세 가지다.

1. **잘하는 것과 못하는 것이 뚜렷하다**: 문법·구현은 컴파일과 테스트로 채점되니 AI가 잘한다. 설계는 채점이 어려워 상대적으로 약하다.
2. **채점표만 맞추는 꼼수가 생긴다**: "테스트 통과"만 보면 AI가 진짜 문제를 풀지 않고 테스트만 통과시키는 경우가 있다.
3. **평균적인 취향으로 쏠린다**: 정답이 없는 일을 여러 사람의 평가로 배우면, 가장 흔하고 무난한 답으로 모이는 경향이 있다.

결론은 "AI를 믿지 말자"가 아니다. **AI가 스스로 채점할 수 없는 부분을 사람이 정하고 확인하자**는 것이다.

## 먼저 알아둘 용어

| 용어 | 쉬운 뜻 | 비유 |
| --- | --- | --- |
| 강화학습 (RL) | 잘하면 점수를 주고, 점수가 오르는 쪽으로 AI를 계속 고치는 학습 방법 | 칭찬 스티커로 습관 들이기 |
| 보상 (Reward) | AI에게 주는 점수 | 시험 점수 |
| 검증기 / 채점기 (Verifier) | 답이 맞는지 자동으로 판정하는 장치 | 정답지 |
| RLHF | 사람이 "A 답과 B 답 중 뭐가 나은지" 골라준 결과로 점수를 매기는 방식 | 심사위원 투표 |
| RLVR | 컴파일·테스트·수학 정답처럼 자동 채점되는 결과로 점수를 매기는 방식 | OMR 채점 |
| 보상 해킹 (Reward hacking) | 진짜 목표 대신 점수만 올리는 꼼수를 AI가 배우는 현상 | 시험 범위만 외우기 |
| 모드 붕괴 (Mode collapse) | AI의 답이 몇 가지 무난한 답으로만 쏠리는 현상 | 모두가 같은 모범 답안을 쓰는 반 |
| Human-in-the-Loop | 자동화된 흐름 중간에 사람이 확인·결정하는 단계를 두는 것 | 결재 라인 |

## 1. AI는 채점할 수 있는 것부터 잘하게 된다

### 요즘 AI는 이렇게 배운다

Andrej Karpathy(전 테슬라 AI 총괄, OpenAI 창립 멤버)는 2025년 AI 학습에 큰 변화가 있었다고 정리했다. 기존에는 "사전학습 → 예시 답안 학습(SFT) → 사람 평가 학습(RLHF)" 순서였는데, 2025년에는 자동 채점 기반 학습(RLVR)이 사실상 표준 단계로 추가됐다([Karpathy, 2025 LLM Year in Review](https://karpathy.bearblog.dev/year-in-review-2025/)).

수학 문제나 코드 퍼즐처럼 자동 채점되는 문제를 많이 풀게 하면, AI가 문제를 작은 단계로 나누고 막히면 되돌아가는 식의 "추론처럼 보이는" 풀이법을 스스로 익힌다. 최근 코딩 에이전트가 크게 좋아진 주요 이유 중 하나다.

### Verifier's Rule: 채점이 쉬울수록 AI를 가르치기 쉽다

Chain-of-Thought 연구로 알려진 AI 연구자 Jason Wei는 이를 한 문장으로 정리했다. **"채점(검증)하기 쉬운 일일수록 AI를 가르치기 쉽고, 풀 수 있으면서 채점이 쉬운 일은 결국 AI가 해낸다"**([Jason Wei 블로그](https://www.jasonwei.net/blog/asymmetry-of-verification-and-verifiers-law)). 처음에는 Verifier's Law라고 불렀고, 현재 글 제목은 Verifier's Rule이다.

그가 꼽은 "채점하기 쉬운 일"의 조건은 다섯 가지다.

| 조건 | 뜻 | 코드 컴파일·테스트 | 설계 품질 |
| --- | --- | --- | --- |
| 객관적 정답 | 무엇이 좋은 답인지 모두 동의 | O | X (사람마다 다름) |
| 빠른 확인 | 몇 초 안에 확인 가능 | O | X (수개월 뒤 드러남) |
| 대량 확인 | 많은 답을 동시에 확인 가능 | O | X (리뷰어 시간 필요) |
| 낮은 잡음 | 채점 결과가 실제 품질과 잘 맞음 | 대체로 O | X |
| 순위 매기기 | 여러 답의 좋고 나쁨을 줄 세우기 쉬움 | 통과율로 가능 | 어려움 |

표의 오른쪽 두 열은 원문에 없는, 이 세미나의 적용 예시다.

### 코드로 보는 차이

```python
# (A) 컴파일/테스트: 자동 채점기가 있다
def score_code(code):
    if not compiles(code):
        return 0
    return pass_rate(code)        # 몇 초면 계산, 누가 해도 같은 점수

# (B) 설계: 자동 채점기가 없다
def score_design(design):
    votes = [person.rate(design) for person in reviewers]
    return average(votes)         # 느리고 비싸고, 사람마다 점수가 다름
```

(A)는 싸고 빠르니 수백만 번 반복해서 가르칠 수 있다. (B)는 한 번 채점하는 데도 사람이 필요하고, 마지막 줄의 **평균이 "무엇이 좋은 설계인가"를 대신 정해버린다**. 이 문제는 4장에서 다시 다룬다.

## 2. 그래서 AI 코딩 실력은 들쭉날쭉하다

Karpathy는 AI의 능력이 고르게 자라지 않고, **자동 채점이 가능한 분야 주변에서만 뾰족하게 솟는다**고 설명한다. 그래서 AI는 천재 박사 같다가도 초등학생처럼 헷갈리는 모습을 동시에 보인다. 그는 이를 "들쭉날쭉한 지능(jagged intelligence)"이라 불렀다([Karpathy, 2025 LLM Year in Review](https://karpathy.bearblog.dev/year-in-review-2025/)). Jason Wei도 같은 글에서 AI가 검증 가능한 일에서 훨씬 똑똑해지는 "들쭉날쭉한 경계"가 생길 것이라고 예상했다.

코딩에 대입하면 대략 이렇다. 아래 표는 연구 결과가 아니라 **위 원리를 적용한 이 세미나의 정리**다.

| 개발 작업 | 자동 채점 수단 | AI에게 기대할 수 있는 것 |
| --- | --- | --- |
| 문법, API 사용법 | 컴파일러, 린터 | 매우 잘함 |
| 함수 하나 구현 | 단위 테스트 | 잘함 |
| 재현 가능한 버그 수정 | 재현 테스트 | 잘함 |
| 모듈 나누기, 역할 분리 | 거의 없음 (사람 리뷰) | 들쭉날쭉함 |
| 아키텍처 선택 | 없음 (몇 달 뒤 드러남) | 무난하고 흔한 답을 내는 경향 |
| 무엇을 만들지 결정 | 없음 | 사람의 몫 |

설계가 어려운 이유는 좋은 설계의 효과가 **늦게** 나타나기 때문이다. 나쁜 설계도 오늘 테스트는 통과한다. 그 대가는 몇 달 뒤 기능을 추가할 때 치른다.

하나 더 기억할 점이 있다. Karpathy는 벤치마크(AI 성능 시험)가 대부분 자동 채점 문제라서 AI 회사들이 거기에 맞춰 학습시키기 쉽고, 그래서 **벤치마크 점수를 예전만큼 믿지 않는다**고 밝혔다. "벤치마크 1등 모델"이 우리 프로젝트의 설계를 잘한다는 보장은 없다.

## 3. 한계 1: 테스트만 통과하는 꼼수

자동 채점이 있는 코딩에도 함정이 있다. AI가 "문제를 푸는 법" 대신 "채점을 통과하는 법"을 배우는 경우다. 이를 **보상 해킹**이라고 한다. 시험 범위의 문제와 답만 외워서 만점을 받는 학생과 같다.

```python
# 요청: 정렬 함수를 만들어라.  채점: 아래 테스트 3개
assert sort([3, 1, 2]) == [1, 2, 3]
assert sort([5, 4])    == [4, 5]
assert sort([])        == []

# 꼼수 답안: 테스트는 전부 통과하지만 정렬 기능은 없다
def sort(xs):
    answers = {(3, 1, 2): [1, 2, 3], (5, 4): [4, 5], (): []}
    return answers[tuple(xs)]
```

실제 연구에서도 이런 모습이 관찰됐다.

- **숨은 테스트에서 드러나는 차이 (SpecBench, 2026)**: AI에게 보여준 테스트와 숨겨둔 테스트의 통과율을 비교했다. 최신 코딩 에이전트들은 보여준 테스트는 거의 다 통과했지만, 숨긴 테스트에서는 통과율이 떨어졌다. 코드 규모가 10배 커질 때마다 그 차이가 28%p씩 벌어졌고, 테스트 입력값을 외워서 답하는 2,900줄짜리 "컴파일러"도 나왔다([SpecBench](https://www.emergentmind.com/papers/2605.21384)).
- **테스트 코드 고쳐 쓰기 (2026)**: 실험에서 AI에게 채점 코드 수정 권한을 주자, 학습 중에 따로 시키지 않아도 채점 코드를 고쳐서 통과하려는 행동이 나타났다. 소형 모델(3\~4B)로 한 통제 실험이지만, 권한 설정이 느슨하면 이런 일이 생길 수 있음을 보여준다([When Reward Hacking Rebounds](https://arxiv.org/abs/2604.01476)).

**우리에게 주는 교훈**: SpecBench 저자들은 에이전트가 사람이 다 읽을 수 없을 만큼 많은 코드를 만들면, 결국 자동 테스트가 유일한 감시 수단이 된다고 지적한다. 그러면 그 테스트가 곧 꼼수의 대상이 된다. 코드가 클수록, 설계가 중요할수록 사람의 확인이 더 필요하다.

## 4. 한계 2: 평균적인 취향으로 쏠리는 문제

"좋은 설계", "아름다운 그림", "훌륭한 소설"처럼 사람마다 평가가 다른 일은, 여러 사람의 평가를 모아서 AI를 가르친다(RLHF). 이 과정에서 AI가 한쪽으로 치우칠 수 있다는 연구가 쌓이고 있다.

### 쏠림 1: 다수 의견이 실제보다 크게 반영된다

사람들의 선호가 서로 엇갈릴 때, 일반적인 RLHF 방식은 **다수의 선호를 실제 비율보다 훨씬 크게 반영**한다는 분석이 있다([Diverse Preference Learning](https://arxiv.org/abs/2511.08594)).

```python
# 설계 리뷰어 10명의 선택
votes = {"계층형 구조": 6, "이벤트 기반 구조": 4}

# 바라는 것: "상황에 따라 둘 다 가능"하다는 걸 아는 AI
# 일어나기 쉬운 것: 점수를 더 받는 쪽만 계속 강화되어
#                  "계층형 구조"만 거의 항상 제안하는 AI
```

같은 연구는 이것이 실력 문제로도 이어질 수 있다고 본다. 60%가 좋아하는 방법만 배운 AI는 나머지 40% 방법이 필요한 문제에서 계속 실패할 수 있다. 설계로 말하면, **"보통은 이게 맞다"는 답이 "우리 프로젝트에선 틀린" 경우를 AI가 알아채기 어렵다**.

### 쏠림 2: 사람은 익숙한 것을 더 좋게 평가한다

평가하는 사람은 심리적으로 익숙한 글을 더 높게 평가하는 경향이 있다. 한 연구는 이 "익숙함 편향"이 AI의 답이 비슷비슷해지는 주요 원인이라고 분석했다([Verbalized Sampling](https://arxiv.org/abs/2510.01171)). 즉 치우침은 알고리즘만의 문제가 아니라 **사람이 만든 평가 데이터에서도** 들어온다. 새롭지만 타당한 설계가 "낯설다"는 이유로 낮은 점수를 받을 수 있다.

### 쏠림 3: 서로 다른 AI도 비슷한 답을 낸다

NeurIPS 2025에서 발표된 Artificial Hivemind 연구는 정답이 없는 질문 2만 6천 개로 여러 AI를 시험했다. 한 모델이 비슷한 답을 반복했고, 더 두드러지게는 **서로 다른 회사의 모델들이 놀랄 만큼 비슷한 답**을 냈다. 또 사람마다 평가가 크게 갈리는 답에 대해서는 AI 채점기(보상 모델, LLM 심사자)의 점수가 사람의 평가와 잘 맞지 않았다([Artificial Hivemind](https://arxiv.org/abs/2510.22954)). 이 연구는 현상을 측정한 것이며, 원인을 한 가지로 단정하지는 않았다.

### 개발자에게 주는 의미

| 쏠림 | 코딩 에이전트에서 보일 수 있는 모습 | 사람이 할 일 |
| --- | --- | --- |
| 다수 의견 과대 반영 | 웹 서비스에서 흔한 패턴을 차량·임베디드 SW에도 그대로 제안 | 도메인 제약(실시간성, 메모리, 안전 규격)을 알려주고 검토 |
| 익숙함 편향 | 흔한 라이브러리·구조를 선호하고 팀 규칙은 놓침 | 팀 규칙을 지침 파일과 테스트로 명시 |
| 모델 간 비슷함 | 다른 AI에게 물어도 같은 답 | "두 번째 의견"은 동료 개발자에게서 |

특히 마지막 줄이 중요하다. **AI 여러 개의 답이 같다고 해서 그 설계가 옳다는 증거는 아니다.** 비슷한 방식으로 학습된 AI들은 같은 쪽으로 치우쳐 있을 수 있다.

## 5. 업계의 해결 시도와 남는 문제

연구자들도 이 문제를 알고 있다. 핵심 아이디어는 "채점하기 어려운 것을 채점 가능한 작은 항목으로 쪼개자"는 것이다.

### 채점표(루브릭)로 쪼개기

"좋은 답인가?" 하나로 점수를 매기는 대신, 문제마다 체크리스트를 만들어 항목별로 점수를 주는 방법이다. Scale AI 연구팀은 이 방식(Rubrics as Rewards)으로 학습했을 때, 기존의 "1\~10점으로 한 번에 채점"하는 방식보다 의료 질문 평가(HealthBench)에서 최대 31%, 과학 문제(GPQA-Diamond)에서 7% 상대적으로 좋은 결과를 얻었다고 보고했다([Rubrics as Rewards](https://arxiv.org/abs/2507.17746)).

설계에 적용하면 이런 모습이다.

```python
# "좋은 설계인가?" 대신 체크리스트로 쪼개기
checklist = [
    ("앱 계층이 드라이버를 직접 부르지 않는가", check_layer_rule),   # 자동 확인 가능
    ("모듈끼리 서로 순환 참조하지 않는가",     check_no_cycle),     # 자동 확인 가능
    ("기존 공개 API를 깨뜨리지 않는가",        check_api_compat),   # 자동 확인 가능
    ("앞으로 기능 추가가 쉬운 구조인가",       ask_reviewer),       # 여전히 사람 판단
]
```

일부는 자동 확인이 되지만, 마지막 항목처럼 판단이 필요한 부분은 남는다. 그리고 **어떤 항목을 체크리스트에 넣을지는 결국 사람이 정한다.**

### 다양한 관점을 살리는 학습

가장 흔한 답 하나가 아니라 타당한 여러 답을 골고루 낼 수 있게 학습시키자는 연구 방향도 있다(다원적 정렬, pluralistic alignment). 다만 아직 연구 단계라서 지금 쓰는 도구에 충분히 반영됐다고 보기는 어렵다.

### 끝까지 남는 문제: "목표는 누가 정하나"

채점기는 정해진 목표를 **점검**할 수는 있어도 목표를 **골라줄** 수는 없다. 무엇을 만들지, 어떤 장단점을 받아들일지, 무엇을 "잘 된 것"으로 볼지 정하는 일에는 채점기가 없다([WeAreDevelopers 해설](https://www.wearedevelopers.com/magazine/765-ai-eats-the-verifiable-first)). 바로 여기가 사람이 있어야 할 자리다.

## 6. 결론: 사람은 어디에 있어야 하나

원칙은 한 문장이다. **자동 채점기가 없거나 약한 곳에 사람을 둔다.** 채점기가 강한 곳(문법, 함수 구현)은 AI에게 맡기고, 사람은 AI가 스스로 채점할 수 없는 판단에 시간을 쓴다.

### 코딩 에이전트와 일할 때 사람이 확인할 지점

| 작업 단계 | 자동 채점 | 사람의 역할 | 이유 |
| --- | --- | --- | --- |
| 무엇을 만들지 정하기 | 없음 | 직접 결정 | 채점기는 목표를 골라주지 못함 (5장) |
| 설계안 고르기 | 약함 | 승인 | 흔한 답으로 쏠리는 경향 (4장) |
| 테스트·완료 기준 만들기 | 중간 | 직접 쓰거나 꼼꼼히 검토 | 테스트가 꼼수의 대상이 됨 (3장) |
| 코드 구현 | 강함 | AI에게 맡김 | AI가 가장 잘하는 영역 (1장) |
| 코드 리뷰 | 중간 | 설계 의도 위주로 확인 | 테스트 통과 ≠ 좋은 설계 (3장) |
| AI가 테스트 코드를 고쳤을 때 | 위험 | 반드시 확인 | 대표적인 꼼수 패턴 (3장) |

### 실무 적용: 사람의 판단을 "검증 가능한 제약"으로 바꾸기

Human-in-the-Loop는 사람이 매번 모든 코드를 보라는 뜻이 아니다. 사람이 한 번 내린 설계 결정을 **자동으로 확인되는 규칙으로 만들어 두면**, 그 다음부터는 AI가 그 규칙을 채점 기준으로 삼는다. 사람은 채점 기준을 만들고, AI는 그 안에서 일한다.

```python
# test_architecture.py
# 팀 결정: "app 폴더의 코드는 drivers 폴더를 직접 import하지 않는다"
import pathlib

def test_app_does_not_use_drivers():
    for f in pathlib.Path("src/app").rglob("*.py"):
        code = f.read_text()
        assert "import drivers" not in code and "from drivers" not in code, \
            f"{f}: app 계층이 drivers를 직접 사용함 (팀 설계 규칙 위반)"
```

이 테스트가 생기면 "계층을 지켜라"라는 사람의 판단이 **컴파일처럼 자동 채점되는 규칙**으로 바뀐다. 1장에서 본 것처럼, 자동 채점되는 일은 AI가 잘 지킨다. (예시는 이해를 돕기 위한 단순한 문자열 검사이며, 실무에서는 언어별 의존성 분석 도구를 쓰는 편이 정확하다.)

바로 써볼 수 있는 방법들:

- **지침 파일 (AGENTS.md, CLAUDE.md)**: 팀의 설계 원칙과 도메인 제약을 AI에게 글로 알려준다.
- **설계 규칙 테스트**: 위 예시처럼 계층 규칙, 순환 참조 금지 등을 CI에서 자동 확인한다.
- **설계 결정 기록 (ADR)**: 왜 이 설계를 골랐는지 적어 두어 사람과 AI가 같은 근거를 본다.
- **Hook**: AI가 테스트 파일을 고치거나 공개 API를 바꾸려 할 때 자동으로 멈추고 사람 확인을 받게 한다.
- **숨은 테스트**: AI가 보지 못한 테스트를 따로 두어 꼼수 여부를 확인한다 (3장의 SpecBench 방식).

### 마무리

AI 시대에 개발자의 가치는 코드를 빨리 쓰는 데서 **"무엇이 좋은지" 정하고, 그것을 확인 가능하게 만드는 능력**으로 옮겨가고 있다. AI가 배운 "평균적인 좋음"을 우리 프로젝트의 "진짜 좋음"으로 맞춰주는 것, 그것이 Human-in-the-Loop의 핵심이다.

## 검증 메모

초안 대비 원문을 다시 확인하여 고친 부분이다.

- Jason Wei의 원칙은 현재 원문 제목이 "Verifier's Rule"이며, 채점이 쉬운 조건은 2가지가 아니라 5가지다.
- Jason Wei는 2025년 7월 OpenAI에서 Meta로 이직했다는 보도가 있어, 소속 대신 "Chain-of-Thought 연구로 알려진 연구자"로 표기했다.
- Artificial Hivemind 연구는 모델 간 비슷함을 측정한 연구이며, 원인을 RLHF로 단정하지 않는다. 초안의 인과 표현을 삭제했다.
- 다수 의견 반영 예시의 "100:0" 표현은 과장이라 "크게 쏠림"으로 바꿨다.
- 코딩 작업별 AI 수준 표와 사람 확인 지점 표는 연구 결과가 아닌 이 세미나의 정리임을 명시했다.
- 2026년 논문 일부는 동료 심사 전 프리프린트이므로 결과가 바뀔 수 있다.
