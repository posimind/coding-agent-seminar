# Human in the Loop가 필요한 이유 ① — 컨텍스트 한계

> **한 줄 요약**
> 코딩 에이전트는 코드베이스 전체를 한 번에 볼 수 없습니다.
> 필요해 보이는 부분만 **검색해서 골라 읽고** 수정하기 때문에,
> 검색에 걸리지 않은 연결 코드는 "없는 것"으로 판단합니다.
> 그 빈틈을 채우는 것이 사람의 역할입니다.

---

## 1. 컨텍스트(Context)란? — "에이전트의 책상"

LLM은 대화 내용, 읽은 파일, 도구 실행 결과를 전부 **컨텍스트**라는 작업 공간에 올려놓고 생각합니다.
책상에 비유하면 이해가 쉽습니다.

- 책상 위에 올려놓은 자료만 보면서 판단할 수 있다
- 책상 크기는 정해져 있다 (= 컨텍스트 허용치)
- 책상 밖에 있는 자료는 **존재하는지조차 모른다**

컨텍스트 크기는 **토큰(token)** 단위로 셉니다. 코드 한 줄은 대략 10~13 토큰 정도입니다.

```text
int speed = get_vehicle_speed();   // 이 한 줄 ≈ 10~13 토큰
```

---

## 2. 코드베이스는 책상보다 훨씬 크다

2026년 현재 최신 모델(예: Claude Opus 5.5)의 컨텍스트는 **1M(100만) 토큰**입니다.
커 보이지만 코드로 환산하면 이렇습니다.

| 컨텍스트 크기 | 담을 수 있는 코드 (추정) | 비고 |
|---|---|---|
| 200K 토큰 | 약 1.5만~2만 줄 | 중간 크기 서비스 하나 |
| 1M 토큰 | 약 7.5만~10만 줄 | 큰 앱 하나, 대부분의 모노레포는 불가 |
| 우리 플랫폼 | **수백만 줄 이상** | 커널, BSP, 미들웨어, 앱, 빌드 레시피… |

게다가 책상에는 코드만 올라가는 것이 아닙니다.
시스템 프롬프트, 지침 파일(CLAUDE.md / AGENTS.md), 대화 기록, 빌드 로그도 같은 공간을 나눠 씁니다.

👉 **결론: 대규모 코드베이스를 통째로 올려놓고 추론하는 것은 불가능합니다.**

---

## 3. 그래서 에이전트는 "검색해서 일부만" 본다

전체를 못 보니, 에이전트는 사람이 처음 보는 코드를 파악할 때처럼 **검색**부터 합니다.

```text
[요청] "on_door_open 함수에 로그를 추가하고 인자 검증을 넣어줘"

 1) grep / rg 로 관련 키워드 검색
 2) 검색된 파일 몇 개만 읽기
 3) 읽은 범위 안에서 영향도 판단
 4) 수정
```

실제로 코딩 에이전트는 수정 전 작업 시간의 절반 이상을 **코드 찾기**에 쓴다는 측정도 있습니다.
문제는 3번입니다. **"읽은 범위 안에서"** 판단한다는 점이죠.

---

## 4. 검색에 안 걸리는 연결이 있다

`grep`은 **글자가 똑같이 적혀 있는 곳**만 찾아줍니다.
그런데 실제 코드에는 글자로 드러나지 않는 연결이 많습니다.

```c
/* handlers.c — 에이전트가 수정하려는 함수 */
void on_door_open(const event_t *ev) { ... }

/* event_table.c — 함수 포인터로 등록 */
static const handler_t table[] = {
    { EVT_DOOR_OPEN, on_door_open },
};

/* isr.c — 인터럽트 문맥에서 번호로 찾아서 호출 */
void door_irq(void) {
    table[find(EVT_DOOR_OPEN)].fn(&ev);   // "on_door_open(" 이라는 글자가 없음
}
```

에이전트의 시야에서는 이렇게 보입니다.

```text
검색어 : "on_door_open("
결과   : handlers.c:12  void on_door_open(const event_t *ev) {   ← 정의만 보임
판단   : "직접 호출하는 곳이 없네. 로그(printf)랑 mutex 추가해도 되겠다"
실제   : 인터럽트 문맥에서 호출됨 → sleep 가능한 코드 추가 시 시스템 문제 발생
```

에이전트가 멍청해서가 아닙니다. **책상 위에 그 정보가 없었을 뿐**입니다.

비슷한 유형은 흔합니다.

- 함수 포인터 / 콜백 테이블
- 매크로로 만들어지는 함수 이름
- 코드 생성기가 만든 코드 (예: ARXML → SOME/IP 스켈레톤, 소스 트리에 없음)
- 문자열로 연결되는 설정 (디바이스 트리 `compatible`, 설정 파일 기반 등록)
- 빌드 설정에 따라 달라지는 코드 (`#ifdef`, Yocto `bbappend`)
- 코드 밖의 규칙 ("이 콜백은 절대 블로킹하면 안 됨" 같은 팀의 암묵지)

그리고 이런 수정은 **테스트도 통과할 수 있습니다.** 한 연구에서는 테스트를 통과한 AI 패치의 약 30%가 사람이 만든 정답 패치와 다르게 동작했고, 그중 상당수는 실제로 틀린 수정이었습니다. 테스트가 에이전트가 못 본 연결까지 검사해주지는 않기 때문입니다.

## 5. "그럼 컨텍스트가 더 커지면 해결되나요?"

아쉽게도 **"다 들어간다"와 "다 제대로 본다"는 다릅니다.**

여러 연구에서, 최신 모델도 입력이 길어질수록 정확도가 떨어지는 현상이 확인되었습니다. 이를 **Context Rot(컨텍스트 부패)** 라고 부릅니다.
필요한 정보가 책상 위에 분명히 있는데도, 자료가 너무 많으면 놓치는 것이죠.

📖 **장편소설로 비유하면**

LLM에게 장편소설을 쓰게 하면, 1장에서 "초록색 눈"이었던 주인공이 15장에서 "갈색 눈"이 되는 식의 모순이 생깁니다. 글이 길수록, 그리고 **앞뒤 거리가 멀수록** 이런 실수가 늘어납니다.
코드도 똑같습니다. 수정하는 파일과 **멀리 떨어진 곳**에 있는 연결일수록 놓치기 쉽습니다.

모델은 세대마다 좋아지고 있어서 실수의 **빈도**는 줄고 있습니다.
하지만 "전부 볼 수 없고, 봐도 흐려진다"는 **구조**는 그대로입니다.

---

## 6. "서브에이전트 여러 개로 전체를 나눠서 조사하면?"

좋은 아이디어이고 실제로 쓰이는 방법입니다. 하지만 **매 수정마다** 쓰기는 어렵습니다.

| 문제 | 설명 |
|---|---|
| 💰 비용 | 멀티 에이전트 방식은 일반 대화보다 토큰을 **약 15배** 더 쓴다는 보고가 있음. 수백만 줄을 매번 훑으면 크레딧이 순식간에 소진됨 |
| ⏱️ 시간 | 한 줄 수정에 전체 조사를 돌리면 수정보다 조사가 훨씬 오래 걸림 |
| 📝 요약 손실 | 서브에이전트는 수만 토큰을 읽고 **1~2천 토큰 요약**만 돌려줌. 정작 필요한 코너케이스가 요약에서 빠질 수 있음 |

즉, 돈과 시간을 들여도 **완벽함이 보장되지 않습니다.**
그래서 이 방법은 공개 API 변경, 대규모 리팩토링처럼 **영향이 큰 작업에만 골라서** 쓰는 것이 현실적입니다.

---

## 7. 그래서 사람이 필요한 지점

사람은 에이전트의 **"책상 밖 기억"** 역할을 합니다.

| 사람의 역할 | 예시 |
|---|---|
| 숨은 연결 알려주기 | "이 함수는 ISR에서 호출돼", "이 인터페이스는 ARXML에서 생성돼" |
| 영향 범위 판단 | "이 구조체는 다른 ECU와 공유하니까 필드 순서 바꾸면 안 돼" |
| 결과 검증 | diff를 보고 "이 변경이 다른 모듈에 영향 없나?" 확인 |
| 조사 수준 결정 | 간단한 수정은 빠르게, 위험한 수정은 전체 빌드·정밀 조사 지시 |

## 8. 신규 입사자를 위한 실전 팁

1. **에이전트에게 숨은 연결을 먼저 알려주세요.**
   반복해서 필요한 정보는 지침 파일(CLAUDE.md / AGENTS.md)에 적어두면 매번 설명할 필요가 없습니다.

   ```markdown
   ## 주의 사항
   - src/events/ 의 핸들러는 인터럽트 문맥에서 호출됨 → 블로킹 함수 금지
   - gen/ 폴더는 ARXML에서 자동 생성됨 → 직접 수정 금지
   ```

2. **"어디서 호출되는지 확인했어?"라고 물어보세요.**
   에이전트가 무엇을 근거로 판단했는지 확인하는 습관이 중요합니다.

3. **grep보다 확실한 도구를 함께 쓰세요.**
   전체 빌드, 링크, 정적 분석, 테스트는 에이전트가 못 본 연결을 기계적으로 드러내 줍니다.

4. **"테스트 통과 = 정답"이 아닙니다.**
   최종 diff는 반드시 사람이 읽고, 특히 **수정 파일 밖의 영향**을 생각해 보세요.

---

## 핵심 정리

1. 코딩 에이전트는 **컨텍스트(책상) 크기**의 한계 때문에 대규모 코드베이스 전체를 한 번에 볼 수 없다.
2. 그래서 **검색으로 일부만** 보고 판단하며, 검색에 걸리지 않은 연결은 놓친다. 컨텍스트가 커져도 **많이 담을수록 흐려지는** 문제가 남는다.
3. 전체 조사는 **비용·시간·요약 손실** 때문에 매번 쓸 수 없다.
   → 숨은 연결을 알고 영향 범위를 판단하는 **사람의 검토(Human in the Loop)** 가 여전히 필요하다.
